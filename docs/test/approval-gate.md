# 테스트 문서: 승인 게이트 — 워크로드 타입이 갖추는 보호 장치

> 📌 **2026-11-05 개정**: 이 문서는 `approval-gated` 워크로드 타입의 테스트 문서(`approval-gated-workload.md`)였다.
> 그 타입이 제거되고 PRD가 게이트를 쓰는 타입들의 공통 계약([`../prd/approval-gate.md`](../prd/approval-gate.md))이
> 되면서, 아래 시나리오는 **게이트를 쓰는 타입의 세션**으로 실행한다 — 지금은 `minimax-code`(그 PRD의 「적용 타입」).
> 타입 선택을 다루던 시나리오 1(AC-F1)은 AC와 함께 폐기했고, 나머지 시나리오 번호는 식별자라 바꾸지 않았다.
> 타입마다 다른 점(헬퍼 파드의 추가 컨테이너·포트, 세션 MCP 등록 방식, 아카이브 게이트 이름)은 그 타입 PRD가
> 열거하며, 아래 기대 결과는 그 열거를 그대로 따른다.

## 검증 대상 AC
- AC-F2: Egress 격리 — 워크로드 파드는 세션 헬퍼 파드를 통해서만 밖으로 나간다 (PRD: 승인 게이트)
- AC-F3: 승인 게이트 — 외부 도구는 사람이 승인해야 실행된다 (PRD: 승인 게이트)
- AC-F4: 보조 파드 = 세션 전용 헬퍼 파드(MCP·credential-proxy 컨테이너), 수명은 세션과 일치 (PRD: 승인 게이트)
- AC-F5: 파일 교환 = 세션 전용 RWX 공유 볼륨, 아카이브에 포함 (PRD: 승인 게이트)
- AC-F6: 자격 증명 분리 — 게이트웨이 호출자 토큰은 MCP 컨테이너에, 공급자 자격 증명은 프록시 컨테이너에 (PRD: 승인 게이트)

> 📌 **재사용 범위**: 게이트를 쓰는 타입의 원샷 실행·직렬 큐·1 MiB prompt·offset 커서·SSE 재연결·아카이브
> 왕복은 그 타입의 계약이고(`minimax-code`는 AC-G1~G4가 `claude-code`의 AC-E2~E5를 재사용한다), 그 검증은
> 그 타입의 테스트 문서가 갖는다. 아래 시나리오는 **게이트가 더하는 차이**만 다룬다.

> ⚠️ **검증 수단 주의**: AC-F2(egress 차단)와 AC-F4(헬퍼 파드 동반 회수)는 참조 구현(`dlddu/pure-agent`)이
> 클러스터에 배선된 적 없는 미검증 전제 위에 있다. 두 AC는 **코드 단언이 아니라 실클러스터 확인**으로
> 검증한다(kind overlay 또는 실 클러스터). `../doc-tracker/`의 미검증 전제 항목 참고.

## 테스트 시나리오

### 시나리오 2: 워크로드 파드의 egress 차단 실측
- **사전 조건**: 실클러스터(또는 NetworkPolicy를 집행하는 CNI가 켜진 kind overlay)에 active 상태의 게이트를 쓰는 타입의 세션 2개(S1, S2)
- **실행 단계**: S1의 워크로드 파드 주 컨테이너에서 (a) kube-dns로 이름 조회 → (b) S1 헬퍼 파드의 **MCP 포트**로 연결 → (c) 같은 헬퍼 파드의 **프록시 포트**(와 타입 PRD가 더한 헬퍼 포트 — `minimax-code`는 K3s MCP 프록시 `8093`, AC-G6)로 연결 → (d) 임의 외부 목적지(공개 IP·다른 네임스페이스의 서비스)로 연결 → (e) **공급자 API origin으로 직접** 연결 → (f) 승인 게이트웨이 주소로 직접 연결 → (g) **S2의 헬퍼 파드 주소**로 직접 연결 → (h) 세션 삭제 후 네트워크 정책 오브젝트 확인
- **기대 결과**: (a)·(b)·(c)는 성공. (d)·(e)·(f)·(g)는 타임아웃 또는 거부되어 연결이 성립하지 않음 — **워크로드 파드의 허용 목록에 외부 origin이 하나도 없으므로** 공급자 API를 가장한 우회도 불가능하고, 다른 세션의 헬퍼 파드도 ingress 제한으로 빌려 쓸 수 없다. (h) 세션마다 올바른 셀렉터의 egress·ingress 정책 오브젝트가 존재했고 삭제 시 함께 사라짐
- **검증 AC**: AC-F2

### 시나리오 2-1: 공급자 호출은 헬퍼 파드의 프록시 컨테이너만 수행한다
- **사전 조건**: 시나리오 2와 같은 환경. 공급자 upstream을 관찰할 수 있는 테스트 대역
- **실행 단계**: (a) 프롬프트를 write해 정상 실행이 일어나게 함 → upstream에 도달한 연결의 출발 파드를 확인 → (b) 헬퍼 파드의 프록시 컨테이너를 일시 중단하고 다시 write → (c) 워크로드 파드에서 프록시를 우회해 upstream으로 직접 연결 시도
- **기대 결과**: (a) upstream에 도달한 연결은 **전부 헬퍼 파드에서 출발**하고 워크로드 파드에서 출발한 것은 하나도 없다. 실제 Authorization은 프록시가 주입한 플랫폼 토큰 하나뿐이다. (b) 프록시 컨테이너가 없으면 실행이 실패하되 세션은 `active`로 남고, 같은 파드의 MCP 컨테이너를 쓰는 승인 경로는 계속 동작한다(공급자 경로가 프록시 단일 통로임을 입증). (c) 직접 연결은 차단된다
- **검증 AC**: AC-F2, AC-F6

### 시나리오 3: 승인(APPROVED) 경로 — write 즉시 반환, 대기 표시, 승인 후 실행
- **사전 조건**: active 상태의 게이트를 쓰는 타입의 세션 1개. 결정을 제어할 수 있는 승인 게이트웨이(실물 또는 테스트 대역)와 호출을 관찰할 수 있는 외부 테스트 upstream
- **실행 단계**: output SSE를 연 뒤 외부 도구를 부르게 하는 프롬프트를 write → write 반환 시각 기록 → 결정을 내리지 않은 채 SSE·read 관찰 → 게이트웨이에서 승인 → 이후 SSE·read·테스트 upstream 로그 확인
- **기대 결과**: write는 승인 대기를 기다리지 않고 **즉시 반환**한다. 결정 전 SSE와 같은 커서의 read에 `awaiting approval` in-band 마커가 나타나고, 그 사이 **테스트 upstream에는 어떤 요청도 도달하지 않는다**. 승인 후에야 실제 외부 호출이 한 번 일어나고 결과가 같은 바이트열에 이어 붙는다. 모든 event id/`nextOffset`과 decoded byte 길이가 일치하며 커서는 UTF-8 code-point 경계다(별도 event type 없음). 승인 요청의 외부 식별자는 `{세션ID}:{요청ID}` 형태다
- **검증 AC**: AC-F3

### 시나리오 4: 거절·만료·타임아웃 경로 — 도구 실패가 세션을 죽이지 않는다
- **사전 조건**: active 상태의 게이트를 쓰는 타입의 세션 1개. 결정을 REJECTED/EXPIRED로 만들거나 응답을 지연시켜 타임아웃을 유발할 수 있는 게이트웨이
- **실행 단계**: (a) 외부 도구 호출 프롬프트를 write → 게이트웨이에서 **거절** → (b) 같은 세션에 다시 write → 결정 없이 **만료** → (c) 다시 write → 폴링 타임아웃까지 방치 → 각 경우 read/SSE·세션 상태·테스트 upstream 확인 → (d) 세 번의 실패 뒤 정상 프롬프트를 write
- **기대 결과**: 세 경우 모두 **실제 외부 호출이 일어나지 않고** 도구가 실패 결과를 반환하며, 그 사실이 in-band 마커로 출력에 남는다. 세션 상태는 계속 `active`이고 실행 큐는 막히지 않으며, (d)의 후속 write가 정상 처리된다. 실패가 세션·pod를 종료시키지 않는다
- **검증 AC**: AC-F3

### 시나리오 5: 승인 대기가 유휴 카운트를 진행시키지 않는다
- **사전 조건**: active 상태의 게이트를 쓰는 타입의 세션 1개. 시간을 제어할 수 있는 테스트 하네스와 결정을 보류할 수 있는 게이트웨이
- **실행 단계**: 외부 도구 호출 프롬프트를 write → 결정을 보류한 채 유휴 한계를 넘길 만큼 시간을 진행 → `lastAccess`와 세션 상태를 관찰 → 게이트웨이에서 결정 → 다시 클라이언트 I/O 없이 시간을 진행하며 관찰
- **기대 결과**: 승인 대기 중에는 클라이언트 read/write가 없어도 `lastAccess`가 갱신되어 유휴 카운트가 진행되지 않고 세션이 동결되지 않는다. **결정이 난 뒤에는 갱신이 멈추고** 일반 유휴 카운트가 다시 진행되어 한계 도달 시 정상적으로 동결된다. 같은 조건에서 `shell`·`claude-code` 세션은 (승인 개념이 없으므로) 기존 AC-D5/AC-B1 그대로 동결됨을 대조 확인한다
- **검증 AC**: AC-F3 (AC-B1 구체화)

### 시나리오 6: 공유 볼륨 파일 왕복 — 동결·복원을 건너서도 남는다
- **사전 조건**: active 상태의 게이트를 쓰는 타입의 세션 1개(공유 볼륨 opt-in과 그 타입의 아카이브 게이트 — `minimax-code`는 `MINIMAX_CODE_ARCHIVE_ENABLED`, AC-G4 — 가 켜진 배포). 승인 시 파일 결과물을 만드는 외부 도구 호출을 준비. 동결 직전 read로 커서 확보(`cursorBefore`)
- **실행 단계**: (a) 승인된 외부 호출로 공유 볼륨에 파일을 만들게 함 → 워크로드 파드와 헬퍼 파드의 MCP 컨테이너 양쪽에서 같은 경로의 파일·내용 확인 → (b) **동결·복원을 건너뛰고** 곧바로 다음 프롬프트로 그 파일을 읽게 함 → (c) 세션 동결(유휴 한계 또는 스냅샷 직접 호출) → 재접근으로 복원 → 같은 파일 재확인 → (d) `cursorBefore`로 read, `offset=0`으로 read → (e) 다른 세션의 워크로드 파드에서 이 볼륨 접근 시도
- **기대 결과**: (a) 워크로드 파드와 헬퍼 파드의 MCP 컨테이너가 같은 파일을 같은 내용으로 본다(RWX 공유 마운트 — 같은 파드의 프록시 컨테이너에는 마운트되지 않는다). (b) **동결을 거치지 않은 다음 실행도** 그 파일을 그대로 본다 — 파일 전달이 도구 응답 본문이 아니라 볼륨으로 이뤄진다. (c) 복원 후에도 파일이 남아 있고 내용이 일치한다(볼륨 내용이 아카이브에 포함되어 그 라운드의 **새** 공유 볼륨에 전개된다 — 볼륨 클레임 자체는 새것이다). (d) `cursorBefore` read는 델타만, `offset=0`은 동결 전·후 전체 이력을 반환한다. (e) 다른 세션은 이 볼륨을 마운트하지 못한다
- **검증 AC**: AC-F5 (AC-B3의 게이트 타입 경로)

### 시나리오 7: 스냅샷·삭제 시 헬퍼 보조 파드 동반 회수
- **사전 조건**: 실클러스터에 active 상태의 게이트를 쓰는 타입의 세션 2개(S1, S2). 각 세션의 워크로드 파드와 헬퍼 파드(게이트의 컨테이너 둘 + 타입이 더한 것)를 라벨로 식별해 둠
- **실행 단계**: (a) 두 세션의 pod 목록을 라벨로 조회 → (b) S1을 스냅샷으로 동결 → pod 목록·가용 자원 확인 → (c) S1에 재접근하여 복원 → pod 목록 확인 → 외부 도구 호출로 새 MCP 연결 확인, 프롬프트 실행으로 새 프록시 경로 확인 → (d) S1을 삭제 → pod 목록 확인
- **기대 결과**: (a) 세션마다 워크로드 파드 1 + 헬퍼 파드 1이 별개로 존재하고(헬퍼 파드의 컨테이너는 게이트의 MCP·credential-proxy 둘에 타입 PRD가 열거한 것을 더한 집합과 정확히 같다) 두 세션이 어떤 파드도 공유하지 않는다. (b) S1의 **두 파드가 모두** 사라지고 클러스터 가용 자원이 회복되며 S2의 파드는 그대로다(AC-A3). 헬퍼 파드는 스냅샷 대상이 아니므로 별도 아카이브가 생기지 않는다. (c) 복원 시 두 파드가 함께 새로 기동되고, 워크로드 파드에 **그때 만들어진 헬퍼 파드 주소**가 주입되어 승인 경로와 공급자 경로가 모두 다시 성립한다. (d) 삭제 후 S1의 두 파드와 egress·ingress 정책·공유 볼륨이 사라지고 S2는 영향을 받지 않는다
- **검증 AC**: AC-F4 (AC-A2/A3·B1/B2 구체화)

### 시나리오 8: 자격 증명의 컨테이너별 분리와 프록시 계약의 배치 무관성
- **사전 조건**: control plane 에 게이트웨이 URL(`APPROVAL_GATEWAY_URL`)을 주고, 헬퍼 파드의 서비스 어카운트(`session-mcp`)를 게이트웨이(PocketAide)에 호출자로 등록하고, 게이트 타입의 Secret·ConfigMap에 AC-E6과 같은 이름의 키(Secret `auth-token`, ConfigMap `base-url`·optional `model`)를 준비(`minimax-code`는 `minimax-code-credentials`·`minimax-code-config`, AC-G3)
- **실행 단계**: (a) 게이트를 쓰는 타입의 세션의 pod 스펙에서 워크로드 파드와 헬퍼 파드 두 컨테이너의 환경 변수·볼륨 마운트·서비스 어카운트를 각각 확인 → (b) 생성 요청 본문에 게이트웨이 URL·API key·`userId`·공급자 자격 증명을 넣어 생성 시도 → (c) 승인 요청을 하나 만든 뒤 게이트웨이에 실제로 전달된 컨텍스트를 확인 → (d) 게이트웨이 호출자 토큰·공급자 토큰 문자열로 read/SSE 출력·control-plane 로그를 검색 → (e) AC-E6의 프록시 검증 항목(고정 HTTPS upstream·평문 HTTP 시작 거부, 헤더 제거와 토큰 단일 주입, CONNECT/Upgrade 거부, 1xx 포함 redaction, upstream EOF 전 safe SSE chunk 전달, response-read 경계 split-token redaction, raw 64 MiB 상한)을 **파드 IP 바인딩 상태에서** 재실행 → (f) 다른 세션의 워크로드 파드에서 이 헬퍼 파드로 연결 시도 → (g) model 계약(concrete/`platform-default`/invalid) 재확인 → (h) 워크로드 파드의 entrypoint 로그와 에이전트 도구 목록을 확인 → (i) 헬퍼 파드의 MCP 컨테이너에서 프록시 컨테이너의 환경 변수·`/proc` 항목 읽기를 시도
- **기대 결과**: (a) 게이트웨이 URL과 호출자 토큰(audience `pocket-aide` 의 projected 서비스 어카운트 토큰 파일)은 헬퍼 파드의 **MCP 컨테이너에만** 있고 헬퍼 파드는 apiserver 용 토큰을 마운트하지 않으며, 공급자 `base-url`·`auth-token`은 같은 파드의 **프록시 컨테이너에만** 있고, **워크로드 파드에는 둘 다 없이** 헬퍼 파드 주소와 비밀 아닌 placeholder만 있다. `k3s-mcp-token`은 워크로드 파드에 주입되지 않으며(AC-F6 확정), 에이전트는 그 세션 MCP를 MCP 서버로 등록한다(`minimax-code`는 `~/.minimax/mcp.json`, AC-G6). (b) 모두 unknown field로 400 거부. (c) 승인 컨텍스트에 자격 증명·호출자 토큰이 실리지 않는다. (d) 어떤 경로에도 문자열이 노출되지 않는다. (e) 프록시 계약이 사이드카일 때와 **동일하게** 성립한다 — 계약은 AC-E6 하나이고 배치만 다름을 확인. (f) ingress 제한으로 차단된다. (g) 그 타입의 model 계약대로 성립한다(`minimax-code`는 AC-G1). (h) 워크로드 파드가 헬퍼 파드 밖의 K3s MCP·marketplace에 **직접** 닿으려 하지 않고, 에이전트의 파드 밖 도구 표면이 그 세션 MCP와 타입 PRD가 열거한 예외(`minimax-code`의 K3s MCP 도구 — 헬퍼 파드의 프록시 경유, AC-G6)뿐임을 확인한다. (i) PID·파일시스템 네임스페이스가 분리되어 **읽히지 않는다** — 같은 파드라도 컨테이너 경계가 Secret을 갈라 둔다
- **검증 AC**: AC-F6, AC-F2

> 비고: 승인 대기 중 수동 동결·삭제로 invocation이 취소되는 경로(AC-F3 마지막 항)는 시나리오 4·7의
> 조합으로 덮이지만, 수동 동결 전용 AC가 PRD에 아직 없어(`../doc-structure-state.md`의 열린 항목)
> 별도 시나리오로 세우지 않았다. 수동 트리거 AC가 생기면 그때 분리한다.
