# 테스트 문서: 세션 워크로드 — 승인 게이트 (approval-gated)

## 검증 대상 AC
- AC-F1: 워크로드 타입 `approval-gated` 선택 (PRD: 세션 워크로드 — 승인 게이트)
- AC-F2: Egress 격리 — 워크로드 파드는 세션 MCP를 통해서만 밖으로 나간다 (PRD: 세션 워크로드 — 승인 게이트)
- AC-F3: 승인 게이트 — 외부 도구는 사람이 승인해야 실행된다 (PRD: 세션 워크로드 — 승인 게이트)
- AC-F4: 보조 파드 = 세션 전용 MCP, 수명은 세션과 일치 (PRD: 세션 워크로드 — 승인 게이트)
- AC-F5: 파일 교환 = 세션 전용 RWX 공유 볼륨, 아카이브에 포함 (PRD: 세션 워크로드 — 승인 게이트)
- AC-F6: 자격 증명 분리 — 게이트웨이 키와 알림 대상은 MCP 파드에만 (PRD: 세션 워크로드 — 승인 게이트)

> 📌 **재사용 범위**: 이 타입의 원샷 실행·직렬 큐·1 MiB prompt·offset 커서·SSE 재연결·아카이브 왕복은
> `claude-code`와 같은 계약이므로 `claude-code-workload.md`의 시나리오 2·3·4·6·8이 그대로 적용된다.
> 아래 시나리오는 **이 타입에만 있는 차이**만 다룬다.

> ⚠️ **검증 수단 주의**: AC-F2(egress 차단)와 AC-F4(보조 파드 동반 회수)는 참조 구현(`dlddu/pure-agent`)이
> 클러스터에 배선된 적 없는 미검증 전제 위에 있다. 두 AC는 **코드 단언이 아니라 실클러스터 확인**으로
> 검증한다(kind overlay 또는 실 클러스터). `../doc-tracker.md`의 미검증 전제 항목 참고.

## 테스트 시나리오

### 시나리오 1: 타입 선택과 불변성
- **사전 조건**: 없음
- **실행 단계**: (a) `workloadType=approval-gated`로 세션 생성 → (b) `workloadType` 미지정·explicit `shell`·explicit `claude-code`로 각각 생성 → (c) 허용값 외 타입(`foo`)과 explicit `""`/`null`/비문자열로 생성 시도 → (d) (a)의 read/write/switch route에 workload/model 변경 필드를 보냄
- **기대 결과**: (a) 세션 조회 응답의 타입이 `approval-gated`이고, 워크로드 파드와 그 세션 전용 MCP 파드가 함께 기동됨. (b) 세 요청 모두 기존과 동일하게 동작(미지정·explicit `shell`은 PTY 쉘 1개, explicit `claude-code`는 기존 에이전트 파드). (c) 모두 pod 생성 전에 400 거부. (d) 모든 route가 400으로 거부하고 원래 타입·모델 유지
- **검증 AC**: AC-F1

### 시나리오 2: 워크로드 파드의 egress 차단 실측
- **사전 조건**: 실클러스터(또는 NetworkPolicy를 집행하는 CNI가 켜진 kind overlay)에 active 상태의 `approval-gated` 세션 2개(S1, S2)
- **실행 단계**: S1의 워크로드 파드 주 컨테이너에서 (a) kube-dns로 이름 조회 → (b) S1 자신의 MCP 파드 서비스 포트로 연결 → (c) 임의 외부 목적지(공개 IP·다른 네임스페이스의 서비스)로 연결 → (d) **S2의 MCP 파드 주소**로 직접 연결 → (e) 승인 게이트웨이 주소로 직접 연결 → (f) 세션 삭제 후 네트워크 정책 오브젝트 확인
- **기대 결과**: (a)·(b)는 성공. (c)·(d)·(e)는 타임아웃 또는 거부되어 연결이 성립하지 않음 — 에이전트가 승인 게이트를 우회해 밖으로 나갈 경로가 없고 다른 세션의 MCP도 빌려 쓸 수 없다. (f) 세션마다 올바른 셀렉터의 정책 오브젝트가 존재했고 삭제 시 함께 사라짐. **단, credential-proxy 사이드카가 쓰는 공급자 HTTPS origin은 현재 허용 목록에 있으므로 그 목적지는 차단되지 않는다** — 이는 AC-F2의 명시된 미해결 항목이며 실패로 기록하지 않는다
- **검증 AC**: AC-F2

### 시나리오 3: 승인(APPROVED) 경로 — write 즉시 반환, 대기 표시, 승인 후 실행
- **사전 조건**: active 상태의 `approval-gated` 세션 1개. 결정을 제어할 수 있는 승인 게이트웨이(실물 또는 테스트 대역)와 호출을 관찰할 수 있는 외부 테스트 upstream
- **실행 단계**: output SSE를 연 뒤 외부 도구를 부르게 하는 프롬프트를 write → write 반환 시각 기록 → 결정을 내리지 않은 채 SSE·read 관찰 → 게이트웨이에서 승인 → 이후 SSE·read·테스트 upstream 로그 확인
- **기대 결과**: write는 승인 대기를 기다리지 않고 **즉시 반환**한다. 결정 전 SSE와 같은 커서의 read에 `awaiting approval` in-band 마커가 나타나고, 그 사이 **테스트 upstream에는 어떤 요청도 도달하지 않는다**. 승인 후에야 실제 외부 호출이 한 번 일어나고 결과가 같은 바이트열에 이어 붙는다. 모든 event id/`nextOffset`과 decoded byte 길이가 일치하며 커서는 UTF-8 code-point 경계다(별도 event type 없음). 승인 요청의 외부 식별자는 `{세션ID}:{요청ID}` 형태다
- **검증 AC**: AC-F3

### 시나리오 4: 거절·만료·타임아웃 경로 — 도구 실패가 세션을 죽이지 않는다
- **사전 조건**: active 상태의 `approval-gated` 세션 1개. 결정을 REJECTED/EXPIRED로 만들거나 응답을 지연시켜 타임아웃을 유발할 수 있는 게이트웨이
- **실행 단계**: (a) 외부 도구 호출 프롬프트를 write → 게이트웨이에서 **거절** → (b) 같은 세션에 다시 write → 결정 없이 **만료** → (c) 다시 write → 폴링 타임아웃까지 방치 → 각 경우 read/SSE·세션 상태·테스트 upstream 확인 → (d) 세 번의 실패 뒤 정상 프롬프트를 write
- **기대 결과**: 세 경우 모두 **실제 외부 호출이 일어나지 않고** 도구가 실패 결과를 반환하며, 그 사실이 in-band 마커로 출력에 남는다. 세션 상태는 계속 `active`이고 실행 큐는 막히지 않으며, (d)의 후속 write가 정상 처리된다. 실패가 세션·pod를 종료시키지 않는다
- **검증 AC**: AC-F3

### 시나리오 5: 승인 대기가 유휴 카운트를 진행시키지 않는다
- **사전 조건**: active 상태의 `approval-gated` 세션 1개. 시간을 제어할 수 있는 테스트 하네스와 결정을 보류할 수 있는 게이트웨이
- **실행 단계**: 외부 도구 호출 프롬프트를 write → 결정을 보류한 채 유휴 한계를 넘길 만큼 시간을 진행 → `lastAccess`와 세션 상태를 관찰 → 게이트웨이에서 결정 → 다시 클라이언트 I/O 없이 시간을 진행하며 관찰
- **기대 결과**: 승인 대기 중에는 클라이언트 read/write가 없어도 `lastAccess`가 갱신되어 유휴 카운트가 진행되지 않고 세션이 동결되지 않는다. **결정이 난 뒤에는 갱신이 멈추고** 일반 유휴 카운트가 다시 진행되어 한계 도달 시 정상적으로 동결된다. 같은 조건에서 `shell`·`claude-code` 세션은 (승인 개념이 없으므로) 기존 AC-D5/AC-B1 그대로 동결됨을 대조 확인한다
- **검증 AC**: AC-F3 (AC-B1 구체화)

### 시나리오 6: 공유 볼륨 파일 왕복 — 동결·복원을 건너서도 남는다
- **사전 조건**: active 상태의 `approval-gated` 세션 1개. 승인 시 파일 결과물을 만드는 외부 도구 호출을 준비. 동결 직전 read로 커서 확보(`cursorBefore`)
- **실행 단계**: (a) 승인된 외부 호출로 공유 볼륨에 파일을 만들게 함 → 워크로드 파드와 MCP 파드 양쪽에서 같은 경로의 파일·내용 확인 → (b) **동결·복원을 건너뛰고** 곧바로 다음 프롬프트로 그 파일을 읽게 함 → (c) 세션 동결(유휴 한계 또는 스냅샷 직접 호출) → 재접근으로 복원 → 같은 파일 재확인 → (d) `cursorBefore`로 read, `offset=0`으로 read → (e) 다른 세션의 워크로드 파드에서 이 볼륨 접근 시도
- **기대 결과**: (a) 두 파드가 같은 파일을 같은 내용으로 본다(RWX 공유 마운트). (b) **동결을 거치지 않은 다음 실행도** 그 파일을 그대로 본다 — 파일 전달이 도구 응답 본문이 아니라 볼륨으로 이뤄진다. (c) 복원 후에도 파일이 남아 있고 내용이 일치한다(볼륨이 아카이브에 포함). (d) `cursorBefore` read는 델타만, `offset=0`은 동결 전·후 전체 이력을 반환한다. (e) 다른 세션은 이 볼륨을 마운트하지 못한다
- **검증 AC**: AC-F5 (AC-B3의 `approval-gated` 경로)

### 시나리오 7: 스냅샷·삭제 시 MCP 보조 파드 동반 회수
- **사전 조건**: 실클러스터에 active 상태의 `approval-gated` 세션 2개(S1, S2). 각 세션의 워크로드 파드와 MCP 파드를 라벨로 식별해 둠
- **실행 단계**: (a) 두 세션의 pod 목록을 라벨로 조회 → (b) S1을 스냅샷으로 동결 → pod 목록·가용 자원 확인 → (c) S1에 재접근하여 복원 → pod 목록 확인 → 외부 도구 호출로 새 MCP 연결 확인 → (d) S1을 삭제 → pod 목록 확인
- **기대 결과**: (a) 세션마다 워크로드 파드 1 + MCP 파드 1이 별개로 존재하고 두 세션이 어떤 파드도 공유하지 않는다. (b) S1의 **두 파드가 모두** 사라지고 클러스터 가용 자원이 회복되며 S2의 파드는 그대로다(AC-A3). MCP 파드는 스냅샷 대상이 아니므로 별도 아카이브가 생기지 않는다. (c) 복원 시 두 파드가 함께 새로 기동되고 에이전트가 새 MCP에 붙어 승인 경로가 다시 성립한다. (d) 삭제 후 S1의 두 파드와 네트워크 정책·공유 볼륨이 사라지고 S2는 영향을 받지 않는다
- **검증 AC**: AC-F4 (AC-A2/A3·B1/B2 구체화)

### 시나리오 8: 게이트웨이 자격 증명·알림 대상의 파드별 분리
- **사전 조건**: 플랫폼 Secret에 게이트웨이 URL·API key·`userId`와 AC-E6의 기존 키(`base-url`·`auth-token`·`k3s-mcp-token`·optional `model`/`models`)를 준비
- **실행 단계**: (a) `approval-gated` 세션의 pod 스펙에서 워크로드 파드 두 컨테이너와 MCP 파드의 환경 변수를 각각 확인 → (b) 생성 요청 본문에 게이트웨이 URL·API key·`userId`를 넣어 생성 시도 → (c) 승인 요청을 하나 만든 뒤 게이트웨이에 실제로 전달된 컨텍스트를 확인 → (d) 게이트웨이 키·`userId` 문자열로 read/SSE 출력·control-plane 로그를 검색 → (e) AC-E6의 provider credential·`k3s-mcp-token`·model 검증 항목을 이 타입에서 재실행
- **기대 결과**: (a) 게이트웨이 URL·API key·`userId`는 **MCP 파드에만** 있고 워크로드 파드의 주 컨테이너·credential-proxy 어디에도 없다. (b) unknown field로 400 거부. (c) 승인 컨텍스트에 자격 증명·API key가 실리지 않는다. (d) 어떤 경로에도 문자열이 노출되지 않는다. (e) AC-E6의 결과가 `claude-code`와 동일하게 성립한다 — 배선이 복제가 아니라 재사용임을 확인
- **검증 AC**: AC-F6

> 비고: 승인 대기 중 수동 동결·삭제로 invocation이 취소되는 경로(AC-F3 마지막 항)는 시나리오 4·7의
> 조합으로 덮이지만, 수동 동결 전용 AC가 PRD에 아직 없어(`../doc-structure-state.md`의 열린 항목)
> 별도 시나리오로 세우지 않았다. 수동 트리거 AC가 생기면 그때 분리한다.
