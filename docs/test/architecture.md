# 테스트 문서: 세션 아키텍처 & 격리

## 검증 대상 AC
- AC-A1: Control plane / data plane 분리 (PRD: 세션 아키텍처 & 격리)
- AC-A2: 세션당 전용 워크로드 Pod (PRD: 세션 아키텍처 & 격리)
- AC-A3: 세션 종료·동결 시 자원 회수 (PRD: 세션 아키텍처 & 격리)

## 테스트 시나리오

### 시나리오 1: 세션 생성 시 data plane pod 기동
- **사전 조건**: control plane 정상 기동, 클러스터에 가용 자원 존재
- **실행 단계**: control plane API로 세션 1개 생성 요청
- **기대 결과**: 전용 data plane 워크로드 파드 1개가 기동되고, control plane 프로세스 내에는 세션 워크로드가 없음
- **검증 AC**: AC-A1

### 시나리오 2: 세션-워크로드 파드 1:1 매핑 및 격리
- **사전 조건**: 클러스터 정상
- **실행 단계**: 세션 3개 생성 → pod 목록 확인 → 세션 2의 워크로드 파드를 강제 종료
- **기대 결과**: 고유 워크로드 파드 3개 존재(1:1), 세션 2 종료가 세션 1·3에 영향을 주지 않음
- **검증 AC**: AC-A2

### 시나리오 2-1: 보조 파드도 세션 전용
- **사전 조건**: 보조 파드를 갖는 타입(승인 게이트를 쓰는 타입 — `minimax-code`) 세션 2개 — 세션마다 워크로드 파드 1 + 헬퍼 보조 파드 1(세션 MCP·credential-proxy와 타입이 더한 컨테이너)
- **실행 단계**: 두 세션의 pod 목록을 라벨로 조회 → 각 세션의 헬퍼 보조 파드와 그 컨테이너 둘 식별 → 한 세션을 삭제
- **기대 결과**: 보조 파드가 세션마다 별개로 존재하고 두 세션이 같은 보조 파드를 공유하지 않음. 세션 삭제 시 그 세션의 파드 둘이 함께 사라지고 다른 세션의 파드는 남음. 1:1 매핑 진술은 워크로드 파드 기준으로 계속 성립
- **검증 AC**: AC-A2 (AC-F4 구체화)

### 시나리오 3: 동결 시 자원 회수
- **사전 조건**: active 세션 1개와 그 세션의 pod(워크로드 파드, 타입에 따라 보조 파드)가 존재
- **실행 단계**: 해당 세션을 스냅샷으로 동결(또는 종료)
- **기대 결과**: 대상 세션의 pod가 모두 제거되고 클러스터 가용 자원이 회복됨
- **검증 AC**: AC-A3

### 시나리오 4: 플랫폼은 모델 입력에 자기 문장을 넣지 않는다
- **사전 조건**: 에이전트 타입 세션(`claude-code`, `codex-chat`) 각 1개. `codex-chat`은 로그인을 마친 세션
- **실행 단계**: (a) 프롬프트 하나를 write한다 → (b) 세션 안에서 1분 뒤 실행되는 예약을 건다(`codex-chat`) → (c) 오래 도는 백그라운드 작업이나 하위 에이전트를 띄우는 프롬프트를 write한다 → (d) 모델이 받은 입력을 확인한다(Codex rollout, 러너가 SDK·app server에 넘긴 입력)
- **기대 결과**: 모델 입력의 사용자 메시지는 write한 프롬프트·등록한 예약 프롬프트 원문뿐이다. 시스템·개발자 메시지는 에이전트 CLI·SDK의 것뿐이고 플랫폼 문장(`session-platform`, 도구 사용 지시)이 없다. 백그라운드 작업·하위 에이전트가 남아도 플랫폼이 턴 안에 메시지를 끼워 넣거나 턴을 스스로 열지 않는다 — 그 결과는 세션 출력의 안내 줄로만 남는다. 권한 거부의 도구 결과는 일어난 일만 적는다
- **검증 AC**: AC-A5
