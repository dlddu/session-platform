# 4차 행 증분 재재판정 — `session_mcp_git.go` · `session_mcp_git_test.go` (2026-09-14)

`2026-09-13 (2)` 증분 재판정은 `git_clone` 슬라이스가 더한 96줄을 **제거 23 · 유지 73**으로 닫았다.
그 73줄을 하루 뒤 다시 열었다. 파일이 바뀌어서가 아니라 — 트리거 이후 이 범위의 주석은 한 줄도
움직이지 않았다 — **유지 근거 자체가 실측에서 무너져서**다.

그 슬라이스는 유지 73줄의 핵심을 「코드·문서 어디에도 없는 관측」 넷으로 열거했다. 넷을 하나씩
원본 후보에 대 봤더니 **둘이 거짓**이었고, 별도로 **원장이 근거로 언급조차 하지 않은 ② 사본**이
하나 더 있었다. 여기에 그 슬라이스가 스스로 「판단이 갈린 것」으로 남긴 자리 하나까지, 네 대목이
이 패스의 대상이다.

이 패스가 여는 것은 **이미 「판정 완료」로 등재된 자리**다. 게이트는 등재 범위가 *변했는지*만
재측정하고 판정의 *참*은 보지 않으므로, 원장이 이 증분을 등재한 순간 이 73줄은 판정 완료로 잠긴 채
영구 초록이 됐다. 파일이 다시 바뀌지 않는 한 어떤 감지도 이 자리를 다시 보지 않는다 — 그래서
재감지를 기다리지 않고 여기서 판정을 고친다.

## 판정 절차

앞선 패스들과 같다 — 각 주석에 「이 줄을 지우면 무엇이 복원 불가능해지는가」를 묻되, 이번에는
**복원 경로 넷을 하나씩 따로 묻는다**. `2026-09-13 (2)` 의 실패 형태가 정확히 그것이었다: 유지
근거가 ①(코드) 하나로만 물어져 있고 ②(문서)·③(PR)은 물어지지 않았다. 원본 후보는 전부 **같은 PR
(#140)이 함께 쓴 것**이라, 「같은 커밋 안에 원본이 실재하는가」가 판정의 형태다.

커밋 안에 실재함을 파일·심볼 단위로 보였으므로 그 조항이 걸리지 않는다.

## 유지 — 같은 밀도로 다시 확인한 것

일괄 제거로 기울지 않도록, **유지가 옳다고 재확인한 자리**를 같은 밀도로 적는다.

| 자리 | 왜 유지인가 |
| --- | --- |
| `cloneTimeout` · `maxCloneBranchChars` · `maxCloneErrorBytes` 의 **출처** | 문서가 그 자리를 **명시적으로 비워 뒀다** — 「경계값은 전부 코드가 갖는다 … 상한값도, 파일 하나의 상한도 여기에 옮기지 않는다: 그 숫자는 코드가 갖고, 여기 적으면 다음 변경에 조용히 거짓이 된다」. ② 복원 경로가 **원리적으로 없고**, 원본을 고치는 쪽(문서에 숫자를 적는 것)은 그 문단이 이미 기각했다 |
| `--` 가 둘째 가드라는 것 | 선행 대시 검사와 **다르게 실패하는** 가드이고, 그 비대칭은 문서·PR 어디에도 없다. 「검증 공백이 언젠가 생기면」이라는 조건절이 이 자리의 전부다 |
| 프롬프트를 끄는 이유 중 「타임아웃까지 막히는 대신 즉시 실패한다」 | 문서는 helper 를 비우는 **정책**만 적고, 프롬프트를 끈 결과가 *블록이 아니라 실패*라는 것은 적지 않는다 |
| `boundedBuffer` 의 메모리 근거 | 원격이 통제하는 텍스트가 이 컨테이너의 메모리가 되지 않게 한다는 것, 그리고 **잘린 양을 함께 보고한다**는 것. 코드 형태만으로는 후자가 의도인지 우연인지 보이지 않는다 |
| 하네스 카운터 doc (`clonedMCP`) | 「git 이 돌지 않았다」가 이 레포에서 승인 게이트의 의미라는 것 — 단언의 *이유*이고 단언 자체가 아니다 |
| `session_mcp_tools.go` 의 신규 2줄 | 이미 **포인터를 달고 압축한 형태**(「No `directory`: R11 and this entry's own ruling …」)라 사본으로 세지 않았다. 경계선에 두고 남긴다 |
