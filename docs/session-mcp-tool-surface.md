# 세션 MCP 도구 표면 — 승인 게이트 워크로드

> 상태: **도구 1개(`web_fetch_get`) 착지 · 다음 구현 대상 4개 등재** — *2026-09-08 신설*.
> `approval-gated` 세션에서 에이전트가 파드 밖에 닿는 유일한 경로는 그 세션 헬퍼 파드의 MCP이고,
> 그 표면은 전부 AC-F3의 승인 게이트를 지난다(AC-F6의 확정 항목). 이 문서는 **그 표면에 무엇을
> 실을지 판정하는 자리**다.

> 📌 **정본 관계**: 도구 표면이 *무엇을 보장해야 하는가*는 [`prd/approval-gated-workload.md`](./prd/approval-gated-workload.md)의
> AC-F3·F5·F6이, *지금 실제로 무엇을 내는가*는 `data-plane/cmd/agent/session_mcp_tools.go`의
> `toolDefinitions`가 갖는다. 이 문서는 그 둘 사이의 **판정 기준과 구현 대상 등재**만 갖고 사본을 두지 않는다 —
> 도구의 인자·응답 스키마를 여기에 다시 적으면 코드가 바뀔 때 조용히 거짓이 된다
> (`doc-tracker.md`가 사본 때문에 세 번 겪은 형태, 그 처방은 [`comment-policy/README.md`](./comment-policy/README.md)의 운영 규칙).

## 왜 이 문서가 있나

두 가지가 이 자리를 비워 두고 있었다.

1. **이 타입은 plugin 부트스트랩을 두지 않는다**(AC-F6의 2026-09-03 확정). 그래서 `claude-code`가
   marketplace plugin으로 얻는 플랫폼 도구 — 번들 `session-platform`의 스킬 넷과 K3s MCP 서버 —
   가 이 타입에는 **하나도 없다.** 그 확정은 대가를 명시했다: 「필요해지면 세션 MCP에 다시 실어야 한다」.
   무엇을 다시 실을지 판정할 문서는 만들지 않았다.
2. **도구를 하나 더하는 일은 함수 하나가 아니다.** 새 도구는 승인 컨텍스트(AC-F3)·자격 증명 배치(AC-F6)·
   결과물 크기(AC-F5)·헬퍼 파드의 egress 프로파일(AC-F2)을 동시에 건드린다. 그 검사 목록이 코드 주석
   한 줄(「도구를 더한다는 것은 게이트 핸들러를 하나 더 만든다는 뜻이지 우회로를 뚫는다는 뜻이 아니다」)
   외에는 없었다.

## 지금 있는 것 (1개)

| 도구 | 인자 | 게이트 | 결과 |
|------|------|--------|------|
| `web_fetch_get` | `url` (https 강제, 그 밖은 `additionalProperties: false`) | 호출마다 1건 | JSON 텍스트 — 성공 여부·상태 코드·`content-type`·본문 |

경계값은 전부 코드가 갖는다(`session_mcp_tools.go`·`approval_gateway.go`). 판정에 필요한 것만 옮기면:
승인 대기는 **분 단위**(사람의 왕복이므로 폴 간격은 초, 대기 상한은 분), 승인된 호출 자체는 그보다 짧게
끊기고, 인라인으로 돌려주는 본문은 **10만 바이트에서 잘린다.** 마지막 것은 설계가 아니라 **AC-F5의
공유 볼륨을 쓰는 축이 착지할 때까지의 임시 대체**다(`doc-tracker.md`의 열린 항목 ②).

두 가지 성질이 이 표면 전체에 걸린다.

- **이름과 모양을 창작하지 않는다.** `web_fetch_get`의 이름·인자·응답 모양은 참조 구현
  `dlddu/pure-agent`의 것을 그대로 가져왔고, mockup [`gated-workspace.html`](./mockups/gated-workspace.html)이
  그리는 값도 같다. 새 도구도 참조 구현에 대응물이 있으면 그것을 따른다.
- **게이트가 없으면 표면이 빈다.** 게이트웨이 env 3종이 빠지면 컨테이너는 뜨되 `tools/list`가 빈 배열을
  낸다. 빠진 Secret이 「게이트 없는 도구」로 바뀌는 경로는 없고, 앞으로도 두지 않는다.

## 도구 추가 규칙

새 도구를 등재·구현할 때 아래를 전부 통과해야 한다. R1·R2·R7·R9는 **위반 시 AC가 깨지므로 협상 대상이
아니다**; 나머지는 어긴다면 그 이유를 이 문서에 함께 적는다.

- **R1 게이트 예외 없음** — 파드 밖에 닿는 도구는 전부 승인을 지난다. 도구 추가 = 게이트 핸들러 추가이지
  우회로가 아니다(AC-F3).
- **R2 미설정은 빈 표면** — 게이트를 구성할 수 없으면 그 도구를 목록에 내지 않는다. 「게이트웨이가 없으니
  일단 그냥 호출」은 금지(AC-F3).
- **R3 검증은 요청 생성 앞에** — 인자 검증 실패는 승인 요청을 만들기 **전에** 끊는다. 잘못된 대상이 사람의
  알림으로 나가면 승인 화면 자체가 신뢰를 잃는다.
- **R4 사람이 읽고 판정할 수 있는 컨텍스트** — 승인 컨텍스트는 사람이 그것만 보고 허락/거절을 정할 수
  있어야 한다. `web_fetch_get`이 https만 받는 이유가 이것이다 — URL로 읽히는 승인이 승인자가 염두에
  두지 않은 스킴으로 충족되면 안 된다. 인자가 길고 구조적일수록(본문·헤더·스크립트) 이 규칙이 먼저 깨진다.
- **R5 외부 식별자 규약** — `{세션ID}:{요청ID}`, 요청ID는 난수. JSON-RPC id를 쓰지 않는다(에이전트
  프로세스마다 1부터 다시 세어 같은 세션의 두 invocation이 충돌한다).
- **R6 대기 마커는 대기 앞에** — 대기 시작을 notice 피드에 낸 **뒤** 대기에 들어간다. 마커의 쓸모는 막혀
  있는 동안에만 있다(AC-F3·AC-E3).
- **R7 실패는 도구 결과** — 거절·만료·타임아웃·게이트웨이 장애는 전부 `isError` 도구 결과다. JSON-RPC
  에러는 파싱 불가와 서버 자체 결함 전용이며, 어느 쪽도 세션이나 실행 큐를 죽이지 않는다(AC-F3).
- **R8 비밀은 컨텍스트에 싣지 않는다** — 게이트웨이 API key는 헤더로만 가고 본문에 넣지 않는다.
  `userId`·공급자 토큰도 승인 컨텍스트·read·SSE·로그 어디에도 나타나지 않는다(AC-F6).
- **R9 새 자격 증명은 도구 추가가 아니다** — MCP 컨테이너가 지금 받는 env는 워크로드·헬퍼 주소·세션ID와
  게이트웨이 3종뿐이다. 여기에 Secret을 하나 더 요구하는 도구는 **AC-F6의 자격 증명 배치 결정을 다시
  여는 일**이라, 이 문서의 등재만으로는 진행할 수 없다.
- **R10 사설 CA 원본은 지금 설 수 없다** — MCP 컨테이너의 fetch는 시스템 루트만 신뢰하고 CA를 넣을
  자리가 없다. 그 자리를 만들려던 시도는 **수요가 0이라 반려됐다**(2026-09-07, `doc-tracker.md`의 ③).
  사설 발급자 https 원본을 대상으로 삼는 도구는 그 판정을 먼저 뒤집어야 한다.
- **R11 큰 결과물은 파일로** — 인라인 본문 상한을 늘려 대응하지 않는다. 큰 결과물은 AC-F5의 공유 볼륨에
  쓰고 에이전트가 파일로 읽는다. 그 볼륨을 아직 아무도 쓰지 않는다는 사실은 아래 1번이 닫는다.
- **R12 헬퍼 파드의 egress는 열려 있다** — 네트워크 정책은 워크로드 egress와 헬퍼 ingress **둘뿐**이라,
  MCP 컨테이너가 나가는 목적지는 L3/L4에서 제한되지 않는다. 즉 **도구의 대상 범위를 좁히는 것은 코드의
  인자 검증뿐이다.** 새 도구가 어디로 나갈 수 있는지는 그 도구가 스스로 정한다.
## 다음에 구현할 도구 (4)

아래 넷이 다음 구현 대상이며, 번호가 그대로 우선순위다.

**넷 중 셋(2·3·4)이 R9에 걸린다** — MCP 컨테이너에 게이트웨이 3종 밖의 자격 증명을 요구하므로,
이 로드맵의 첫 관문은 도구 코드가 아니라 **AC-F6 자격 증명 배치의 개정**이다. 1번만 그 문 앞에서 설 수
있고, 그것이 1번이 먼저인 이유이기도 하다. 3·4는 승인 대상이 URL이 아니라 **명령줄**이 되는 첫 자리라
R4(사람이 읽고 판정할 수 있는 컨텍스트)가 함께 설계되어야 한다 — 그 화면은 이 레포 밖이다.

### 1. `git_clone`

- **무엇**: 원격 레포를 세션 작업 공간에 클론한다. 이름·인자 모양은 참조 구현 `pure-agent`의 `git_clone`을 따른다.
- **왜**: `claude-code`가 plugin 번들의 `git-repo-cloner` 스킬로 하던 일이고, 이 타입에는 그 스킬도
  `github.com`으로 나갈 egress도 없다. **코드를 다루는 세션이 가장 먼저 막히는 자리다.**
- **게이트**: 참조 구현의 `git_clone`은 **gatekeeper를 부르지 않는다** — 그 레포에서 게이트를 지나는 것은
  `web_fetch_get` 하나뿐이다. R1에 따라 **모양만 빌리고 게이트는 새로 씌운다.**
- **자격 증명**: 공개 레포 한정이면 R9에 걸리지 않는다 — 그래서 이것만 첫 관문 앞에서 설 수 있다.
  private 레포는 토큰이 필요하고, 그 토큰의 자연스러운 출처는 2번이 열어 줄 K3s MCP의 **단명 GitHub App
  토큰**이다. **private 클론은 2·3 뒤로 미루는 편이 자격 증명을 하나 덜 만든다.**
- **부수 소득**: 클론 결과물은 파일이라 **AC-F5 공유 볼륨의 첫 소비자**가 된다. 지금 그 볼륨은 마운트만
  돼 있고 아무도 쓰지 않으며, 그 사실이 원장의 열린 항목으로 등재돼 있다. 인라인 10만 바이트 절단(R11)을
  걷어내는 축도 여기서 시작된다.
- **승인 컨텍스트**: 「원격 URL + 대상 경로」면 R4를 지킨다. 경로를 에이전트가 정하게 하면 승인자가 볼
  것이 늘어나므로, **경로는 MCP가 정하고 결과로 알려주는** 쪽이 맞다.

### 2. K3s MCP 재노출

- **무엇**: plugin 번들이 붙여 주던 K3s MCP 서버의 도구를, 세션 MCP가 **도구별로 게이트를 씌워 위임하는
  얇은 프록시**로 다시 낸다. 그 서버로 가는 **통로를 여는 것이 아니다** — 통로를 열면 에이전트가 게이트
  없이 그 서버에 닿아 R1이 깨진다.
- **왜**: AC-F6의 2026-09-03 확정이 명시한 대가 그 자체다.
- **선행(R9)**: K3s MCP는 토큰을 요구한다. 그것을 MCP 컨테이너에 넣는 순간 「게이트웨이 3종만」이라는
  배치가 깨진다. 부트스트랩을 버린 그때의 근거(대안 ③ = 허용 목록 확장은 AC-F2를 느슨하게 한다)가
  **egress가 아니라 자격 증명 축으로 되돌아온 것**이다. 다만 그때 기각한 형태와 **같지는 않다** — 토큰이
  워크로드 파드가 아니라 헬퍼 파드에만 들어가고, 그 도구는 전부 게이트를 지난다.
  **그 차이를 AC-F6에 적는 것이 이 항목의 첫 작업이고, 도구 코드는 그다음이다.**
- **범위**: 한꺼번에 다 내지 않는다. 읽기(로그·파드 조회·검색)와 쓰기(재시작·스케일·문서 색인)는 승인
  컨텍스트의 성격이 다르다 — 쓰기는 「무엇을 어떻게 바꾸는가」가 사람에게 읽히는 형태여야 한다(R4).
- **사본 금지**: 어느 도구를 냈는지의 목록은 코드가 갖는다. 이 문서에 그 목록을 복사하지 않는다.

### 3. `gh` CLI

- **무엇**: MCP 컨테이너에서 `gh`를 실행하고 결과를 돌려주는 도구. **워크로드 파드에서 직접 실행할 수는
  없다** — 그쪽에는 egress가 없다.
- **왜**: 1번 다음에 오는 것들(PR 생성·이슈 조회·리뷰)이 전부 여기 있다. 클론만으로는 읽어 오기만 하고
  되돌려줄 수 없다.
- **자격 증명**: 2번이 열리면 **자기 Secret 없이 설 수 있다** — K3s MCP의 GitHub App 단명 토큰 발급을
  그대로 쓰면 된다. **2 → 3 순서의 실질적 근거가 이것이다**(둘의 순서를 바꾸면 여기에 Secret이 하나 는다).
- **R4 주의**: **이 목록에서 승인 표면이 처음으로 크게 넓어지는 자리다.** 사람이 승인하는 것이 URL이
  아니라 명령줄이 되고, `gh pr create`와 `gh api -X DELETE`가 도구 하나로 들어오면 승인 화면이 그 차이를
  드러내지 못한다. **하위 명령 허용 목록으로 좁혀 시작하고**, 승인 컨텍스트에는 「무엇을 어느 레포에」가
  구조화되어 실려야 한다.
- **R8**: `gh`의 출력에 토큰이 섞여 나가지 않게 하는 일이 남는다. credential-proxy가 이미 하는 redaction과
  같은 종류의 작업이다.

### 4. `kubectl`

- **무엇**: MCP 컨테이너에서 `kubectl`을 실행하는 도구.
- **왜**: 2번이 내는 K3s MCP 도구는 정해진 몇 가지 조회·조작이라 임의 리소스·`apply`·`exec`를 덮지
  못한다. **2번과 겹치는 부분이 있음을 알고 넣는다** — 겹치는 자리는 승인 컨텍스트가 좁은 K3s MCP 쪽이
  낫고, `kubectl`은 그 밖을 맡는다.
- **비대칭 하나**: **워크로드 파드는 `data-plane` ServiceAccount 토큰을 갖지만 API 서버로 나갈 길이 없고**
  (egress 허용은 kube-dns와 자기 헬퍼뿐), **헬퍼 파드는 길은 있지만 토큰이 없다**(헬퍼 파드는 SA 토큰을
  마운트하지 않는다 — AC-F4). 그래서 `kubectl`은 워크로드 쪽에 둘 수 없고 반드시 이 표면으로 온다.
- **선행(R9 + AC-F4 개정)**: 토큰을 마운트하도록 헬퍼 파드 스펙을 바꾸거나 kubeconfig를 Secret으로
  넣어야 하고, 어느 쪽이든 **AC-F4의 파드 스펙 서술과 AC-F6의 자격 증명 배치를 함께 고친다.**
- **권한 범위가 진짜 위험이다**: `data-plane` SA는 클러스터 `view`와 노드 읽기이고 Secret 읽기는 거부된다.
  그 SA를 그대로 쓰면 `apply`·`exec`가 되지 않고, 되게 하려면 권한을 넓혀야 한다 — **이 도구의 실제
  blast radius는 명령어가 아니라 그때 넓히는 RBAC이다.** 넓힌 권한은 게이트가 거절해도 남는다.
- **R4**: 3번과 같은 문제이고 더 크다. `kubectl get`과 `kubectl delete`는 승인 화면에서 반드시 달라
  보여야 한다.

## 이 표면에 두지 않는 것

- **워크로드 파드 안에서 되는 일** — 에이전트는 이미 관리 설정의 도구 허용 목록(`Read`·`Write`·`Edit`·
  `Glob`·`Grep`·`Bash`)을 갖는다. 같은 일을 MCP로 한 번 더 내면 표면이 두 갈래가 되고, 게이트를 지나지
  않는 도구가 세션 MCP 목록에 섞인다. **판정 기준은 도구의 생김새가 아니라 실행 위치다** — 위 3·4가
  명령 실행인데도 이 표면에 오는 이유는 그것이 `Bash`의 중복이어서가 아니라, **egress가 있는 쪽이
  MCP 컨테이너뿐**이기 때문이다. 워크로드 파드에서 성립하는 명령은 여기로 올리지 않는다.
- **게이트를 지나지 않는 도구** — 순수 로컬 계산이면 `Bash`로 되고, 외부에 닿으면 R1이 적용된다.
  「가벼우니까 게이트 없이」에 해당하는 자리가 이 표면에는 없다.
- **승인 상태 조회 도구** — 대기와 결정은 이미 notice 피드로 나가고 출력 바이트열에 in-band 마커로
  남으며, 유휴 예외는 워크로드가 control plane에 내는 별도 경로가 갖는다. 도구로 다시 낼 이유가 없다.
