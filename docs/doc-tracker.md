### 🟡 확인 필요한 설계 결정 (스킬 표준 위험은 아니나 명세 공백)
- **🆕 워크로드↔프록시 홉의 평문 노출 (AC-F2 ↔ AC-F6)**: 공급자 프록시를 보조 파드로 옮기면서(아래 해결된 결정) 주 컨테이너와 프록시 사이가 loopback이 아니라 **클러스터 네트워크 홉**이 되었다. 이 홉에 공급자 토큰은 흐르지 않지만(하류는 placeholder, 토큰 교체는 프록시가 상류에서 한다) 프롬프트·응답 본문이 평문으로 지나가므로, AC-E6이 평문 HTTP upstream을 거부한 것과 같은 종류의 노출이다. 선택지는 ① 네임스페이스 네트워크를 신뢰 경계로 수용, ② 홉을 TLS/mTLS로 감싸기, ③ CNI 수준 암호화에 위임. **현재 AC-F2·F6은 ①을 전제로 기술되어 있다.**
- **🆕 헬퍼 컨테이너의 egress 프로파일 통합 (AC-F4 ↔ AC-F2)**: MCP와 credential-proxy를 한 헬퍼 파드에 담으면서 둘의 egress 정책이 파드 단위로 **합쳐진다** — 프록시 컨테이너도 L3/L4에서는 MCP가 승인 뒤 나가는 목적지에 닿고, 그 반대도 마찬가지다. 원래의 사이드카 문제와 성격이 다르다: 그때 프록시와 한 파드였던 것은 모델이 조종하는 `Bash` 실행 컨테이너였지만, 지금 합쳐진 둘은 **모두 플랫폼 코드**다. 따라서 "에이전트는 게이트를 통해서만 밖에 나간다"는 성질은 온전하고 잃는 것은 신뢰된 둘 **사이의** 심층 방어뿐이다. 다시 갈라 각자의 좁은 정책을 주는 선택지는 열려 있으며, 대가는 세션당 파드가 셋이 되는 것이다.
- **🆕 세션당 파드 수 증가 (AC-F4)**: `approval-gated`는 세션마다 파드가 둘(워크로드 + 헬퍼)이다. 동결된 세션은 둘 다 회수되므로 유휴 점유는 0이지만, **활성 세션당 스케줄링 단위와 기동 지연이 늘어난다.** 이는 AC-F2의 egress 경계를 파드 단위 정책으로 강제하기 위한 비용이며, 용량 계획이 붙을 때 재검토 대상이다.
- **🆕 미검증 참조 구현 전제 (AC-F2·F4·F5)**: egress 허용 목록·보조 파드 수명·RWX 공유 볼륨은 `dlddu/pure-agent`의 구조에서 가져왔고, 그 참조 구현은 **CI는 그린이지만 클러스터에 배선되어 검증된 적이 없다.** 따라서 T-승인게이트의 시나리오 2·7은 코드 단언이 아니라 **실클러스터 확인**으로 적혀 있다. 실검증 전까지 AC-F2·F4는 "설계 의도"이지 "확인된 동작"이 아니다. *2026-09-03 갱신*: AC-F2의 정책 오브젝트는 코드로 착지했지만 이 항목은 그대로다 — 오브젝트가 존재한다는 것과 클러스터가 그것을 집행한다는 것은 다른 사실이다.
- **🆕 구현 사슬 부채 — `approval-gated`의 도구 표면과 프로덕션 활성화 (AC-F3·F5)**: *2026-09-04 갱신 — 승인 게이트가 착지했다.* 세션 MCP는 이제 외부 도구 `web_fetch_get` 하나를 내고, `tools/call`이 승인 게이트웨이에 요청을 만들어 사람의 결정을 기다린 뒤 **APPROVED일 때만** 실제 외부 GET을 한다. wire 규약과 도구 모양은 PRD가 지목한 참조 구현(`dlddu/pure-agent`)의 것을 그대로 쓴다 — POST `/api/requests`(+`x-api-key`) → GET `/api/requests/{id}`, 외부 식별자 `{세션ID}:{요청ID}`. 거절·만료·타임아웃·게이트웨이 장애는 전부 **`isError` 도구 결과**로 돌아가 세션과 실행 큐를 죽이지 않는다(AC-F3). 게이트웨이 3종 env가 없으면 컨테이너는 뜨되 **도구 목록이 빈다** — 빠진 Secret이 게이트 없는 도구로 바뀌는 경로는 없다. control plane은 그 외부 식별자를 위해 MCP 컨테이너에 `SESSION_ID`를 평문으로 넘긴다(자격 증명이 아니라 파드가 이미 라벨로 다는 값). *앞선 부채(파드 쌍이 서지 않던 것)는 2026-09-03에 해소됐다* — data plane이 `approval-gated`·`mcp` 두 워크로드를 알고, credential-proxy가 배치별로 바인딩을 갈라(사이드카=loopback 강제 유지 · 헬퍼=파드 IP) 헬퍼 파드의 두 컨테이너가 모두 기동한다. AC-F2의 NetworkPolicy 2종(워크로드 egress 허용목록 · 헬퍼 ingress 제한)도 세션 셀렉터로 착지했고, 그 라운드 헬퍼 파드의 `ownerReferences`에 묶여 파드와 함께 회수된다. **남은 것 셋**: ~~① 대기 표시·유휴 예외~~ *2026-09-04 해소 — 유휴 예외까지 착지해 AC-F3의 이 레포 몫이 닫혔다.* 선행이던 **신호 경로 설계가 확정됐다: 워크로드가 헬퍼를 당긴다(pull).** 헬퍼 파드의 MCP가 대기 시작과 결정을 seq 붙은 메모리 피드(`GET /notices?after=<seq>`, long-poll)에 내고, 워크로드 파드의 에이전트가 그것을 tail해 AC-E3의 같은 append-only 바이트열에 `[session-platform: awaiting approval — <도구> · <외부 식별자>]`와 결정 한 줄을 in-band 마커로 붙인다. 반대 방향(헬퍼 → 워크로드 push)을 택하지 않은 이유는 AC-F2다 — **워크로드 → 헬퍼:8092는 egress 허용목록에 이미 있는 두 목적지 중 하나**라 정책·매니페스트를 하나도 건드리지 않는 반면, push는 양쪽에 새 규칙을 요구한다. 피드가 메모리뿐인 것도 의도다(AC-F4의 「헬퍼는 자체 상태를 보존하지 않는다」) — 동결 시 피드는 버려지고 이미 찍힌 마커는 워크로드 scrollback을 타고 아카이브된다. 새 SSE event type이나 필드를 만들지 않았으므로 커서 규약은 타입 간 그대로다. **유휴 예외도 같은 pull 방향으로 착지했다** — tailer가 피드에서 읽은 대기를 externalID 집합으로 들고, 워크로드 에이전트가 `GET /approval`로 그것을 내고, control plane의 유휴 경로(`SnapshotIfIdle`)가 `approval-gated` 세션에 한해 그 답을 물어 대기 중이면 `lastAccess`를 갱신하고 동결을 건너뛴다. **방향을 다시 pull로 고른 근거는 AC-F2의 정책 실물이다** — 워크로드 egress 허용목록은 kube-dns와 자기 헬퍼뿐이라 워크로드는 control plane에 닿지 못하고, 헬퍼 ingress는 워크로드만 받아 control plane은 헬퍼에 닿지 못하며, **control plane → 워크로드만 ingress 정책이 없어 열려 있다**(read/write가 이미 쓰는 길). 그래서 여기서도 NetworkPolicy·`k8s/` 매니페스트는 바뀌지 않는다. blast radius(유휴 리퍼는 **모든 타입**의 동결에 걸린다)는 세 겹으로 좁혔다: 리퍼 경로(`idleCutoff != nil`)에서만 · `approval-gated`에서만 · 조회 실패는 「대기 아님」으로 떨어져 기존 AC-B1로 되돌아간다. 그 결과 **수동 동결은 대기 중에도 그대로 얼고**(AC-F3의 「동결·삭제와의 충돌」), `shell`·`claude-code`는 질문조차 받지 않는다. ② **AC-F5 RWX 공유 볼륨 미착지** — 그때까지 승인된 호출의 결과 본문은 100 000바이트에서 잘라 도구 응답으로 돌려준다. ③ **kind e2e SUT는 게이트웨이 Secret 부재로 여전히 막혀 있다 — 프로덕션 활성화는 2026-09-05 해소** — **프로덕션 활성화는 #81이 끝냈다**: base `k8s/deployment.yaml:75`가 `DATA_PLANE_APPROVAL_GATED_IMAGE`를 ghcr 핀 이미지로 선언하고(선언된 이미지 env는 이제 - **🆕 승인자와 작업자의 분리 (AC-F6)**: 승인 알림 대상 `userId`가 플랫폼 전역 단일 값이라, 일을 맡기는 사람과 승인하는 사람이 현재 같은 사람으로 전제되어 있다. 다중 사용자·역할 분리가 필요해지면 AC-F6과 여정 `JRN-approval-gated-work`가 함께 개정된다.
- **스냅샷 트리거 정책 (AC-B1)**: 60분 최대 유휴 한계에 대한 **운영 트리거는 구현됨** (`service.IdleReaper`가 유휴 ≥ `MaxIdle` 세션을 주기 스캔해 스냅샷 + pod 회수). 다만 grace period·per-session override 등 정확한 트리거 타이밍 정책은 여전히 미확정 (`session.go`의 `TODO(policy)`).
- **바쁜 쉘 동결 여부 (AC-D5 ↔ AC-B1)**: 장시간 포그라운드 작업 실행 중 클라이언트 유휴 60분 도달 시 동결 대상이 되는지 — CRIU상 기술적으로는 가능하나, 트리거 정책과 함께 결정 필요. (AC-D5로 유휴 "정의"는 확정, "정책"은 미확정)
- **read 출력 버퍼 증가 (AC-D3, shell)**: 페이지네이션은 2026-07-03 `offset` 커서 개정으로 해소(반복 read의 `payload`는 델타만큼). shell scrollback은 agent 메모리에 있지만 agent 자체는 CRIU dump 대상이 아니므로 `/checkpoint`가 **CRIU images와 같은 archive에 별도 직렬화**하고 `/restore`가 preload한다. 이 때문에 복원 전 offset cursor가 그대로 유효하다. shell 누적 버퍼 자체의 상한/ring buffer는 계속 보류한다. `claude-code`는 별도 계약으로 invocation 16 MiB·누적 256 MiB 상한과 terminal marker를 구현했다(AC-E2/E3). Live SSE도 같은 append-only byte cursor를 사용해 반복 전송을 줄이지만 저장 상한 자체를 바꾸지는 않는다.
- **제품명·소유자**: "Session Pod Platform"은 임시 작업명. 실제 제품명/소유자 확정 필요.
- **🆕 claude-code의 `idle` 상태 의미 (AC-E5 ↔ AC-C2/C3)**: 상주 프로세스가 없는 타입에서 `active`와 `idle`(pod 보유·미사용)의 실질 차이는 자원 점유뿐이다. 상태 모델은 타입 공통으로 유지했으나, `idle` 구간에 대한 별도 정책(예: 더 짧은 유휴 한계)이 필요한지는 미결.

- **`approval-gated`의 plugin 부트스트랩 (AC-F6 ↔ AC-F2/AC-E6)** — *2026-09-03 확정*. Secret은 컨테이너 단위 주입과 PID·파일시스템 네임스페이스 분리로 계속 갈린다(AC-E6이 이미 기대는 성질). 프록시의 **동작 계약 정본은 계속 AC-E6**이고 배치와 바인딩(loopback → 파드 IP + ingress 제한)만 타입별로 다르다. 대가는 위 🟡 항목(평문 홉·헬퍼 egress 통합·파드 수)으로 등재했다.

- ~~**AC-C1 Lease/metadata 안전 부채**~~ → **2026-08-08 해소**: Snapshot·Restore·recovery가 기본 15초 Lease를 5초 heartbeat + per-Renew deadline으로 갱신하고, holder loss는 operation context를 취소한다. `Touch`는 latest-only monotonic partial update, lifecycle은 state + private snapshot transaction을 한 번에 owner-fenced aggregate CAS하며 더 최신 `lastAccess`를 merge한다. Claude snapshot은 CP-owned generation의 durable `preparing→committing` transaction으로 crash recovery한다.
- **reaper access freshness 안전 부채**: `SnapshotIfIdle`은 Lease를 잡고 authoritative `lastAccess`를 재조회해 List 이후 이미 완료된 접근은 걸러낸다. 그러나 read/write는 그 Lease를 공유하지 않고 agent I/O 뒤 `Touch`가 best-effort라, 재조회와 checkpoint 사이에 완료되는 접근은 여전히 예상보다 일찍 동결될 수 있다. read/write fencing 또는 실패를 표면화하는 정책이 필요하다.
- ~~**세션 레코드의 pod 참조가 단수 (AC-A2 개정 ↔ AC-F4)**~~ → **2026-09-03 해소 (참조 모델 한정)**: 세션이 이제 워크로드 파드 하나(`Session.Pod`, 개정 AC-A2의 1:1 주어)와 세션 전속 보조 파드 집합(`Session.AuxiliaryPods`)을 함께 들고, `Session.Pods()`가 그 집합을 돌려준다. 포트가 집합을 다룬다 — `PodOrchestrator.Start`/`RestoreInto`는 `SessionPods{Workload, Auxiliary}`를 반환하고 `Stop`은 가변 refs를 받는다. 라이프사이클 다섯 경로(생성·생성 롤백·동결(shell CRIU + claude archive + 복구 커밋)·복원·삭제)가 전부 `sess.Pods()` 집합을 회수·재기동하며, 동결·삭제는 보조 파드까지 회수하고 복원은 새 집합을 기록한다. `Reach`는 워크로드 파드에만 건다(보조 파드는 세션 에이전트가 아니다). 공개 계약은 additive — `Session.auxiliaryPods`가 OpenAPI·SPA 타입에 더해졌고 `pod`의 타입·의미는 그대로라 e2e의 wire 단정(#23 재편 후 `control-plane/test/e2e_a2_dedicated_pod_test.go`)도 불변이다. **남은 것**: 이 항목이 열어 준 자리를 채우는 AC-F1~F6 본체 — `approval-gated` 열거값, 헬퍼 파드 스펙(MCP·credential-proxy 컨테이너), egress/ingress NetworkPolicy, 승인 게이트, RWX 공유 볼륨, 자격 증명 분리. 라벨 기반 조회는 그 스펙이 헬퍼 파드를 실제로 만들 때 함께 정한다. **보조 파드를 만드는 워크로드 타입이 아직 없으므로**, 집합 계약은 스텁의 `SetAuxiliaryPods` 노브로 단정된다(생성 시 동반 기동 · 동결/삭제 시 전량 회수 · 복원 시 재기동 · 실패 롤백 시 누수 없음).
- **restore hard-crash 안전 부채 (모든 workload)**: `RestoreInto`가 새 pod를 만든 뒤 final aggregate CAS 전에 control plane이 hard crash하면 target pod를 orphan할 수 있다. 일반 오류·Renew loss는 best-effort Stop으로 정리하지만 process crash에는 durable RestoreTransaction, deterministic target 또는 reconciler가 필요하다.
- **snapshot 실패 안전 부채 (shell)**: CRIU dump가 shell을 종료한 뒤 durable upload·pod Stop·final metadata 저장이 실패하면 record와 pod 상태가 어긋날 수 있다. Claude archive는 owner-fenced prepare/commit recovery를 갖지만 shell은 leave-running 또는 명시적 transition/reconcile 프로토콜이 필요하다.
- **delete retention/crash-window 안전 부채**: 공개 DELETE는 lifecycle Lease heartbeat 아래 live/current/source pod를 회수하고 레코드를 제거한다. 다만 pod Stop과 metadata Delete 사이 hard crash에는 durable `deleting` marker/reconciler가 없고, 이미 업로드된 checkpoint/archive object는 checkpoint-store retention 정책에 남는다.
