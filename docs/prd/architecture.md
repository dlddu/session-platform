# PRD: 세션 아키텍처 & 격리

> 대상 요구사항: ① control plane API server + data plane pod, ⑤ 세션별 별도 pod

## 달성 가치
- **V1 세션 격리** — 세션별 전용 워크로드 pod 모델로 격리를 구조적으로 보장
- **V2 유휴 자원 회수** — control plane이 pod 생명주기를 단일 관리하여 회수 가능
- **V5 일관된 세션 상태** — control plane이 세션 메타데이터의 단일 진입점 역할

## Acceptance Criteria

### AC-A1: Control plane / data plane 분리
- **설명**: 시스템은 control plane API server와 data plane pod로 분리된다. Control plane은 세션 생성·조회·전환·스냅샷·복원 요청을 수신·오케스트레이션하고, 실제 세션 워크로드는 data plane pod에서만 수행된다. Control plane은 세션 자체 연산을 직접 수행하지 않는다.
- **달성 가치**: V1, V5
- **구체화**: "실제 세션 워크로드"는 **워크로드 타입별로 분기**한다 → 타입 선택은 AC-E1, `shell` 타입은 AC-D1 (`shell-workload.md`), `claude-code` 타입은 AC-E2~E6 (`claude-code-workload.md`), `minimax-code` 타입은 AC-G1~G6 (`minimax-code-workload.md`), 그리고 타입이 갖추는 능력인 승인 게이트는 AC-F2~F6 (`approval-gate.md`)
- **검증 방법**: control plane에 세션 생성 요청 시 별도 data plane pod가 기동되며, control plane 프로세스 내부에서는 세션 워크로드가 실행되지 않음을 확인한다.

### AC-A2: 세션당 전용 워크로드 Pod
- **설명**: 각 세션은 **세션 워크로드를 실행하는 data plane pod**(이하 *워크로드 파드*) 정확히 하나에 매핑된다(1:1). 서로 다른 세션은 동일한 워크로드 파드를 공유하지 않는다. 워크로드 타입(AC-E1)이 달라도 이 매핑은 동일하다 — 타입은 워크로드 파드 안에서 무엇이 도는지만 바꾼다.
- **보조 파드**: 워크로드 타입에 따라 세션은 워크로드 파드 **외에 보조 파드를 가질 수 있다.** 보조 파드는 세션 워크로드를 실행하지 않고 그 워크로드가 쓰는 부수 기능만 제공하며, **수명이 세션에 묶이고 세션 간 공유되지 않는다.** 위 1:1 매핑은 워크로드 파드에 대한 진술이므로 보조 파드의 존재가 이를 깨지 않는다 — 격리(V1)의 관점에서 보조 파드도 세션 전용이기 때문이다. 보조 파드를 갖는 것은 승인 게이트를 쓰는 타입(지금은 `minimax-code`)이며 **세션마다 하나**(세션 MCP·credential-proxy 컨테이너와 타입이 더한 컨테이너를 담은 헬퍼 파드)를 갖는다. 그 수명·회수 규칙은 AC-F4(`approval-gate.md`)가 정의한다. `shell`·`claude-code`는 보조 파드가 없다 — `claude-code`의 credential-proxy는 같은 파드 안의 사이드카 컨테이너이므로 보조 파드가 아니다(AC-E6). 같은 프록시를 게이트 타입이 보조 파드 쪽으로 옮기는 이유는 파드 단위 네트워크 정책으로 egress 경계를 세우기 위해서다 — 경계에 필요한 것은 프록시가 **워크로드 파드 밖에** 있다는 사실뿐이라, 그 프록시는 별도 파드가 아니라 MCP와 같은 헬퍼 파드의 컨테이너로 산다(AC-F2·F4).
- **달성 가치**: V1
- **검증 방법**: N개의 세션을 생성하면 N개의 고유 워크로드 파드가 존재하고 세션↔워크로드 파드 매핑이 1:1임을 확인한다. 한 세션 워크로드 파드의 강제 종료가 다른 세션에 영향을 주지 않음을 확인한다. 보조 파드를 갖는 타입에서는 보조 파드 역시 세션 전용으로 기동되어 다른 세션과 공유되지 않고, 세션이 회수될 때 함께 회수됨을 확인한다(AC-F4).

### AC-A3: 세션 종료·동결 시 자원 회수
- **설명**: 세션이 종료되거나 스냅샷으로 동결되면 해당 세션의 data plane pod(워크로드 파드와, 있다면 보조 파드)와 점유 자원(CPU/메모리)이 회수된다.
- **달성 가치**: V2
- **검증 방법**: 세션 동결/종료 후 대상 pod가 모두 제거되고 클러스터 가용 자원이 회복됨을 확인한다.

### AC-A4: 세션 생성은 호출자의 연결보다 오래 산다
- **설명**: 세션 생성(`POST /api/v1/sessions`)의 프로비저닝 라운드는 호출자의 HTTP 연결과 분리되어 진행된다. 워크로드 파드가 노드 증설을 기다리면 Ready까지 수 분이 걸릴 수 있고, 그 사이 호출자 쪽의 프록시가 조용한 요청을 끊을 수 있다. 호출자가 떠나도 라운드는 취소되지 않고 오케스트레이터의 파드 대기 상한(2분)까지 이어지며, 성공하면 세션은 평소처럼 `active`로 저장되어 목록 조회로 찾을 수 있다. 라운드를 끝내는 것은 오케스트레이터의 상한과 그 뒤의 백스톱(10분)뿐이며, 실패한 라운드는 지금처럼 만든 파드를 회수한다(AC-A3). 이전에는 호출자의 끊김이 파드 대기를 취소해 반쯤 만든 파드를 지웠고, 재시도마다 노드 증설만 일으키고 아무것도 남기지 않았다.
- **달성 가치**: V5
- **검증 방법**: 이미 취소된 요청 컨텍스트로 생성을 호출해도 세션이 만들어져 목록에 나타남을 확인한다.
- **자동화**: Go 단위 `control-plane/internal/service/create_detached_test.go`(`TestCreateOutlivesTheCallersContext`)
