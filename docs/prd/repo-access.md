# PRD: 비공개 레포 접근 — 허용 목록과 접근 요청 (repo-access)

> 대상 요구사항: 세션 MCP의 `git_clone`이 **사람이 레포 단위로 허락한 비공개 GitHub 레포**를 받을 수 있게 하고,
> 그 허락(허용 목록)을 control plane이 보관·관리하며, 세션이 허락을 **요청**할 수 있게 한다.
> 적용 대상은 세션 MCP가 있는 두 타입 `approval-gated`(AC-F)·`minimax-code`(AC-G)다.

## 달성 가치
- **V8 목적에 맞는 작업 환경 선택** — 게이트가 걸린 에이전트 세션이 공개 레포에 묶이지 않고, 작업자가 고른 비공개 레포 위에서도 일할 수 있게 함 (AC-H5)
- **V1 세션 격리** — 비공개 레포 자격 증명은 레포 하나·읽기 전용·클론 한 번으로 좁혀 워크로드 파드 밖에서만 쓰고, 허락되지 않은 레포에는 어떤 경로로도 닿지 않게 함 (AC-H3·H5 — AC-A1·F6 구체화)
- **V1 세션 격리 (관리 경계)** — 무엇을 열지는 로그인한 사람만 정하고, 세션은 요청만 남길 수 있음 (AC-H2·H4)

> 📌 **가치 연결 규칙**: 다른 PRD와 같이 각 AC의 달성 가치는 자신이 구체화하는 상위 AC의 가치를 상속한다.
> 새 가치는 신설하지 않는다.

> 이 PRD가 못박는 성질은 하나다 — **레포를 여는 결정(허용 목록)과 호출 하나를 여는 결정(AC-F3 승인)은 다른
> 결정이고, 비공개 클론은 둘 다를 통과해야만 일어난다.** 허용 목록은 레포 단위로 오래 남는 허락이고, 호출 승인은
> 그 순간의 한 번이다. 어느 한쪽만으로는 비공개 레포가 열리지 않는다.

## Acceptance Criteria

### AC-H1: 허용 목록 저장 — control plane의 SQLite, 단일 replica opt-in
- **설명**: 허용 목록과 대기 중인 접근 요청은 control plane이 SQLite 파일 하나에 보관한다. 항목은 GitHub 레포 하나(`owner/repo`, 대소문자 무시 비교)이고 누가·언제·어떤 경로(직접 추가 / 요청 허락)로 추가했는지를 함께 남긴다. 저장소는 **opt-in**이다 — 파일 경로 설정(`REPO_ACCESS_DB_PATH`)이 있을 때만 켜지고, 없으면 이 PRD의 API는 전부 `503`을 돌려주며 세션 MCP는 비공개 클론과 접근 요청을 하지 않는다(공개 클론은 그대로). SQLite는 control plane 파드 안의 파일이라 **replica 사이에 공유되지 않으므로**, 이 기능을 켠 배포는 control plane을 replica 1개·`Recreate` 전략으로 운영한다. 이것은 AC-C1의 "상태는 다중 replica가 공유한다"에 대한 **이 기능 한정 예외**이며, 세션 상태(AC-C1)는 영향을 받지 않는다. 파일은 영속 볼륨에 두어 control plane 재시작·재배포를 건너 보존된다.
- **달성 가치**: V1 (AC-H2·H5의 기반)
- **검증 방법**: 허용 목록에 항목을 추가하고 control plane을 재시작한 뒤에도 항목이 남아 있음을 확인한다. 경로 설정 없이 기동하면 관리·내부 API가 `503`이고 세션 MCP가 비공개 클론을 시도하지 않음을 확인한다. 같은 레포를 대소문자만 바꿔 두 번 추가하면 한 항목으로 수렴함을 확인한다.

### AC-H2: 관리 API와 화면 — Authelia OIDC 로그인 뒤에서만
- **설명**: control plane은 허용 목록 조회·추가·삭제와 대기 요청 조회·허락·거절을 하는 관리 API와, 그것을 쓰는 SPA 화면(레포 접근 화면)을 낸다. 관리 API는 **Authelia OIDC로 로그인한 사용자**만 호출할 수 있다 — control plane이 OIDC 인가 코드 흐름(PKCE)을 직접 처리하고, 로그인 결과는 서명된 세션 쿠키로 유지한다. 로그인한 사용자는 모두 관리 권한을 가진다(별도 그룹 제한 없음). 로그인하지 않은 호출은 `401`이고, 화면은 목록 대신 로그인 안내를 보인다. **기존 세션 API(AC-C*)와 다른 화면은 인증 범위 밖**으로 지금과 같이 동작한다. 요청을 허락하면 그 레포가 허용 목록에 오르고 요청은 대기 목록에서 빠지며, 거절하면 요청만 빠진다. 이미 허용된 레포에 대한 요청은 허락해도 항목이 늘지 않는다.
- **달성 가치**: V1
- **검증 방법**: 로그인 없이 관리 API를 부르면 `401`, 로그인 후에는 같은 호출이 성공함을 확인한다. 기존 세션 API가 로그인 없이 그대로 동작함을 확인한다. 요청 허락 → 허용 목록 반영·대기 목록 제거, 거절 → 대기 목록 제거·허용 목록 불변을 확인한다.

### AC-H3: 헬퍼 파드 → control plane 내부 API — 서비스 어카운트 토큰으로 신원 확인
- **설명**: 세션 MCP(헬퍼 파드의 `session-mcp` 컨테이너)는 control plane의 내부 API로 (a) 레포가 허용 목록에 있는지 묻고 (b) 접근 요청을 남긴다. 이 호출은 그 컨테이너에만 마운트되는 **control plane 전용 audience의 projected 서비스 어카운트 토큰**으로 인증하고, control plane은 TokenReview로 그 토큰이 `session-mcp` 서비스 어카운트의 것이고 어느 세션의 헬퍼 파드에 바인딩됐는지 확인한다. 워크로드 파드는 이 API에 닿지 않는다(AC-F2 egress 경계 그대로). 내부 API는 허용 목록을 바꾸지 못한다 — 요청을 **대기** 상태로 남기는 것까지만 할 수 있다.
- **달성 가치**: V1 (AC-F2·F6 구체화)
- **검증 방법**: 유효한 헬퍼 토큰으로는 조회·요청이 성공하고, 다른 audience 토큰·다른 서비스 어카운트 토큰·토큰 없음은 `401`임을 확인한다. 내부 API로 허용 목록을 추가·삭제하는 경로가 없음을 확인한다. 요청에 남은 세션 식별자가 토큰이 바인딩된 헬퍼 파드의 세션과 같음을 확인한다.

### AC-H4: 접근 요청 도구 — 승인 게이트 대신 control plane의 사람 결정
- **설명**: 세션 MCP는 접근 요청 도구 하나를 더 낸다. 인자는 레포(`owner/repo`)와 이유이고, 결과는 "대기 중 · 이미 허용됨" 중 하나다. 이 도구는 AC-F3의 승인 게이트를 **거치지 않는다** — 하는 일이 control plane에 대기 항목을 만드는 것뿐이고, 그 항목이 실제 허락이 되려면 사람이 control plane에서 결정해야 하므로(AC-H2), 그 결정이 이 도구의 게이트다. 이것은 세션 MCP 도구 표면 규칙 R1("파드 밖에 닿는 도구는 전부 게이트")의 **명시적 예외**이며 예외의 조건은 세 가지다: 닿는 곳이 control plane뿐이다 · 결과로 아무것도 열리지 않는다 · 같은 세션의 같은 레포 요청은 하나로 합쳐진다. 요청이 남으면 세션 출력에 in-band 마커(AC-F3과 같은 형태)로 "어디서 결정하는지"를 남긴다. 도구 목록에는 게이트가 설 때만 오른다(R2 그대로).
- **달성 가치**: V1, V8
- **검증 방법**: 도구 호출이 승인 게이트웨이에 요청을 만들지 않고 control plane에 대기 항목 하나를 만듦을 확인한다. 같은 레포를 두 번 요청하면 대기 항목이 하나임을, 이미 허용된 레포면 "이미 허용됨"을 돌려주고 항목을 만들지 않음을 확인한다. 저장소가 꺼진 배포(AC-H1)에서는 도구가 목록에 없음을 확인한다.

### AC-H5: 비공개 `git_clone` — 허용 목록 + 헬퍼 파드가 발급한 단명 토큰
- **설명**: `git_clone`은 대상이 `github.com`의 레포일 때, 승인(AC-F3)을 받은 **뒤** control plane에 허용 목록 여부를 묻는다(AC-H3). 허용 목록에 있으면 헬퍼 파드가 K3s MCP의 GitHub App 설치 토큰 도구로 **그 레포 하나·`contents: read`** 토큰을 발급받아, 그 클론 프로세스에만 URL 범위 인증 헤더로 넘겨 클론한다. 토큰은 승인 문맥·도구 결과·로그·공유 볼륨·클론된 저장소의 설정 어디에도 남지 않는다. 허용 목록에 없으면 클론하지 않고 "허용 목록에 없음 — 접근 요청 도구로 요청할 수 있다"를 결과로 돌려준다. 공개 레포는 허용 목록과 무관하게 지금처럼 받는다. 토큰을 발급하는 K3s MCP 프록시는 헬퍼 파드 안에서 세션 MCP만 쓰며, `approval-gated` 헬퍼 파드에도 같은 프록시를 둔다 — 두 타입 모두 **워크로드 파드는 그 프록시에 닿지 않는다**(AC-F2 egress 경계, AC-G6의 K3s 도구 예외와 별개). 실패는 사유별로 구분한다: 허용 목록에 없음 · 호출 거절 · 레포를 찾을 수 없음/권한 없음 · 토큰 발급 실패.
- **달성 가치**: V8, V1 (AC-F3·F5·F6 구체화)
- **검증 방법**: 허용 목록에 있는 비공개 레포가 승인 후 클론되고, 없는 레포는 승인 후에도 클론되지 않고 "허용 목록에 없음"으로 끝남을 확인한다. 발급 요청이 그 레포 하나·읽기 권한으로만 나가는지 확인한다. 클론 결과·로그·승인 문맥과 클론된 `.git/config`에 토큰이 없음을 확인한다. 공개 레포 클론이 허용 목록과 무관하게 그대로 동작함을 확인한다.

## 결정 사항 (2026-10-24, 사용자)
- **저장소는 SQLite, 운영 replica 1개** — 다중 replica 공유가 필요한 ConfigMap 방식 대신 SQLite를 택했다. 따라서 이 기능은 replica 1개·`Recreate` 배포에서만 켠다(AC-H1). kind e2e(replica 2개)에서는 끈다.
- **인증 범위는 관리 기능만** — 기존 세션 API·화면은 인증 밖에 그대로 둔다(AC-H2).
- **관리 권한은 로그인한 사용자 전부** — 그룹 제한을 두지 않는다(AC-H2).
- **토큰은 헬퍼 파드가 직접 발급** — control plane이 토큰을 다루지 않는다. 정책(허용 목록) 판정은 control plane, 자격 증명은 헬퍼 파드(AC-H3·H5).
- **항목 단위는 `owner/repo` 정확히** — 와일드카드 없음(AC-H1).
- **접근 요청 도구는 승인 게이트를 거치지 않는다** — R1에 예외를 명시한다(AC-H4).
- **화면은 mockup 먼저** — `docs/mockups/repo-access.html`과 여정 `JRN-repo-access`를 먼저 세우고 구현은 그 뒤에 한다.
