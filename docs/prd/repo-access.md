# PRD: 비공개 레포 접근 — 허용 목록과 접근 요청 (repo-access)

> 대상 요구사항: 세션 MCP의 `git_clone`이 **사람이 레포 단위로 허락한 비공개 GitHub 레포**를 받을 수 있게 하고,
> 그 허락(허용 목록)을 control plane이 보관·관리하며, 세션이 허락을 **요청**할 수 있게 한다.
> 적용 대상은 세션 MCP가 있는 두 타입 `approval-gated`(AC-F)·`minimax-code`(AC-G)다.

## 달성 가치
- **V8 목적에 맞는 작업 환경 선택** — 게이트가 걸린 에이전트 세션이 공개 레포에 묶이지 않고, 작업자가 고른 비공개 레포 위에서도 일할 수 있게 함 (AC-H5)
- **V1 세션 격리** — 비공개 레포 자격 증명은 레포 하나·읽기 전용·클론 한 번으로 좁혀 워크로드 파드 밖에서만 쓰고, 허락되지 않은 레포에는 어떤 경로로도 닿지 않게 함 (AC-H3·H5 — AC-A1·F6 구체화)
- **V1 세션 격리 (관리 경계)** — 무엇을 열지는 배포의 인그레스 인증을 지난 사람만 정하고, 세션은 요청만 남길 수 있음 (AC-H2·H4)

> 📌 **가치 연결 규칙**: 다른 PRD와 같이 각 AC의 달성 가치는 자신이 구체화하는 상위 AC의 가치를 상속한다.
> 새 가치는 신설하지 않는다.

> 이 PRD가 못박는 성질은 하나다 — **허용 목록이 있는 배포에서 레포 클론의 문은 허용 목록 하나다.** 허용 목록은
> 레포 단위로 오래 남는 사람의 결정이고, 그 결정이 있는 레포는 호출마다 다시 묻지 않으며(AC-F3 승인을 거치지
> 않는다), 그 결정이 없는 레포는 공개 레포라도 받지 않는다. 다른 외부 호출(`web_fetch_get` 등)의 승인은 그대로다.

## Acceptance Criteria

### AC-H1: 허용 목록 저장 — control plane의 SQLite, 단일 replica opt-in
- **설명**: 허용 목록과 대기 중인 접근 요청은 control plane이 SQLite 파일 하나에 보관한다. 항목은 GitHub 레포 하나(`owner/repo`, 대소문자 무시 비교)이고 누가·언제·어떤 경로(직접 추가 / 요청 허락)로 추가했는지를 함께 남긴다. 저장소는 **opt-in**이다 — `REPO_ACCESS_ENABLED=true`일 때만 켜지고, 없으면 이 PRD의 API는 전부 `503`을 돌려주며 세션 MCP는 비공개 클론과 접근 요청을 하지 않는다(공개 클론은 그대로). SQLite는 control plane 파드 안의 파일이라 **replica 사이에 공유되지 않으므로**, 이 기능을 켠 배포는 control plane을 replica 1개·`Recreate` 전략으로 운영한다. 이것은 AC-C1의 "상태는 다중 replica가 공유한다"에 대한 **이 기능 한정 예외**이며, 세션 상태(AC-C1)는 영향을 받지 않는다. 파일 위치는 설정이 아니라 코드에 고정된 경로(`/var/lib/session-platform/repo-access/`)이고, 켜는 배포는 그 디렉터리에 영속 볼륨을 마운트해 control plane 재시작·재배포를 건너 보존한다 — 마운트 없이 켜면 기동이 실패한다(파드 파일시스템에 조용히 만들어 재시작 때 잃지 않게).
- **달성 가치**: V1 (AC-H2·H5의 기반)
- **검증 방법**: 허용 목록에 항목을 추가하고 control plane을 재시작한 뒤에도 항목이 남아 있음을 확인한다. 경로 설정 없이 기동하면 관리·내부 API가 `503`이고 세션 MCP가 비공개 클론을 시도하지 않음을 확인한다. 같은 레포를 대소문자만 바꿔 두 번 추가하면 한 항목으로 수렴함을 확인한다.

### AC-H2: 관리 API와 화면 — 배포의 인그레스 인증(Authelia forward-auth) 뒤에서
- **설명**: control plane은 허용 목록 조회·추가·삭제와 대기 요청 조회·허락·거절을 하는 관리 API와, 그것을 쓰는 SPA 화면(레포 접근 화면)을 낸다. 관리 API·화면에는 **control plane 자체의 로그인이 없다** — 세션 API(AC-C*)·다른 화면과 같이, 배포가 인그레스에 건 Authelia forward-auth가 이 경로의 유일한 문이다. 그 문을 지난 사용자는 모두 관리 권한을 가진다(별도 그룹 제한 없음). 인그레스가 `Remote-User` 헤더를 넘겨주면 control plane은 그 값을 항목의 "추가한 사람"으로 남기되, 헤더는 **기록일 뿐 검사하지 않는다**(클러스터 안에서는 누구나 붙일 수 있다). 인그레스를 거치지 않는 클러스터 안 호출자는 세션 API와 같이 이 API에도 닿는다 — 워크로드 파드는 AC-F2 egress 경계로 control plane에 닿지 않는다. 요청을 허락하면 그 레포가 허용 목록에 오르고 요청은 대기 목록에서 빠지며, 거절하면 요청만 빠진다. 이미 허용된 레포에 대한 요청은 허락해도 항목이 늘지 않는다.
- **달성 가치**: V1
- **검증 방법**: 관리 API가 별도 로그인·쿠키 없이 응답함을 확인한다. 인그레스를 통한 호출은 forward-auth를 지나야 닿고, `Remote-User`가 넘어오면 추가·허락한 항목의 `addedBy`에 그 값이 남으며 없으면 빈 값임을 확인한다. 요청 허락 → 허용 목록 반영·대기 목록 제거, 거절 → 대기 목록 제거·허용 목록 불변을 확인한다.

### AC-H3: 헬퍼 파드 → control plane 내부 API — 서비스 어카운트 토큰으로 신원 확인
- **설명**: 세션 MCP(헬퍼 파드의 `session-mcp` 컨테이너)는 control plane의 내부 API로 (a) 레포가 허용 목록에 있는지 묻고 (b) 접근 요청을 남긴다. 이 호출은 그 컨테이너에만 마운트되는 **control plane 전용 audience의 projected 서비스 어카운트 토큰**으로 인증하고, control plane은 TokenReview로 그 토큰이 `session-mcp` 서비스 어카운트의 것이고 어느 세션의 헬퍼 파드에 바인딩됐는지 확인한다. 워크로드 파드는 이 API에 닿지 않는다(AC-F2 egress 경계 그대로). 내부 API는 허용 목록을 바꾸지 못한다 — 요청을 **대기** 상태로 남기는 것까지만 할 수 있다.
- **달성 가치**: V1 (AC-F2·F6 구체화)
- **검증 방법**: 유효한 헬퍼 토큰으로는 조회·요청이 성공하고, 다른 audience 토큰·다른 서비스 어카운트 토큰·토큰 없음은 `401`임을 확인한다. 내부 API로 허용 목록을 추가·삭제하는 경로가 없음을 확인한다. 요청에 남은 세션 식별자가 토큰이 바인딩된 헬퍼 파드의 세션과 같음을 확인한다.

### AC-H4: 접근 요청 도구 — 승인 게이트 대신 control plane의 사람 결정
- **설명**: 세션 MCP는 접근 요청 도구 하나를 더 낸다. 인자는 레포(`owner/repo`)와 이유이고, 결과는 "대기 중 · 이미 허용됨" 중 하나다. 이 도구는 AC-F3의 승인 게이트를 **거치지 않는다** — 하는 일이 control plane에 대기 항목을 만드는 것뿐이고, 그 항목이 실제 허락이 되려면 사람이 control plane에서 결정해야 하므로(AC-H2), 그 결정이 이 도구의 게이트다. 이것은 세션 MCP 도구 표면 규칙 R1("파드 밖에 닿는 도구는 전부 게이트")의 **명시적 예외**이며 예외의 조건은 세 가지다: 닿는 곳이 control plane뿐이다 · 결과로 아무것도 열리지 않는다 · 같은 세션의 같은 레포 요청은 하나로 합쳐진다. 요청이 남으면 세션 출력에 in-band 마커(AC-F3과 같은 형태)로 "어디서 결정하는지"를 남긴다. 도구 목록에는 게이트가 설 때만 오른다(R2 그대로).
- **달성 가치**: V1, V8
- **검증 방법**: 도구 호출이 승인 게이트웨이에 요청을 만들지 않고 control plane에 대기 항목 하나를 만듦을 확인한다. 같은 레포를 두 번 요청하면 대기 항목이 하나임을, 이미 허용된 레포면 "이미 허용됨"을 돌려주고 항목을 만들지 않음을 확인한다. 저장소가 꺼진 배포(AC-H1)에서는 도구가 목록에 없음을 확인한다.

### AC-H5: 비공개 `git_clone` — 허용 목록 + 헬퍼 파드가 발급한 단명 토큰
- **설명**: 허용 목록이 있는 배포(AC-H1)에서 `git_clone`은 **AC-F3의 승인을 거치지 않는다** — 받을 수 있는 것은 허용 목록에 있는 `https://github.com/owner/repo` 레포뿐이고, 그 판정이 곧 이 호출의 문이다. 호출이 오면 control plane에 허용 목록 여부를 묻고(AC-H3), 있으면 헬퍼 파드가 K3s MCP의 GitHub App 설치 토큰 도구로 **그 레포 하나·`contents: read`** 토큰을 발급받아, 그 클론 프로세스에만 URL 범위 인증 헤더로 넘겨 클론한다. 토큰을 발급할 수 없으면(설치 범위 밖의 공개 레포 등) 익명으로 클론하고, 그것도 실패하면 토큰 발급 실패로 끝난다. 토큰은 도구 결과·로그·공유 볼륨·클론된 저장소의 설정 어디에도 남지 않는다. 허용 목록에 없으면 **공개 레포라도** 클론하지 않고 "허용 목록에 없음 — 접근 요청 도구로 요청할 수 있다"를 돌려준다. `github.com` 밖의 주소는 받지 않는다. 허용 목록을 확인할 수 없으면 클론하지 않는다(닫힌 쪽으로 실패). 허용 목록이 없는 배포의 `git_clone`은 이전 그대로 호출마다 승인을 받고 공개 레포만 받는다. 토큰을 발급하는 K3s MCP 프록시는 헬퍼 파드 안에서 세션 MCP만 쓰며, `approval-gated` 헬퍼 파드에도 같은 프록시를 둔다 — 두 타입 모두 **워크로드 파드는 그 프록시에 닿지 않는다**(AC-F2 egress 경계, AC-G6의 K3s 도구 예외와 별개). 실패는 사유별로 구분한다: 허용 목록에 없음 · 허용 목록을 확인할 수 없음 · 레포를 찾을 수 없음/권한 없음 · 토큰 발급 실패.
- **달성 가치**: V8, V1 (AC-F3·F5·F6 구체화)
- **검증 방법**: 허용 목록에 있는 비공개 레포가 승인 게이트웨이에 요청 없이 클론되고, 없는 레포는 공개 레포라도 클론되지 않고 "허용 목록에 없음"으로 끝남을 확인한다. 발급 요청이 그 레포 하나·읽기 권한으로만 나가는지 확인한다. 클론 결과·로그와 클론된 `.git/config`에 토큰이 없음을 확인한다. 허용 목록 조회가 실패하면 아무것도 클론되지 않음을 확인한다. 허용 목록이 없는 배포에서는 이전처럼 승인 후 공개 레포만 받음을 확인한다.

## 결정 사항 (2026-10-24, 사용자)
- **저장소는 SQLite, 운영 replica 1개** — 다중 replica 공유가 필요한 ConfigMap 방식 대신 SQLite를 택했다. 따라서 이 기능은 replica 1개·`Recreate` 배포에서만 켠다(AC-H1). kind e2e(replica 2개)에서는 끈다.
- **관리 기능에 앱 자체 로그인을 두지 않는다** — 처음에는 control plane이 Authelia OIDC(PKCE)를 직접 처리했으나, 배포가 control plane 전체를 Authelia forward-auth 뒤에 두면서(2026-10-24) 같은 Authelia 세션을 두 번 묻는 중복이 됐다. 그래서 관리 API·화면도 세션 API와 같이 인그레스 인증 하나에 맡긴다(AC-H2, 2026-10-24 사용자).
- **관리 권한은 인그레스 인증을 지난 사용자 전부** — 그룹 제한을 두지 않는다(AC-H2).
- **토큰은 헬퍼 파드가 직접 발급** — control plane이 토큰을 다루지 않는다. 정책(허용 목록) 판정은 control plane, 자격 증명은 헬퍼 파드(AC-H3·H5).
- **항목 단위는 `owner/repo` 정확히** — 와일드카드 없음(AC-H1).
- **접근 요청 도구는 승인 게이트를 거치지 않는다** — R1에 예외를 명시한다(AC-H4).
- **허용 목록이 있으면 `git_clone`도 승인 게이트를 거치지 않는다** — 허용 목록이 유일한 문이고, 목록에 없는 레포는 공개 레포라도 받지 않는다. R1의 두 번째 명시적 예외(AC-H5). 처음 설계는 승인 + 허용 목록의 두 겹이었으나, 허용 목록에 넣는 것이 이미 사람의 결정이라 같은 레포를 받을 때마다 다시 묻는 것은 중복이라고 판단했다.
- **화면은 mockup 먼저** — `docs/mockups/repo-access.html`과 여정 `JRN-repo-access`를 먼저 세우고 구현은 그 뒤에 한다.
