# PRD: 세션 스케줄러 — 나중에·반복해서 도는 프롬프트

> 대상 요구사항: `codex-chat`·`codex-task` 세션의 모델이 **나중에 한 번, 또는 반복해서** 자기 세션에 프롬프트를 넣을 수 있게 한다 — Claude Code CLI의 `/loop`(고정 간격·자체 페이싱)와 한 번 예약에 해당하는 것
> (`codex-workload.md` AC-J5·`codex-task-workload.md` AC-M1의 도구 표면에 얹히는 축, 2026-11-09 사용자 요청)

## 달성 가치
- **V8 목적에 맞는 작업 환경 선택** — 고른 작업 환경(codex 세션)이 「지켜보기·나중에 다시 보기」 같은 시간에 걸친 일을 그 환경 안에서 끝낸다 (AC-P1·P2가 AC-J5·AC-M1의 도구 표면을 넓힘)
- **V2 유휴 자원 회수** — 예약이 남아 있는 동안만 유휴 회수를 미루고, 예약이 끝나면 일반 규칙으로 돌아간다 (AC-P3이 AC-B1의 예외를 하나 더 정함)

> 📌 **가치 연결 규칙**: 각 AC는 자신이 구체화하는 상위 AC의 가치를 상속한다. 새 가치는 신설하지 않는다.

## 용어
- **예약(schedule)** — 세션 안에서 나중에 실행될 프롬프트 하나. 종류는 셋이다.
  - **한 번(once)** — 정한 시각에 한 번 돌고 사라진다.
  - **고정 루프(fixed loop)** — 정한 간격마다 돈다.
  - **자체 페이싱 루프(self-paced loop)** — 회차마다 모델이 다음 실행 시각을 정한다(`loop_next`). 정하지 않고 턴을 끝내면 등록 때의 **기본 간격** 뒤에 다시 돈다.
- **회차(run)** — 예약 하나가 큐에 넣은 프롬프트 한 번과 그것이 만든 턴.
- **스케줄러** — codex 세션 파드의 loopback 사이드카(`k3s-mcp-proxy` 컨테이너, AC-J6)가 함께 내놓는 MCP 엔드포인트와 그 시계.

## Acceptance Criteria

### AC-P1: 스케줄러 MCP 도구 — 모델이 등록·조회·취소한다
- **설명**: `codex-chat`·`codex-task` 세션의 관리형 `config.toml`은 사이드카의 스케줄러를 MCP 서버 `scheduler`(`http://127.0.0.1:<사이드카 포트>/scheduler/mcp`, 도구 승인 없음)로 등록한다. 도구는 다섯이다.
  - `schedule_once{prompt, delay | at}` — `delay`(ISO 8601 기간, 예 `PT30M`) 뒤, 또는 `at`(오프셋이 붙은 RFC 3339 시각) 에 한 번.
  - `loop_create{prompt, interval?, fallback_interval?, expires_in?}` — `interval`이 있으면 고정 루프, 없으면 자체 페이싱 루프(`fallback_interval` 기본 `PT10M`). 첫 회차는 등록 직후다. `expires_in` 기본·상한 `P7D`.
  - `loop_next{id, delay}` — 자체 페이싱 루프의 다음 회차를 `delay` 뒤로 정한다. 고정 루프·한 번 예약에는 오류다.
  - `schedule_list{}` — 이 세션의 예약 목록(id·종류·프롬프트 앞부분·다음 실행 시각·회차 수·만료 시각·지금 도는 중인지).
  - `schedule_cancel{id}` — 예약을 지운다. 자체 페이싱 루프를 끝내는 것도 이 도구다.
- **입력은 해석하지 않는다.** 시간은 ISO 8601 기간(`P[nD][T[nH][nM][nS]]`, 정수만)과 오프셋이 붙은 RFC 3339 시각만 받는다 — 「내일 아침」 같은 자연어를 해석하는 일은 모델의 몫이고 도구는 하지 않는다. 사람의 말을 모델이 그대로 옮겼는지를 도구는 보장할 수 없으므로(2026-11-09 사용자와 확인), 등록·`loop_next`의 결과는 **계산한 절대 시각(UTC RFC 3339)과 id**를 돌려주고, 개발자 지시가 그 시각을 사용자에게 알리라고 이른다.
- **한계는 도구가 강제한다**(모델이 넘겨도 넘을 수 없다): 세션당 예약 20개, 프롬프트 1~16 KiB의 UTF-8, 간격·기본 간격·`loop_next` 지연 1분~24시간, 한 번 예약은 1분~7일 뒤, 루프 수명 1분~7일. 벗어나면 도구 결과가 `isError`이고 예약은 생기지 않는다. 잘못된 모양의 호출(모르는 인자 등)은 JSON-RPC 오류다.
- **예약은 사이드카의 메모리에만 있다.** 사이드카가 다시 시작하거나 파드가 바뀌면(동결·복원, 삭제) 예약은 사라진다 — 복원된 세션은 예약 없이 뜬다. 도구 설명이 이를 알린다.
- **달성 가치**: V8
- **구체화 대상**: AC-J5·AC-M1의 도구 표면 — MCP 서버 하나를 더한다(K3s MCP·skills·세션 DB와 같은 자리)
- **검증 방법**: 두 타입의 관리형 설정에 `scheduler` 서버가 있음을 확인한다. 각 도구의 정상 호출이 id와 절대 시각을 돌려주고 `schedule_list`에 반영됨을, 한계를 벗어난 값·자연어 시간·고정 루프에 대한 `loop_next`가 `isError`이고 목록이 변하지 않음을 확인한다.

### AC-P2: 회차는 claudeWorkload 큐로 들어가고, 세션이 한가할 때만 시작한다
- **설명**: 회차는 **그 세션 에이전트의 직렬 큐(AC-E2)에 프롬프트로 들어간다** — 사이드카가 loopback으로 에이전트의 `POST /write`를 부른다. control plane을 거치지 않는다(2026-11-09 사용자 결정: `codex queue`도 control plane `session write`도 아니고 큐로 깨운다). 그래서 회차는 사람의 write와 같은 턴이 되고, 같은 출력·커서 규약(AC-E3)에 남는다.
  - **한가할 때만 시작**: 실행 시각이 된 예약은 에이전트가 한가할 때 — 도는 턴이 없고 큐가 비어 있을 때 — 큐에 들어간다. 사람이 대화 중이면 그 대화가 끝날 때까지 기다린다. 스케줄러가 넣은 회차는 한 번에 하나다 — 그 회차의 턴이 끝나기 전에는 다른 예약도 넣지 않는다. 사이드카는 에이전트 loopback 전용 `GET /queue`(도는 턴·대기 수·끝난 턴 수)로 이를 본다.
  - **다음 회차**: 한 번 예약은 회차가 끝나면 사라진다. 고정 루프의 다음 실행 시각은 계획 시각에 간격을 더한 것이고, 그 시각이 이미 지났으면(턴이 길었거나 세션이 바빴으면) 지금 뒤의 첫 칸으로 건너뛴다 — 밀린 회차를 몰아서 돌리지 않는다. 자체 페이싱 루프는 회차 중에 `loop_next`가 오면 그 시각, 오지 않고 턴이 끝나면 끝난 때부터 기본 간격 뒤다. 만료 시각을 넘긴 루프는 다음 회차 없이 사라진다.
  - **회차 표식**: 큐에 넣는 프롬프트는 첫 줄에 `[session-platform scheduler] <id> …`(종류·회차 번호, 자체 페이싱이면 `loop_next`/`schedule_cancel`을 부르라는 안내와 기본 간격)를 붙인다 — 출력에서 어떤 턴이 예약이 만든 것인지 읽을 수 있다.
  - **넣지 못하면**: 큐가 차 있거나(429) 에이전트가 동결 준비·복원 중이면(409·503) 회차를 버리지 않고 잠시 뒤 다시 시도한다.
- **달성 가치**: V8
- **구체화 대상**: AC-E2(직렬 큐)·AC-J2(write = 턴 1회) — 큐에 쓰는 주체가 하나 더 생긴다
- **검증 방법**: 예약 회차가 출력에 표식과 함께 턴으로 나타남을 확인한다. 사람의 턴이 도는 동안 실행 시각이 된 예약은 그 턴이 끝난 뒤에 시작함을, 고정 루프의 간격보다 긴 턴 뒤에 밀린 회차가 한 번만 돎을, 자체 페이싱 루프가 `loop_next`의 시각과 기본 간격을 따름을 확인한다.

### AC-P3: 예약이 남아 있는 동안은 유휴 회수를 미룬다
- **설명**: 사이드카가 회차를 control plane을 거치지 않고 넣으므로 `lastAccess`는 회차로 갱신되지 않는다. 그대로 두면 60분 뒤 유휴 회수(AC-B1)가 파드를 거두고 예약도 함께 사라진다. 그래서 **유휴 회수 경로(IdleReaper)는 `codex-chat`·`codex-task` 세션의 에이전트에 `GET /scheduler`로 예약 수를 묻고, 하나 이상이면 동결 대신 `lastAccess`를 갱신한다** — AC-F3의 승인 대기 예외와 같은 자리, 같은 방식이다(2026-11-09 사용자 결정: 회수를 막는다). 에이전트는 이 물음을 loopback 사이드카에 넘긴다.
  - 예약이 모두 끝나면(한 번 예약이 돌았거나, 루프가 취소·만료되면) 갱신도 멈추고 일반 유휴 카운트로 돌아간다. 루프 수명 상한(7일, AC-P1)이 곧 이 예외가 파드를 붙잡을 수 있는 상한이다.
  - **사용자 주도 동결·삭제는 막지 않는다** — 그때 예약은 사라진다(AC-P1). 예외는 회수 경로에만 있다.
  - 답을 읽지 못하면(에이전트·사이드카 응답 없음) 일반 유휴 규칙을 적용한다 — AC-F3과 같다.
- **달성 가치**: V2
- **구체화 대상**: AC-B1(60분 유휴)의 「마지막 read/write 이후 경과 시간」 — 예약이 남아 있는 구간의 처리. AC-D5의 「유휴는 클라이언트 접근 부재로 잰다」에서 **의도적으로 벗어나는** 두 번째 예외다(첫째는 AC-F3)
- **검증 방법**: 예약이 있는 codex 세션은 유휴 시간이 기준을 넘어도 회수 경로가 동결하지 않고 `lastAccess`가 갱신됨을, 예약을 취소한 뒤에는 다시 회수됨을, 사용자 동결은 예약이 있어도 동결함을, 에이전트가 답하지 않으면 회수됨을 확인한다.

## 결정 사항 (2026-11-09, 사용자)
- **회차는 claudeWorkload 큐로 넣는다** — `codex queue`(상주 codex 프로세스가 없어 붙을 곳이 없다)도 control plane `session write`도 아니다.
- **회수를 막는다** — 예약이 남은 세션은 유휴 회수 경로가 건너뛴다(AC-P3). 대가: 예약이 있는 동안 파드와 그 세션의 인증 풀 슬롯(AC-N2)이 계속 잡힌다.
- **고정 루프·한 번 예약·자체 페이싱 루프를 모두 둔다.** 셋의 차이는 「누가 정하느냐」가 아니라 **실행 시각이 등록 때 한 번 정해지는가, 회차마다 모델이 다시 정하는가**다 — 도구는 모델이 넘긴 값만 보므로 사람의 말을 「그대로」 옮겼다는 보장은 도구 수준에서 성립하지 않는다. 그래서 입력을 모호하지 않게 받고, 계산한 시각을 되읽어 주고, 한계를 도구가 강제하고, 회차에 표식을 남긴다.
- **스케줄러는 기존 사이드카(`k3s-mcp-proxy`)가 함께 내놓는다** — 세션 DB MCP(AC-N6)와 같은 방식이다. 컨테이너를 더하지 않는다.

## 알려 둘 경계
- 사람이 모델을 거치지 않고 예약을 직접 보거나 지우는 길(SPA·control plane API)은 없다. 사람은 세션에 말해서 모델이 도구를 부르게 한다.
- 예약은 영속하지 않는다(AC-P1). 동결·복원을 건너 이어지는 예약이 필요해지면 후속 결정이다.
- 회차는 사람의 턴과 같은 큐·같은 출력에 쌓이므로 출력 한도(AC-E3)를 함께 쓴다. 짧은 간격의 긴 루프는 세션 출력 상한에 빨리 닿는다.
- `codex-chat`의 회차도 `codex-chat`의 좁은 도구 표면(AC-J5) 안에서만 돈다 — 예약이 도구를 넓히지 않는다.
- 다른 에이전트 타입(`claude-code`·`approval-gated`·`minimax-code`)에는 이번에 두지 않는다.
