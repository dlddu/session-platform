# PRD: 세션 워크로드 — 승인 게이트 (approval-gated)

> 대상 요구사항: 세션 워크로드 타입에 **승인 게이트가 걸린 대화형 에이전트** 추가
> (`shell`·`claude-code`와 병존하는 세 번째 타입, `claude-code-workload.md`와 대응 관계)

## 달성 가치
- **V8 목적에 맞는 작업 환경 선택** — 세션 생성 시 세 번째 작업 환경을 고를 수 있게 하고, 선택과 무관하게 V1~V5 보장이 동일하게 성립함을 확정 (AC-F1)
- **V1 세션 격리** — 에이전트의 나가는 트래픽·보조 파드·자격 증명을 세션 경계 안에 가둠 (AC-A1/A2/A3 구체화)
- **V2 유휴 자원 회수** — 보조 파드와 공유 볼륨까지 세션 수명에 묶어 함께 회수 (AC-A3·B1의 타입별 경로)
- **V3 끊김 없는 세션 연속성** — 승인 게이트를 통과한 결과물과 대화 문맥이 동결·복원을 건너 보존됨 (AC-B2/B3 구체화), write/read를 프롬프트·실행 출력 시맨틱으로 확정 (AC-C2/C3 구체화)
- **V4 자유로운 멀티세션 전환** — 전환 후에도 동일한 offset 커서 규약으로 출력을 이어 읽음 (AC-C2 구체화)

> 📌 **가치 연결 규칙**: `shell-workload.md`·`claude-code-workload.md`와 동일하게, 각 AC의 달성 가치는 자신이
> 구체화하는 상위 AC의 가치를 상속한다. **AC-F1(타입 선택)만 예외**로, 상속할 상위 AC가 없어 추상 가치
> **V8**에 직접 연결한다 — AC-E1이 V8에 연결된 것과 같은 이유이며, 타입이 늘어도 `../values.md`는 변하지 않는다.
> 새 가치는 신설하지 않는다.

> 이 PRD는 **"에이전트가 외부에 닿는 순간마다 사람의 승인을 요구한다"** 는 한 가지 성질을 세션 워크로드
> 타입으로 못박는다. AC-F1이 타입 축에 세 번째 값을 더하고, AC-F2~F6은 이 타입에서 기존 AC들
> (AC-A1·A2·A3·B1·B2·B3·C2·C3)이 어떻게 구체화되는지를 정의한다. 실행 모델(원샷 프롬프트·직렬 큐·커서
> 규약·아카이브)은 `claude-code`와 같으므로 **복제하지 않고 AC-E2~E6을 참조**하며, 이 문서는 그 위에
> 얹히는 차이만 적는다. 재사용 중 **한 가지는 배치가 다르다** — 공급자 credential-proxy는 같은 동작 계약을
> 유지한 채 사이드카가 아니라 **보조 파드**로 분리된다(AC-F2의 확정 항목 · AC-F4 · AC-F6).

## Acceptance Criteria

### AC-F1: 워크로드 타입 `approval-gated` 선택
- **설명**: 세션 생성 요청의 `workloadType` 허용값에 `approval-gated`가 추가되어 `shell`·`claude-code`·`approval-gated` 세 가지가 된다. **필드 생략만** `shell` 기본값으로 해석하는 규칙과 explicit empty/null/비문자열·허용값 밖 입력을 pod 생성 전에 400으로 거부하는 규칙은 AC-E1과 동일하다. 타입은 **생성 시 확정되고 세션 수명 동안 불변**이다(바꾸려면 새 세션을 만든다). 하나의 세션은 정확히 하나의 워크로드 타입을 가지며, control plane은 이 타입에 대해 워크로드 파드와 **그 세션 전용 보조 파드 둘**(MCP 파드·credential-proxy 파드, AC-F4)을 함께 프로비저닝한다. 타입이 늘어나도 AC-A1(control plane은 워크로드를 직접 실행하지 않음)과 AC-A2(1 세션 = 1 전용 워크로드 파드, 보조 파드는 세션 전속)는 그대로 유지된다. `model` 필드의 계약(생략=`platform-default` 별칭, 불변, pattern 검증)도 AC-E6을 그대로 따른다.
- **달성 가치**: V8, V1
- **구체화 대상**: AC-A1의 "실제 세션 워크로드" — 이제 세 갈래로 분기한다 (AC-D1=`shell`, AC-E2~E6=`claude-code`, AC-F2~F6=`approval-gated`)
- **검증 방법**: `workloadType=approval-gated`로 세션을 생성하면 워크로드 파드와 세션 전용 보조 파드 둘(MCP·프록시)이 함께 기동되고 세션 조회 응답의 타입이 `approval-gated`임을 확인한다. `workloadType` 미지정·explicit `shell`·explicit `claude-code`는 기존과 동일하게 동작함을 확인한다. 허용값 외 타입과 explicit `""`/`null`/비문자열은 pod 생성 전 400으로 거부됨을 확인한다. 기존 세션 route로 workload/model 변경 필드를 보내면 400이고 원래 값이 유지됨을 확인한다.

### AC-F2: Egress 격리 — 워크로드 파드는 보조 파드를 통해서만 밖으로 나간다
- **설명**: `approval-gated` 세션의 **워크로드 파드는 나가는 트래픽(egress)이 명시적 허용 목록으로 제한된다.** 허용 대상은 (a) 이름 해석을 위한 kube-dns, (b) **그 세션 자신의** MCP 보조 파드(AC-F4), (c) **그 세션 자신의** credential-proxy 보조 파드(AC-F4·F6) 뿐이다. **공급자 API origin을 포함해** 그 밖의 모든 목적지 — 임의의 공개 인터넷 호스트, 클러스터 안의 다른 서비스, **다른 세션의 보조 파드** — 로 향하는 연결은 차단된다.

  즉 워크로드 파드에서 나가는 모든 연결은 **그 세션 전속 보조 파드 둘 중 하나에서 끝나고, 클러스터 밖으로 나가는 일은 보조 파드만 한다** — MCP는 승인 게이트(AC-F3)를 지나서, 프록시는 시작할 때 고정된 단일 HTTPS origin으로만. 따라서 에이전트가 스스로 `curl`이나 임의 소켓으로 외부에 닿을 경로가 없고, 공급자 API를 가장한 임의 외부 통신도 성립하지 않는다.

  두 보조 파드는 **ingress도 제한한다** — 각 보조 파드는 자기 세션의 워크로드 파드에서 오는 연결만 받는다. 그래서 다른 세션이 남의 MCP나 프록시를 빌려 쓸 수 없다. 이 제한은 전부 파드 수준의 네트워크 정책으로 강제하며 워크로드가 설정을 바꿔 우회할 수 없다.
- **달성 가치**: V1
- **구체화 대상**: AC-A1의 "실제 세션 워크로드"가 가질 수 있는 **네트워크 경계**, AC-A2의 세션 격리
- **검증 방법**: 실클러스터에서 워크로드 파드 안에 셸을 붙여 (a) kube-dns 조회 성공, (b) 자기 세션 MCP 파드로의 연결 성공, (c) 자기 세션 프록시 파드로의 연결 성공, (d) 임의 외부 목적지(공개 IP·다른 네임스페이스 서비스)와 **공급자 API origin 직접 연결**이 모두 **타임아웃/거부**됨을 실측한다. 다른 세션의 MCP·프록시 파드 주소로 직접 연결해도 차단되고(ingress 제한), 승인 게이트웨이 주소로도 닿지 못함을 확인한다. 네트워크 정책 오브젝트가 세션마다 올바른 셀렉터로 존재하고 세션 삭제 시 함께 사라짐을 확인한다.

> ✅ **확정 (2026-09-03, 공급자 프록시의 배치)**: 초판은 credential-proxy를 `claude-code`(AC-E6)처럼 워크로드
> 파드 안의 **사이드카**로 두었다. 그러나 네트워크 정책은 **파드 단위**로 적용되므로 사이드카가 공급자 HTTPS로
> 나가려면 허용 목록에 그 origin이 있어야 하고, 그러면 같은 파드의 주 컨테이너도 L3/L4에서는 같은 목적지에
> 닿아 승인 게이트에 구멍이 남았다. 이를 해소하기 위해 **프록시를 보조 파드로 분리**했다(참조 구현
> `pure-agent`의 llm-gateway와 같은 배치). 이제 워크로드 파드의 허용 목록에는 **외부 origin이 하나도 없다.**
>
> 대가는 셋이다 — ① 세션마다 파드가 셋(워크로드 + MCP + 프록시)이라 자원과 기동 시간이 늘고,
> ② 주 컨테이너와 프록시 사이가 loopback이 아니라 **클러스터 네트워크 홉**이 되며(아래 미해결 항목),
> ③ `claude-code`는 사이드카 배치를 유지하므로 같은 프록시가 두 가지 배치로 존재한다.
> ③은 프록시의 **동작 계약을 AC-E6 하나로 유지**하고 배치만 타입별로 다르게 두어 감수한다(AC-F6).

> ⚠️ **미해결 (워크로드↔프록시 홉의 평문 노출)**: 프록시가 보조 파드가 되면서 주 컨테이너와 프록시 사이가
> 같은 파드의 loopback이 아니라 **클러스터 네트워크 홉**이 되었다. 이 홉에 실리는 것은 공급자 자격 증명이
> 아니지만(토큰 교체는 프록시가 상류에서 하고, 하류에는 비밀이 아닌 placeholder만 흐른다) 프롬프트와 응답
> 본문이 평문으로 지나가므로, AC-E6이 평문 HTTP upstream을 "같은 pod 네트워크에서의 패킷 관찰 위험" 때문에
> 거부한 것과 **같은 종류의 노출**이다. 선택지는 ① 네임스페이스 네트워크를 신뢰 경계로 보고 수용,
> ② 이 홉을 TLS(또는 mTLS)로 감싸기, ③ CNI 수준 암호화에 위임. **현재 AC-F2·F6은 ①을 전제로 기술되어 있다.**
> `../doc-tracker.md`의 열린 항목 참고.

### AC-F3: 승인 게이트 — 외부 도구는 사람이 승인해야 실행된다
- **설명**: 세션 MCP(AC-F4)가 제공하는 **외부 네트워크 도구**는 호출될 때마다 외부 승인 게이트웨이에 승인 요청을 만들고, 그 요청이 **승인된 뒤에만** 실제 외부 호출을 수행한다. 결정이 거절·만료·타임아웃이면 도구는 실패를 반환하고 실제 호출은 일어나지 않는다. **도구 실패는 세션이나 실행 큐를 죽이지 않는다** — 에이전트는 실패를 도구 결과로 받아 다음 행동을 결정하고, 세션은 계속 `active`다.

  - **유일성**: 승인 요청의 외부 식별자는 게이트웨이에서 중복될 수 없으므로 **`{세션ID}:{요청ID}`** 형태로 만든다(요청ID는 그 도구 호출을 유일하게 가리키는 값). 같은 세션의 서로 다른 호출, 서로 다른 세션의 같은 호출이 모두 구분된다.
  - **대기 위치**: 승인 대기는 **AC-E2의 직렬 실행 큐 안에서 블로킹**한다. 대기하는 동안 그 invocation은 계속 자리를 점유하고, 같은 세션의 다음 write는 기존과 동일하게 큐에 선다(한 세션에서 두 실행이 겹치지 않는다). **write 자체는 대기를 기다리지 않고 즉시 반환**하며, prompt 1 MiB·큐 포화 429·누적 출력 상한은 AC-E2/E3 그대로다.
  - **대기 표시**: 대기 시작과 결정 결과는 **AC-E3의 같은 append-only 출력 바이트열에 in-band 마커로** 기록된다(예: `[session-platform: awaiting approval — <도구> · <외부 식별자>]`, 이어서 승인/거절/만료 결과 한 줄). 별도 SSE event type이나 run/queue 상태 event를 만들지 않으므로 커서 규약(`id=nextOffset`, `{offset,payloadBase64,nextOffset}`, UTF-8 경계, reset 복구)은 타입 간 동일하게 유지된다. 승인 컨텍스트에 자격 증명이나 게이트웨이 API key가 실리지 않는다(AC-F6).
  - **유휴 기준**: **승인 대기가 진행되는 동안 시스템은 그 세션의 `lastAccess`를 갱신하여 유휴 카운트가 진행되지 않게 한다.** 이는 AC-B1의 유휴 기준을 이 타입에서 구체화한 것으로, `shell`(AC-D5)의 "유휴는 워크로드의 바쁨이 아니라 클라이언트 접근 부재로 측정한다"는 규칙에서 **의도적으로 벗어난 예외**다. 근거: 승인 대기는 사람의 응답을 기다리는 구간이라 분 단위로 길어질 수 있는데, 이때 동결되면 승인이 나도 실행할 파드가 없어 승인 자체가 무의미해진다. 대기가 끝나면 이 갱신도 멈추고 일반 유휴 카운트로 돌아간다.
  - **동결·삭제와의 충돌**: 승인 대기 중에 수동 동결(AC-B1의 사용자 주도 트리거)이나 삭제가 오면 대기 중인 invocation은 취소되고 그 도구 호출은 실패로 끝난다. 게이트웨이에 남은 요청은 그대로 만료된다.
- **달성 가치**: V3, V2, V4
- **구체화 대상**: AC-C3(Write API 상태별 분기)의 "write" 시맨틱과 AC-C2/AC-E3의 출력·커서 규약 — `approval-gated` 타입 버전. AC-B1(60분 유휴)의 "마지막 read/write 이후 경과 시간" — 승인 대기 구간의 처리
- **검증 방법**: (a) 승인 경로 — 외부 도구를 부르는 프롬프트를 write하면 write가 즉시 반환하고, 대기 마커가 SSE와 read에 나타나며, 게이트웨이에서 승인한 뒤에만 실제 외부 호출이 일어나고 결과가 이어 붙는다. (b) 거절·만료·타임아웃 경로 — 각 결정마다 실제 호출이 일어나지 않고 도구가 실패를 반환하며 세션은 `active`로 남고 다음 write가 정상 처리된다. (c) 유일성 — 같은 세션의 연속 두 호출, 서로 다른 세션의 동시 호출이 서로 다른 외부 식별자를 만들고 게이트웨이 중복 오류가 발생하지 않는다. (d) 유휴 — 승인 대기가 지속되는 동안 `lastAccess`가 갱신되어 유휴 카운트가 진행되지 않고, 대기 종료 후에는 다시 진행된다. (e) 대기 중 수동 동결·삭제 시 invocation이 취소되고 실패로 마감된다.

### AC-F4: 보조 파드 둘 — 세션 전용 MCP와 credential-proxy, 수명은 세션과 일치
- **설명**: `approval-gated` 세션은 워크로드 파드 외에 **그 세션 전용 보조 파드 둘**을 갖는다. 둘 다 세션 워크로드(에이전트)를 실행하지 않고 그 워크로드가 쓰는 부수 기능만 제공하므로, AC-A2의 1:1 매핑을 깨지 않는 **보조 파드**다. 각각 세션 식별자 라벨로 세션에 귀속되며 다른 세션과 공유하지 않는다.

  - **MCP 파드** — 외부 접근 도구와 승인 게이트(AC-F3)를 제공한다. 승인을 통과한 외부 호출을 실제로 수행하는 것은 이 파드다.
  - **credential-proxy 파드** — 공급자 API로 가는 유일한 통로다. 시작할 때 HTTPS upstream origin을 고정하고 플랫폼 토큰을 주입하며, 그 동작 계약은 AC-E6과 같고 **배치만 사이드카가 아니라 보조 파드**다(AC-F6).

  수명은 세션과 일치한다 — 세션 생성 시 워크로드 파드와 함께 기동되고, **세션이 스냅샷으로 동결되거나 삭제될 때 워크로드 파드와 함께 회수된다**(AC-A3의 자원 회복은 세 파드를 합쳐 성립한다). 복원(AC-B2) 시에는 새 워크로드 파드와 함께 새 보조 파드 둘이 기동되고, 워크로드 파드에는 그때 만들어진 보조 파드 주소가 주입된다. 두 보조 파드 모두 **자체 상태를 보존하지 않는다** — 대기 중인 승인 요청의 진실 원천은 외부 게이트웨이이고, 파일 결과물은 공유 볼륨(AC-F5)에 있으며, 프록시는 요청을 중계할 뿐 아무것도 쌓지 않는다. 따라서 보조 파드는 스냅샷 대상이 아니며 동결 시 그냥 버려진다.
- **달성 가치**: V1, V2
- **구체화 대상**: AC-A2의 **보조 파드** 조항, AC-A3(자원 회수)의 회수 대상, AC-B1(동결)·AC-B2(복원)에서 함께 다뤄야 하는 pod 집합
- **검증 방법**: 실클러스터에서 세션 2개를 만들어 각 세션의 MCP 파드와 프록시 파드가 라벨로 구분되는 별개 파드이고 서로 공유되지 않음을 확인한다. 스냅샷 시 **세 파드가 모두** 사라지고 자원이 회복되는지, 삭제 시에도 같은지 확인한다. 복원 시 세 파드가 함께 기동되고, 에이전트가 새 MCP에 붙어 도구 호출이 다시 성립하며 새 프록시를 통해 공급자 호출이 다시 성립하는지 확인한다.

> 📌 **비용 메모**: 세션당 파드가 하나(다른 타입)에서 셋으로 늘어난다. 유휴 회수(V2)가 세 파드를 함께 걷어가므로
> 동결된 세션의 점유는 여전히 0이지만, **활성 세션당 스케줄링 단위와 기동 지연이 늘어난다.** 이는 AC-F2의
> egress 경계를 파드 단위 정책으로 강제하기 위해 치르는 값이며, 대안(사이드카 유지)은 경계에 구멍을 남긴다.

### AC-F5: 파일 교환 = 세션 전용 RWX 공유 볼륨, 아카이브에 포함
- **설명**: 워크로드 파드와 세션 MCP 파드는 **그 세션 전용의 ReadWriteMany 볼륨을 같은 경로에 함께 마운트**한다(credential-proxy 파드는 파일을 다루지 않으므로 마운트하지 않는다). 승인을 통과한 외부 호출의 결과물 중 도구 응답으로 실어 나르기에 큰 것(내려받은 파일, 큰 응답 본문)은 MCP가 이 볼륨에 쓰고 에이전트가 **파일로 읽는다** — 도구 응답 본문으로 왕복시키지 않는다. 볼륨은 세션 전용이라 다른 세션이 마운트하지 않는다(AC-A2/V1).

  **이 볼륨의 내용은 파일시스템 아카이브에 포함된다** — 동결 시 작업 디렉터리·대화 기록·누적 출력 버퍼와 함께 아카이브되고(AC-E5와 같은 경로·같은 opt-in 규칙), 복원 시 새 파드 쌍에 그대로 전개된다. 따라서 **동결·복원을 건너서도 이전 실행이 만든 파일이 남아 있고**, 복원 전에 발급된 `nextOffset` 커서도 AC-E5 그대로 유효하다.
- **달성 가치**: V3
- **구체화 대상**: AC-B3(스냅샷·복원 무결성)의 "보존 대상 상태" — 이 타입에서는 대화 기록·작업 디렉터리·출력 버퍼에 **공유 볼륨**이 더해진다. AC-B2(복원)의 전개 대상
- **검증 방법**: 승인된 외부 호출이 만든 파일이 워크로드 파드의 마운트 경로에서 보이고 MCP 파드가 쓴 것과 동일함을 확인한다. 그 세션을 동결했다가 복원한 뒤 같은 파일이 그대로 남아 있고 내용이 일치함을 확인한다(동결·복원을 건너선 왕복). 다른 세션의 볼륨이 마운트되지 않음을 확인한다. 동결 직전 확보한 `nextOffset`으로 복원 후 read하면 델타만 반환되고 `offset=0`은 전체 이력을 반환함을 확인한다.

### AC-F6: 자격 증명 분리 — 게이트웨이 키는 MCP 파드에, 공급자 자격 증명은 프록시 파드에
- **설명**: **워크로드 파드에는 어떤 외부 자격 증명도 주입하지 않는다.** 플랫폼 전역 Kubernetes Secret의 키는 필요한 보조 파드에만 나뉘어 들어간다.

  - **게이트웨이 URL·API key와 승인 알림 대상 `userId`** → **MCP 파드에만.** 따라서 에이전트는 게이트웨이에 직접 요청을 만들거나 자기 요청을 스스로 승인할 수 없다(AC-F2의 egress 제한과 합쳐져 게이트웨이 주소 자체에 닿지 못한다). `userId`는 **플랫폼 전역 단일 값**이며 세션 생성 요청으로 지정할 수 없다 — 요청 본문에 넣으면 unknown field로 400이다.
  - **공급자 `base-url`·`auth-token`** → **credential-proxy 파드에만.** 워크로드 파드의 주 컨테이너는 그 세션 프록시 파드의 **클러스터 내 주소**와 비밀이 아닌 placeholder 토큰만 받는다.

  프록시의 **동작 계약은 AC-E6을 그대로 재사용한다** — 시작 시 HTTPS upstream origin 고정(평문 HTTP upstream은 시작 거부), 허용 목록 밖 요청 헤더 제거와 플랫폼 토큰 단일 주입, CONNECT·Upgrade·trailer 거부, 중간 1xx를 포함한 응답의 토큰 redaction, raw upstream 64 MiB 상한 안에서의 SSE 증분 전달, response-read 경계를 넘는 tail-safe redaction이 모두 동일하다. **다른 것은 배치와 바인딩뿐이다**: 사이드카가 아니라 보조 파드이므로 loopback이 아니라 파드 IP에 바인딩하고, 대신 **자기 세션의 워크로드 파드에서 오는 연결만 받도록 ingress를 제한한다**(AC-F2). optional `model`/`models`의 기본값·soft catalog와 runner 출력의 증분 redaction도 AC-E6 그대로다.

  게이트웨이 키·`userId`·공급자 토큰은 세션 조회 응답·로그·read·SSE 출력 어디에도 노출되지 않으며, 승인 요청에 실리는 컨텍스트에도 포함되지 않는다.
- **달성 가치**: V1
- **구체화 대상**: AC-A1의 control plane / data plane 경계에서의 **자격 증명 배치**, AC-E6 프록시 계약의 재사용 지점과 배치 차이
- **검증 방법**: 세션 pod 스펙에서 (a) 게이트웨이 URL·API key·`userId`가 **MCP 파드에만**, (b) 공급자 `base-url`·`auth-token`이 **프록시 파드에만** 있고, (c) **워크로드 파드에는 둘 다 없이** 프록시의 클러스터 내 주소와 placeholder만 있음을 확인한다. 생성 요청에 게이트웨이 필드·`userId`·공급자 자격 증명을 넣으면 400임을 확인한다. 워크로드 파드에서 게이트웨이 주소·공급자 origin으로의 직접 연결이 AC-F2로 차단되고, 다른 세션의 워크로드 파드에서 이 프록시로의 연결도 ingress 제한으로 차단됨을 확인한다. 어떤 토큰 문자열도 read/SSE/control-plane 로그·승인 컨텍스트에 나타나지 않음을 확인한다. AC-E6의 프록시 검증 항목(고정 HTTPS upstream, 헤더 제거·토큰 주입, 1xx 포함 redaction, EOF 전 SSE chunk 전달, split-token redaction, 64 MiB 상한)은 **파드 IP 바인딩에서도 동일하게** 성립함을 확인한다. model 계약도 `claude-code`와 동일함을 확인한다.

> ⚠️ **미해결 (plugin 부트스트랩과 egress 허용 목록의 충돌)**: AC-E6의 런타임 plugin 부트스트랩은 주
> 컨테이너가 K3s MCP 엔드포인트와 `github.com`으로 **직접 나가는 것**을 전제한다. AC-F2의 허용 목록에는 그 두
> 목적지가 없으므로 `approval-gated`에서는 이 배선이 그대로는 성립하지 않는다. 선택지는 셋이다 —
> ① 이 타입에서는 런타임 부트스트랩과 `k3s-mcp-token`을 **아예 두지 않고** 플랫폼 도구를 세션 MCP 보조 파드
> 쪽으로만 노출한다(허용 목록이 그대로 유지되고 주 컨테이너의 Secret이 하나 줄어 가장 단순하다),
> ② MCP 보조 파드가 plugin seed를 공유 볼륨(AC-F5)에 내려놓고 주 컨테이너가 그것을 읽는다(런타임 갱신은
> 유지되나 기동 순서 의존이 생긴다), ③ 두 목적지를 허용 목록에 추가한다(AC-F2가 다시 느슨해지므로 비권장).
> **현재 AC-F6은 ①을 전제로 기술되어 있다** — 즉 이 타입의 주 컨테이너에는 `k3s-mcp-token`을 주입하지 않고
> 런타임 marketplace 설치도 하지 않는다. `../doc-tracker.md`의 열린 항목 참고.
