# PRD: 멀티테넌시 — 테넌트별 워크로드 타입과 세션 목록

> 대상 요구사항: 테넌시별로 **사용할 수 있는 워크로드 타입**과 **세션 목록**을 구분해서 제공
> (`architecture.md`·`state-api.md`의 세션 API 위에 얹히는 호출자 축)

## 달성 가치
- **V1 세션 격리** — 한 테넌트의 세션이 다른 테넌트에게 보이지도, 조작되지도 않음 (AC-K1·K2가 AC-A1의 격리를 호출자 축으로 넓힘)
- **V8 목적에 맞는 작업 환경 선택** — 테넌트마다 고를 수 있는 작업 환경을 정해 줌 (AC-K3이 AC-E1의 선택 축을 테넌트별로 좁힘)
- **V5 일관된 세션 상태** — 테넌트 소속은 세션의 불변 메타데이터로 같은 상태 저장소에 있음 (AC-K2)

> 📌 **가치 연결 규칙**: 각 AC는 자신이 구체화하는 상위 AC의 가치를 상속한다. 새 가치는 신설하지 않는다 —
> "누가 어떤 세션을 보는가"는 V1의 격리를, "누가 어떤 타입을 고르는가"는 V8의 선택을 호출자별로 나눈 것이다.

## 용어
- **테넌트** — 이름(DNS 라벨), 그 테넌트로 말하는 Kubernetes ServiceAccount 목록(`<namespace>/<name>`), 그 테넌트에 허용된 워크로드 타입 목록(또는 `"*"` — 타입 제한 없음).
- **운영자** — `Authorization` 헤더가 없는 요청. 배포의 Authelia forward-auth 뒤 브라우저 SPA와, 지금처럼 토큰 없이 부르는 내부 호출자.
- **무소속 세션** — 테넌트가 없는 세션. 테넌시 이전의 모든 세션과, 운영자가 테넌트를 지정하지 않고 만든 세션.

## Acceptance Criteria

### AC-K1: 호출자 식별 — ServiceAccount 토큰, 없으면 운영자
- **설명**: `Authorization: Bearer <토큰>`이 있는 요청은 테넌트 호출자다. control plane은 그 토큰을 TokenReview로 audience `session-platform`(설정 `TENANT_TOKEN_AUDIENCE`)에 대해 검증하고, 인증된 사용자 이름 `system:serviceaccount:<ns>:<name>`을 그 ServiceAccount를 목록에 둔 테넌트로 바꾼다. audience를 고정하는 이유는 워크로드의 기본(apiserver audience) 토큰이 테넌트 자격 증명으로 쓰이지 않게 하기 위해서다. 검증되지 않은 토큰·Bearer가 아닌 헤더·빈 헤더는 **401**, 검증됐지만 어느 테넌트도 주장하지 않는 계정은 **403**이다 — 어떤 경우에도 **운영자로 떨어지지 않는다**. `Authorization` 헤더가 아예 없는 요청은 운영자다(2026-11-05 사용자 결정).
- **달성 가치**: V1
- **구체화 대상**: AC-A1의 세션 격리 — 격리의 경계를 호출자까지 넓힌 것
- **검증 방법**: 테넌트 계정의 audience `session-platform` 토큰은 그 테넌트로, 위조 토큰·apiserver audience 토큰은 401로, 미등재 계정 토큰은 403으로 처리되고, 헤더 없는 요청은 운영자로 처리됨을 확인한다.

### AC-K2: 세션 소속과 가시성
- **설명**: 세션은 생성 시 소속 테넌트(`tenant`)를 받고 그 뒤 바뀌지 않는다 — 워크로드 타입처럼 세션 레코드(ConfigMap)에 저장되고 동결·복원을 건너 유지된다. 테넌트 호출자가 만든 세션은 항상 그 테넌트 소속이다. 테넌트 호출자의 `GET /sessions`는 자기 테넌트 세션만 돌려주고, 세션 id를 받는 모든 경로(조회·read·write·stream·switch·snapshot·delete·recover)는 다른 테넌트의 세션과 무소속 세션을 **없는 세션과 똑같이 404**로 답한다 — 어떤 id가 존재하는지도 알려 주지 않는다. 운영자는 모든 세션을 보고 조작하며, `GET /sessions?tenant=<이름>`으로 한 테넌트만(빈 값이면 무소속만) 거를 수 있다. 테넌트 호출자가 이 필터를 보내면 400이다.
- **달성 가치**: V1, V5
- **구체화 대상**: AC-C2/C3/C4·AC-A3 경로의 대상 범위 — 같은 동작을 호출자가 보는 세션으로 한정
- **검증 방법**: 두 테넌트가 각자 만든 세션이 각자의 목록에만 나타나고, 상대 세션과 무소속 세션의 id 경로가 모두 404이며 그 시도 뒤에도 세션이 남아 있고, 운영자는 둘 다 보고 필터로 가를 수 있음을 확인한다.

### AC-K3: 테넌트별 워크로드 타입
- **설명**: 테넌트는 허용된 워크로드 타입 목록을 가진다. 목록이 `["*"]` 하나면 **타입 제한 없음**이다 — 배포가 내놓는 모든 타입이 허용되고, 나중에 더해지는 타입도 설정을 고치지 않고 따라온다. 세션 생성은 **소속 테넌트**가 그 타입(생략이면 `shell`)을 허용받았을 때만 성공하고, 아니면 pod를 만들기 전에 **403**이다. 테넌트 호출자가 요청 본문의 `tenant`로 다른 테넌트를 지정해도 403이다. 운영자는 `tenant`로 소속을 지정해 생성할 수 있고(없는 테넌트면 400) 그때도 같은 허용 검사를 받는다. 운영자가 `tenant` 없이 만드는 무소속 세션은 지금처럼 배포가 내놓는 모든 타입을 쓸 수 있다. `GET /config`는 테넌트 호출자에게 `workloadTypes`를 그 테넌트 허용 목록으로 좁혀 내놓는다 — 화면이 생성에 실패할 타입을 보이지 않게 하는, AC-E1의 "이미지가 있는 타입만" 규칙과 같은 이유다. `"*"` 테넌트의 목록은 운영자와 같고, 응답 어디에도 `"*"` 자체는 나오지 않는다(`tenant`·`tenants`의 타입도 펼친 목록).
- **달성 가치**: V8
- **구체화 대상**: AC-E1(·F1·G1·J1)의 타입 선택 — 선택지를 테넌트별로 좁힌 것
- **검증 방법**: 허용되지 않은 타입·다른 테넌트로의 생성이 403이고 pod가 생기지 않으며, 테넌트의 `GET /config`가 허용 타입만 내놓음을 확인한다. `"*"` 테넌트의 `GET /config`는 배포가 내놓는 타입 전부를 내놓고, 알 수 없는 타입 생성은 여전히 400임을 확인한다.

### AC-K4: 운영자 화면과 운영자 전용 경로
- **설명**: `GET /config`는 운영자에게 `tenants`(이름과 그 테넌트가 실제로 고를 수 있는 타입)를, 테넌트 호출자에게 `tenant`(자기 자신)를 내놓는다. 운영자 SPA는 테넌트가 하나 이상 설정된 배포에서 — 세션 목록에 **테넌트 필터**(전체 · 각 테넌트 · 무소속)와 세션 카드의 **테넌트 태그**를, 새 세션 화면에 **테넌트 선택**(기본 무소속)을 보이고, 테넌트를 고르면 타입 카드를 그 테넌트의 타입으로 좁힌다. 테넌트가 없는 배포의 화면은 지금과 같다. 레포 접근 관리 API(`/api/v1/repo-access` 관리 경로, AC-H2)는 운영자 전용이다 — Bearer 헤더가 있는 호출은 검증 전에 403이다(헬퍼 파드 내부 경로 AC-H3은 그대로).
- **달성 가치**: V1, V8
- **구체화 대상**: AC-K2·K3의 운영자 측 표면, AC-H2의 문을 호출자 축으로 좁힌 것
- **검증 방법**: 테넌트가 설정된 SUT에서 운영자 화면에 필터·태그·선택이 보이고, 테넌트를 골라 만든 세션이 그 테넌트 태그를 달고 필터에 걸림을 확인한다. Bearer 호출의 레포 접근 관리 API가 403임을 확인한다.

### AC-K5: 테넌트 설정과 하위 호환
- **설명**: 테넌트 집합은 ConfigMap `session-platform-tenants`의 `tenants.json`을 control plane 환경 변수 `SESSION_PLATFORM_TENANTS`로 투영한 기동 시점 스냅숏이다(형식: `{"tenants":[{"name","serviceAccounts","workloadTypes"}]}`). 이름 형식·중복, 계정 형식·여러 테넌트의 같은 계정, 알 수 없는 타입·중복 타입, `"*"`를 다른 타입과 함께 적은 목록, 알 수 없는 필드는 **기동 실패**다 — 조용히 넓은 권한으로 뜨지 않는다. 설정이 없거나 비면 테넌트가 없다: 운영자 경로는 지금과 같고 Bearer 호출은 모두 403이다. 기존 세션은 무소속으로 남아 운영자만 본다. 토큰 검증에는 control plane ServiceAccount의 `system:auth-delegator` 바인딩이 필요하다(클러스터 범위라 base 밖 — 운영은 flux-cd-apps, kind e2e는 `deploy/overlays/e2e/e2e-tenancy.yaml`).
- **달성 가치**: V5, V1
- **구체화 대상**: AC-K1~K4의 입력
- **검증 방법**: 잘못된 설정이 기동을 실패시키고, 빈 설정에서 운영자 동작이 그대로이며 Bearer 호출이 403임을 확인한다.

## 결정 사항 (2026-11-05, 사용자)
- **테넌트 식별은 Kubernetes ServiceAccount**로 한다.
- **토큰 없는 요청은 운영자 뷰**다 — 모든 테넌트의 세션을 보고, 테넌트를 골라 거르고 만든다.

## 결정 사항 (2026-11-07, 사용자)
- **타입 제한 없는 테넌트**를 둔다 — 운영 테넌트 `homelab-k3s-mcp`가 모든 타입을 쓴다. 표기는 `"workloadTypes": ["*"]`다. 목록 생략·빈 목록을 「전부」로 읽지 않는 이유는 AC-K5와 같다: 오타나 누락이 조용히 넓은 권한이 되지 않게, 넓은 권한은 눈에 띄는 한 글자로만 준다.
- **한 테넌트에 여러 호출자** — 같은 테넌트의 `serviceAccounts`에 둘 이상을 둬 서로 다른 앱이 같은 세션 목록을 본다(운영: K3s MCP 서버와 PocketAide 세션 탭). 기존 형식 그대로다.

## 알려 둘 경계
- 운영자 경로는 "토큰이 없다"로 정해진다. control plane 앞의 NetworkPolicy(`deploy/base/network-policy.yaml`)는 traefik과 헬퍼 파드만 들이므로, 클러스터 안 테넌트 호출자가 토큰을 빼고 traefik 게이트웨이로 들어오면 운영자가 된다 — 지금의 내부 호출자 구조(AC-H2: "인그레스를 거치지 않는 호출자는 세션 API와 같은 범위")를 그대로 둔 결과다. 테넌시가 **보안 경계**가 되어야 하면 게이트웨이 경로에서 토큰을 필수로 하거나 운영자도 신원을 내게 하는 후속 결정이 필요하다.
- 세션 파드·아카이브·네임스페이스는 테넌트별로 나뉘지 않는다(모두 같은 네임스페이스). 이 PRD의 격리는 API 표면의 가시성·생성 권한이다.
