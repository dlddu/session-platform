# PRD: 세션 워크로드 — Codex SDK (codex)

> 대상 요구사항: 세션 워크로드 타입에 **Codex SDK 에이전트** 추가
> (`shell`·`claude-code`·`approval-gated`·`minimax-code`와 병존하는 다섯 번째 타입, `claude-code-workload.md`와 대응 관계)

## 달성 가치
- **V8 목적에 맞는 작업 환경 선택** — 세션 생성 시 다섯 번째 작업 환경(ChatGPT 구독으로 도는 대화형 에이전트)을 고를 수 있게 하고, 선택과 무관하게 V1~V5 보장이 동일하게 성립함을 확정 (AC-J1)
- **V3 끊김 없는 세션 연속성** — 대화 문맥·누적 출력·**세션의 ChatGPT 로그인**이 동결·복원을 건너 보존됨 (AC-J2~J4가 AC-B2/B3·AC-C2/C3 구체화)
- **V4 자유로운 멀티세션 전환** — 전환 후에도 동일한 offset 커서 규약으로 출력을 이어 읽음 (AC-J2가 AC-C2 구체화)
- **V2 유휴 자원 회수** — 다른 에이전트 타입과 같은 파일시스템 아카이브로 동결·회수 (AC-J4가 AC-B1·A3 구체화)
- **V1 세션 격리** — 에이전트가 닿을 수 있는 도구 표면을 대화·플랫폼 플러그인 스킬·K3s MCP로 좁히고(AC-J5), 플랫폼 자격 증명을 에이전트가 도는 컨테이너 밖에 둠 (AC-J6이 AC-A1/A2 구체화)

> 📌 **가치 연결 규칙**: 다른 타입 PRD와 동일하게, 각 AC의 달성 가치는 자신이 구체화하는 상위 AC의 가치를 상속한다.
> **AC-J1(타입 선택)만 예외**로 추상 가치 **V8**에 직접 연결한다 — AC-E1·AC-F1·AC-G1과 같은 이유이며, `../values.md`는 변하지 않는다.

> 이 PRD는 **"같은 실행 모델 위에서 CLI와 로그인 방식, 도구 표면만 바꾼다"** 는 성질을 못박는다.
> 실행 모델(원샷 프롬프트·직렬 큐·커서 규약·대화 연속성·아카이브)은 `claude-code`와 같으므로 **AC-E2~E5를 참조**하고,
> 이 문서는 그 위에 얹히는 차이만 적는다. 차이는 다섯이다 — 실행하는 러너(Codex SDK)와 출력 투영(AC-J2),
> 세션마다 하는 ChatGPT 로그인과 그 보존(AC-J3), 아카이브 게이트(AC-J4), 도구 표면(AC-J5), K3s MCP 토큰의 배치(AC-J6).
> `approval-gated`·`minimax-code`와 달리 **헬퍼 파드도 승인 게이트도 없다** — 셸·파일·네트워크 도구 자체가 없으므로
> 게이트가 지킬 경로가 K3s MCP 하나뿐이고, K3s MCP는 자기 쓰기를 스스로 게이트한다(AC-G5와 같은 판단).

## Acceptance Criteria

### AC-J1: 워크로드 타입 `codex` 선택
- **설명**: 세션 생성 요청의 `workloadType` 허용값에 `codex`가 추가된다. 필드 생략만 `shell`로 해석하는 규칙, 허용값 밖 입력을 pod 생성 전에 400으로 거부하는 규칙, 타입 불변 규칙은 AC-E1과 같다. control plane은 이 타입에 대해 **워크로드 파드 하나**를 띄운다 — 주 컨테이너(Codex 러너)와 loopback K3s MCP 프록시 사이드카(AC-J6). 보조 파드는 없다. 이미지는 control plane 설정 `DATA_PLANE_CODEX_IMAGE`이고, 비어 있으면 `GET /config`가 이 타입을 내놓지 않고 생성은 pod 없이 실패한다(AC-E1과 같은 규칙). `model`은 AC-E6의 계약을 따른다 — 생략은 `platform-default`이며 이때 파드는 ConfigMap `codex-config`의 선택 `model` 키를 `CODEX_MODEL`로 받고, 키가 없으면 Codex가 로그인한 플랜의 기본 모델을 쓴다. UI 모델 카탈로그는 같은 ConfigMap의 `models`(control plane `CODEX_MODELS`)다.
- **달성 가치**: V8, V1
- **구체화 대상**: AC-A1의 "실제 세션 워크로드" — 다섯 갈래로 분기한다 (… AC-G2~G6=`minimax-code`, AC-J2~J6=`codex`)
- **검증 방법**: `workloadType=codex`로 세션을 생성하면 컨테이너 둘(주 컨테이너 + `k3s-mcp-proxy`)의 워크로드 파드 하나만 기동되고 조회 응답의 타입·모델이 기대값임을 확인한다. 이미지 미설정 배포에서는 `GET /config`에 타입이 없고 생성이 pod 없이 실패함을 확인한다.

### AC-J2: write = Codex SDK 턴 1회, read = 에이전트 메시지 텍스트
- **설명**: 큐·바운드·커서·대화 연속성은 AC-E2~E4를 그대로 따른다(1 MiB 프롬프트 413, 큐 429, 실행당 16 MiB·세션 256 MiB 출력 한도). 한 번의 실행은 이미지에 고정 버전으로 들어 있는 `@openai/codex-sdk` 러너 1회다:

  ```
  codex-runner --model <모델|platform-default> [--resume] -- "<payload>"
  ```

  러너는 SDK로 스레드를 시작하거나(첫 실행) 저장된 스레드 id로 재개하고(`--resume`, AC-E4와 같이 첫 **성공** 이후에만), `runStreamed`의 이벤트를 한 줄에 하나씩 JSON으로 내보낸다. 스레드 옵션은 고정이다 — `sandboxMode: read-only`, `approvalPolicy: never`, `webSearchMode: disabled`, `networkAccessEnabled: false`, `skipGitRepoCheck: true`. 에이전트는 이 투영으로 read를 만든다: 완료된 에이전트 메시지 텍스트, K3s MCP 도구 호출의 시작 한 줄과 실패 한 줄, 턴 실패·오류 한 줄, 그리고 플랫폼 안내(AC-J3). 추론 텍스트·할 일 목록은 투영하지 않는다. `--` 뒤 payload는 옵션이 아닌 단일 positional argv다.
- **달성 가치**: V3, V4
- **구체화 대상**: AC-C2(read)·AC-C3(write) — AC-E2/E3의 투영 규칙을 Codex SDK 이벤트 형식에 맞춘 것
- **검증 방법**: 첫 write의 argv에 `--resume`이 없고 성공 후에는 있음을, `--`로 시작하는 프롬프트가 옵션으로 해석되지 않음을 확인한다. 이벤트 종류별 투영(에이전트 메시지·도구 호출·실패·안내)과 잘못된 줄·과대 줄·끊긴 마지막 줄 처리를 확인한다.

### AC-J3: 세션마다 ChatGPT 로그인(device code), 로그인은 세션 상태의 일부
- **설명**: 플랫폼은 공급자 자격 증명을 갖지 않는다. 세션은 **첫 프롬프트**에서 로그인 상태를 확인하고, 로그인되어 있지 않으면 `codex login --device-auth`를 실행해 그 **확인 주소와 일회용 코드**를 플랫폼 안내 줄로 세션 출력에 내보낸다. 사용자가 브라우저에서 그 주소를 열어 코드를 넣고 승인하면 같은 턴이 이어서 실행된다. 로그인 실패·만료는 그 턴만 실패시키고 다음 프롬프트가 다시 로그인을 시도한다. 로그인 결과(`$HOME/.codex/auth.json`)는 세션 HOME, 즉 **아카이브 대상 상태 트리 안**에 둔다 — 동결·복원 후에도 다시 로그인하지 않는다(2026-11-05 사용자 결정). 로그인 방식은 ChatGPT로 고정한다(`forced_login_method = "chatgpt"`) — API 키 로그인은 이 타입의 경로가 아니다. 자격 증명은 파일에만 둔다(`cli_auth_credentials_store = "file"`); 파드에 OS 키링이 없고, 키링에 두면 아카이브가 로그인을 잃는다. 주 컨테이너에 Codex·OpenAI 자격 증명 환경 변수가 있으면 에이전트가 기동을 거부한다 — 세션 밖에서 주입된 계정이 세션 로그인을 대신하지 않게 한다.
- **달성 가치**: V3, V1
- **구체화 대상**: AC-E4(대화 연속성)를 로그인 상태까지 넓힌 것, AC-A1의 격리 — 세션의 로그인은 그 세션 파드와 그 아카이브에만 있다
- **검증 방법**: 로그인되지 않은 세션의 첫 write 출력에 확인 주소와 코드가 안내 줄로 나타남을 확인한다. 로그인 후 동결→복원한 세션의 다음 write가 로그인 안내 없이 실행됨을 확인한다. 자격 증명 환경 변수가 있는 주 컨테이너가 기동을 거부함을 확인한다.

### AC-J4: 파일시스템 아카이브, 전용 게이트
- **설명**: 동결·복원은 AC-E5의 파일시스템 아카이브를 그대로 쓴다 — 작업 디렉터리·HOME(`~/.codex`의 스레드 기록과 **로그인**, AC-J3)·누적 출력 버퍼, generation 펜스, 복원 후 커서 연속성. 플랫폼 관리 파일(`~/.codex/config.toml`, 플러그인 스킬)은 부팅과 복원마다 그 파드의 설정으로 다시 쓴다 — 아카이브가 옛 설정을 되살리지 못한다. 외부 스토리지 전송은 **이 타입 전용 게이트** `CODEX_ARCHIVE_ENABLED`(기본 off) 뒤에 둔다 — 이 타입의 아카이브는 사용자의 ChatGPT 로그인을 담으므로, 켜는 것은 그 로그인을 아카이브 저장소에 두기로 하는 결정이다. 게이트 off에서 동결은 거부되고 파드는 남는다.
- **달성 가치**: V2, V3
- **구체화 대상**: AC-B1(동결)·AC-B2(복원)·AC-B3(무결성)
- **검증 방법**: 게이트 on에서 동결→복원 후 타입·모델·출력·커서와 `~/.codex/auth.json`이 보존되고, 관리형 `config.toml`이 복원 파드의 것으로 다시 쓰임을 확인한다. 게이트 off에서 동결이 거부되고 파드가 남음을 확인한다.

### AC-J5: 도구 표면 — 대화, 플랫폼 플러그인 스킬, K3s MCP뿐
- **설명**: 이 타입의 에이전트가 쓸 수 있는 것은 셋뿐이다 (2026-11-05 사용자 결정).
  1. **대화** — 모델 응답.
  2. **플러그인으로 연결된 스킬** — K3s MCP 프록시 사이드카가 마켓플레이스에서 받아 온 플랫폼 플러그인(`CODEX_PLUGINS`, 기본 `codex-session` — 이 타입의 표면에서 동작하는 스킬만 모은 마켓플레이스 전용 번들, 2026-11-05 사용자 결정)의 스킬만 — 플러그인 매니페스트의 `skills` 필드가 가리키는 디렉터리, 없으면 `skills/<이름>/` — `$HOME/.agents/skills/<플러그인>--<스킬>/`에 관리 표식과 함께 설치한다. `read_skill`은 디렉터리 이름과 SKILL.md 머리말의 이름 둘 다로 찾는다(Codex가 머리말 이름으로 목록을 보이므로). 셸이 없으므로 모델은 SKILL.md를 파일로 열 수 없다 — 대신 에이전트 바이너리가 stdio MCP 서버 `skills`(`list_skills`·`read_skill`)로 그 디렉터리 안의 일반 파일만, 크기 상한 안에서 읽어 준다. 관리형 설정의 개발자 지시가 스킬은 `read_skill`로 읽으라고 알린다. 사용자가 손으로 둔 스킬(표식 없음)은 동기화가 지우지 않는다.
  3. **K3s MCP** — AC-J6의 사이드카를 거친다. 프록시가 토큰을 갖지 않으면 등록하지 않는다.

  그 밖은 모두 끈다 — 관리형 `~/.codex/config.toml`이 셸(`shell_tool`·`unified_exec`), 이미지 보기·생성, 앱·Codex 자체 플러그인·원격 플러그인, 브라우저·컴퓨터 사용, 메모리·훅·목표·도구 제안·스킬의 MCP 자동 설치, 번들 시스템 스킬을 끄고, 웹 검색을 `disabled`로 둔다. 원격 모델 카탈로그가 강제하는 코드 모드 안의 `apply_patch`와 하위 에이전트 도구는 설정으로 끌 수 없어(Codex 0.166.0에서 확인), 파일 쓰기는 `sandbox_mode = "read-only"` + `approval_policy = "never"`가 막고, 러너가 **킬 스위치**로 한 번 더 막는다 — 턴 중 `command_execution`·`file_change`·`web_search` 아이템이 하나라도 나타나면 안내 한 줄을 남기고 턴을 즉시 중단한다. 이미지 빌드는 관리형 설정으로 `codex debug prompt-input`을 렌더해 셸·이미지 도구·번들 스킬이 모델에 보이면 실패한다 — Codex 버전을 올려 표면이 넓어지면 이미지가 나가지 않는다.
- **달성 가치**: V1
- **구체화 대상**: AC-A1의 격리 — 세션이 자기 파드 밖에 닿는 경로를 도구 수준에서 좁힌 것
- **검증 방법**: 관리형 설정으로 렌더한 모델 도구 목록에 `exec_command`·`write_stdin`·`view_image`와 번들 스킬이 없음을 확인한다(이미지 빌드 검사 + 배포 파드 안 실측). 스킬 동기화(표식·오래된 관리 스킬 제거·사용자 스킬 보존)와 `read_skill`의 경로 경계·크기 상한을 확인한다. 금지 아이템 이벤트가 오면 러너가 턴을 중단함을 확인한다.

### AC-J6: K3s MCP 토큰은 loopback 사이드카에만
- **설명**: 선택 `k3s-mcp-token`은 Secret `codex-credentials`(control plane `CODEX_CREDENTIALS_SECRET`)에 두고, 세션 파드의 `k3s-mcp-proxy` 사이드카에만 투영한다. 사이드카는 `minimax-code`의 K3s MCP 프록시(AC-G5)를 헬퍼 파드 대신 **같은 파드의 loopback**(`127.0.0.1:8093`)에 띄운 것이다 — 같은 헤더 허용 목록, 같은 쓰기·exec·세션 도구 차단, 같은 마켓플레이스 시드. 주 컨테이너는 그 주소만 받고 Secret 참조를 하나도 갖지 않는다. 워크로드 파드는 Kubernetes API 자격 증명도 받지 않는다(`automountServiceAccountToken: false`) — 다른 에이전트 타입은 셸로 클러스터를 조회하지만 이 타입에는 그 도구가 없다. Secret·ConfigMap 이름은 다른 에이전트 타입과 겹치면 control plane이 기동을 거부한다(키 이름이 같아 겹치면 다른 타입의 토큰이 조용히 넘어온다).
- **달성 가치**: V1
- **구체화 대상**: AC-A1/A2의 세션 격리 — AC-G5의 토큰 배치를 헬퍼 파드 없는 파드에 옮긴 것
- **검증 방법**: 제출된 pod spec에서 주 컨테이너에 Secret 참조가 없고 `K3S_MCP_PROXY_URL`이 loopback이며, 사이드카만 이 타입 Secret의 선택 `k3s-mcp-token`을 읽고, 파드의 `automountServiceAccountToken`이 false임을 확인한다.

## 결정 사항 (2026-11-05, 사용자)
- **SDK 기반**: 러너는 `@openai/codex-sdk`(고정 버전)로 스레드를 시작·재개한다. CLI 직접 호출이 아니다.
- **로그인 단위는 세션**: 플랫폼 공용 계정·테넌트별 계정을 두지 않는다. ChatGPT의 refresh token이 사용 중 갱신되는 구조라 계정 하나를 여러 파드에 복사하면 서로를 무효화할 수 있다 — 세션 단위 로그인은 그 공유 자체를 없앤다.
- **로그인은 아카이브에 포함**: 복원 후 다시 로그인하지 않는다. 대신 이 타입의 아카이브 게이트를 따로 둔다(AC-J4).
- **도구 표면**: 대화 · 플러그인 스킬 · K3s MCP만 (AC-J5). 세션 MCP(파일·git·drop)는 주지 않는다.
