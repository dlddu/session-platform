# PRD: 세션 워크로드 — Codex 채팅용 (codex-chat)

> 대상 요구사항: 세션 워크로드 타입에 **Codex SDK 에이전트** 추가
> (`shell`·`claude-code`·`minimax-code`와 병존하는 타입 — 신설 당시는 `approval-gated`(2026-11-05 제거)까지 다섯 번째였다, `claude-code-workload.md`와 대응 관계)

> 📌 **개정 (2026-11-07, 사용자 결정)**: Codex를 채팅용과 작업용으로 나눴다. 이 문서의 타입은 **채팅용 `codex-chat`** 이다 — 장기 단일 세션을 가정하고 도구를 대화·스킬·K3s MCP로 좁힌 그대로다. 타입 이름이 `codex`에서 `codex-chat`으로 바뀌었고 옛 이름은 저장된 레코드에서만 읽는다(AC-J1). 작업용 `codex-task`(셸·파일·네트워크, 인증 풀 로그인)는 `codex-task-workload.md`다. 아래 본문의 「`codex` 타입」·「`codex` 세션」은 `codex-chat`으로 읽는다. 설정 이름(`DATA_PLANE_CODEX_IMAGE`·`CODEX_*`·`codex-config`·`codex-credentials`)은 바꾸지 않았다.

> 📌 **개정 (2026-11-09, 사용자 결정)**: 이 타입도 **슬롯 풀**(`agent-auth-pool.md` AC-N6, 풀 `codex-chat`)을 쓴다. 슬롯 PVC에 ChatGPT 로그인과 **세션 DB**(SQLite)를 함께 두고, 사이드카가 세션 DB를 MCP(`raw_query`·`raw_exec`)로 내놓는다. 로그인은 아카이브가 아니라 슬롯에 남는다(AC-J3·J4), 도구 표면에 세션 DB가 더해진다(AC-J5).

> 📌 **2026-11-09 (AC-P1~P3)**: 도구 표면(AC-J5)에 사이드카의 **스케줄러 MCP**(`scheduler` — 한 번·고정 루프·자체 페이싱 예약)가 더해진다. 회차는 이 세션 에이전트의 큐로 들어가고, 예약이 남은 동안은 유휴 회수가 미뤄진다(`session-scheduler.md`).

> 📌 **개정 (2026-11-13, 사용자 결정)**: 러너가 Codex SDK(`codex exec`) 대신 **`codex app-server`** 를 구동한다(AC-J2). exec는 메인 스레드의 턴이 끝나면 Codex를 내려, 그 턴이 띄운 하위 에이전트까지 죽인다 — 하위 에이전트를 백그라운드로 돌릴 수 없었다. 이제 러너는 메인 턴이 끝난 뒤에도 하위 에이전트가 끝나기를 기다리고, 결과를 후속 턴으로 메인 에이전트에 넘긴다(AC-J8). 출력 형식과 도구 표면은 그대로다. 킬 스위치는 하위 에이전트의 아이템까지 본다(AC-J5).

## 달성 가치
- **V8 목적에 맞는 작업 환경 선택** — 세션 생성 시 다섯 번째 작업 환경(ChatGPT 구독으로 도는 대화형 에이전트)을 고를 수 있게 하고, 선택과 무관하게 V1~V5 보장이 동일하게 성립함을 확정 (AC-J1)
- **V3 끊김 없는 세션 연속성** — 대화 문맥·누적 출력·**ChatGPT 로그인**·**세션 DB**가 동결·복원을 건너 보존됨 (로그인·세션 DB는 슬롯, AC-N6) (AC-J2~J4가 AC-B2/B3·AC-C2/C3 구체화)
- **V4 자유로운 멀티세션 전환** — 전환 후에도 동일한 offset 커서 규약으로 출력을 이어 읽음 (AC-J2가 AC-C2 구체화)
- **V2 유휴 자원 회수** — 다른 에이전트 타입과 같은 파일시스템 아카이브로 동결·회수 (AC-J4가 AC-B1·A3 구체화)
- **V3 끊김 없는 세션 연속성(하위 에이전트)** — 턴이 띄운 하위 에이전트가 답 뒤에도 마저 돌고, 그 결과가 같은 대화로 돌아옴 (AC-J8이 AC-E2의 「턴의 백그라운드 작업은 그 턴 안에서 끝낸다」를 구체화)
- **V3 끊김 없는 세션 연속성(장기 세션)** — 오래 쓰는 세션이 대화를 끊지 않고 바뀐 플랫폼 스킬을 받아 옴 (AC-J7이 AC-J5의 스킬 동기화와 AC-E4의 대화 연속성을 함께 구체화)
- **V1 세션 격리** — 에이전트가 닿을 수 있는 도구 표면을 대화·플랫폼 플러그인 스킬·K3s MCP로 좁히고(AC-J5), 플랫폼 자격 증명을 에이전트가 도는 컨테이너 밖에 둠 (AC-J6이 AC-A1/A2 구체화)

> 📌 **가치 연결 규칙**: 다른 타입 PRD와 동일하게, 각 AC의 달성 가치는 자신이 구체화하는 상위 AC의 가치를 상속한다.
> **AC-J1(타입 선택)만 예외**로 추상 가치 **V8**에 직접 연결한다 — AC-E1·AC-F1·AC-G1과 같은 이유이며, `../values.md`는 변하지 않는다.

> 이 PRD는 **"같은 실행 모델 위에서 CLI와 로그인 방식, 도구 표면만 바꾼다"** 는 성질을 못박는다.
> 실행 모델(원샷 프롬프트·직렬 큐·커서 규약·대화 연속성·아카이브)은 `claude-code`와 같으므로 **AC-E2~E5를 참조**하고,
> 이 문서는 그 위에 얹히는 차이만 적는다. 차이는 다섯이다 — 실행하는 러너(Codex app server)와 출력 투영(AC-J2, 하위 에이전트 대기 AC-J8),
> 세션마다 하는 ChatGPT 로그인과 그 보존(AC-J3), 아카이브 게이트(AC-J4), 도구 표면(AC-J5), K3s MCP 토큰의 배치(AC-J6).
> 승인 게이트를 쓰는 `minimax-code`(`approval-gate.md` 「적용 타입」)와 달리 **헬퍼 파드도 승인 게이트도 없다** — 셸·파일·네트워크 도구 자체가 없으므로
> 게이트가 지킬 경로가 K3s MCP 하나뿐이고, K3s MCP는 자기 쓰기를 스스로 게이트한다(AC-G5와 같은 판단).

## Acceptance Criteria

### AC-J1: 워크로드 타입 `codex-chat` 선택 (옛 이름 `codex`)
- **설명**: 세션 생성 요청의 `workloadType` 허용값에 `codex-chat`이 추가된다. 옛 이름 `codex`는 **저장된 세션 레코드에서만** `codex-chat`으로 읽는다 — 이름 변경 전에 만든 세션의 목록·조회·복원이 깨지지 않게 하고, 다음 쓰기가 새 이름으로 저장한다. 생성 요청과 테넌트의 `workloadTypes`에서 `codex`는 모르는 타입이다(생성 400, 테넌트 설정은 기동 실패). 응답·`GET /config`·파드 라벨·`DATA_PLANE_WORKLOAD`는 언제나 `codex-chat`을 쓴다. *2026-11-07*: 처음엔 생성 요청·테넌트 설정에서도 별칭으로 받았으나, 호출하는 쪽(pocket-aide #395, homelab-k3s-mcp #321, flux-cd-apps #115)이 모두 새 이름으로 옮겨 걷었다(사용자 결정). 이 타입은 모델만 받고 `reasoningEffort`는 받지 않는다(AC-E8). 필드 생략만 `shell`로 해석하는 규칙, 허용값 밖 입력을 pod 생성 전에 400으로 거부하는 규칙, 타입 불변 규칙은 AC-E1과 같다. control plane은 이 타입에 대해 **워크로드 파드 하나**를 띄운다 — 주 컨테이너(Codex 러너)와 loopback K3s MCP 프록시 사이드카(AC-J6). 보조 파드는 없다. 이미지는 control plane 설정 `DATA_PLANE_CODEX_IMAGE`이고, 비어 있거나 슬롯 풀 크기(`CODEX_CHAT_AUTH_SLOTS`, `agent-auth-pool.md` AC-N6)가 0이면 `GET /config`가 이 타입을 내놓지 않고 생성은 pod 없이 실패한다(AC-E1과 같은 규칙, *2026-11-09* 슬롯 조건 추가). 파드는 그 슬롯 PVC를 함께 마운트한다(AC-J3·AC-N6). `model`은 AC-E6의 계약을 따른다 — 생략은 `platform-default`이며 이때 파드는 ConfigMap `codex-config`의 선택 `model` 키를 `CODEX_MODEL`로 받고, 키가 없으면 Codex가 로그인한 플랜의 기본 모델을 쓴다. UI 모델 카탈로그는 같은 ConfigMap의 `models`(control plane `CODEX_MODELS`)다.
- **달성 가치**: V8, V1
- **구체화 대상**: AC-A1의 "실제 세션 워크로드" — 다섯 갈래로 분기한다 (… AC-G2~G6=`minimax-code`, AC-J2~J6=`codex`)
- **검증 방법**: `workloadType=codex`로 세션을 생성하면 컨테이너 둘(주 컨테이너 + `k3s-mcp-proxy`)의 워크로드 파드 하나만 기동되고 조회 응답의 타입·모델이 기대값임을 확인한다. 이미지 미설정 배포에서는 `GET /config`에 타입이 없고 생성이 pod 없이 실패함을 확인한다.

### AC-J2: write = Codex 턴 1회, read = 에이전트 메시지 텍스트
- **설명**: 큐·바운드·커서·대화 연속성은 AC-E2~E4를 그대로 따른다(1 MiB 프롬프트 413, 큐 429, 실행당 16 MiB·세션 256 MiB 출력 한도). 한 번의 실행은 이미지에 고정 버전으로 들어 있는 `@openai/codex` 바이너리의 `codex app-server`를 구동하는 러너 1회다:

  ```
  codex-runner --model <모델|platform-default> [--resume] -- "<payload>"
  ```

  러너는 app server(stdio JSON-RPC)로 스레드를 시작하거나(첫 실행) 저장된 스레드 id로 재개하고(`--resume`, AC-E4와 같이 첫 **성공** 이후에만), 메인 스레드의 알림을 `codex exec`가 내던 이벤트 형식으로 한 줄에 하나씩 JSON으로 내보낸다. 설정은 고정이다 — 샌드박스 `read-only`, 승인 정책 `never`, 웹 검색 `disabled`, 샌드박스 네트워크 꺼짐. app server가 러너에 묻는 요청은 `codex exec`처럼 답한다 — MCP 도구의 사용자 확인(elicitation)은 비대화형으로 취소하고, 승인·사용자 입력 요청은 거절한다. *2026-11-13 개정*: 처음엔 `@openai/codex-sdk`의 `runStreamed`(속은 `codex exec`)였다 — 바꾼 이유는 AC-J8. 에이전트는 이 투영으로 read를 만든다: 완료된 에이전트 메시지 텍스트, K3s MCP 도구 호출의 시작 한 줄과 실패 한 줄, 턴 실패·오류 한 줄, 그리고 플랫폼 안내(AC-J3). 추론 텍스트·할 일 목록은 투영하지 않는다. `--` 뒤 payload는 옵션이 아닌 단일 positional argv다.
- **달성 가치**: V3, V4
- **구체화 대상**: AC-C2(read)·AC-C3(write) — AC-E2/E3의 투영 규칙을 Codex 이벤트 형식에 맞춘 것
- **검증 방법**: 첫 write의 argv에 `--resume`이 없고 성공 후에는 있음을, `--`로 시작하는 프롬프트가 옵션으로 해석되지 않음을 확인한다. 이벤트 종류별 투영(에이전트 메시지·도구 호출·실패·안내)과 잘못된 줄·과대 줄·끊긴 마지막 줄 처리를 확인한다.

### AC-J3: ChatGPT 로그인(device code), 로그인은 슬롯에 남는다
- **설명**: 플랫폼은 공급자 자격 증명을 갖지 않는다. 세션은 **첫 프롬프트**에서 로그인 상태를 확인하고, 로그인되어 있지 않으면 `codex login --device-auth`를 실행해 그 **확인 주소와 일회용 코드**를 플랫폼 안내 줄로 세션 출력에 내보낸다. 사용자가 브라우저에서 그 주소를 열어 코드를 넣고 승인하면 같은 턴이 이어서 실행된다. 로그인 실패·만료는 그 턴만 실패시키고 다음 프롬프트가 다시 로그인을 시도한다. 로그인 결과(`$HOME/.codex/auth.json`)는 세션이 임대한 **슬롯**(`agent-auth-pool.md` AC-N4·AC-N6, 슬롯의 `auth/auth.json`)에 복사로 남고 아카이브에서 빠진다 — 동결·복원 후에도, 같은 슬롯을 받은 다음 세션도 다시 로그인하지 않는다. *2026-11-09 개정*: 처음엔 세션 HOME, 즉 아카이브 대상 상태 트리 안에 두었다(2026-11-05 사용자 결정). 세션 DB를 둘 PVC가 필요해지며 로그인도 슬롯으로 옮겼고, 그 전에 만든 세션은 첫 프롬프트에서 다시 로그인한다(사용자 결정). 로그인 방식은 ChatGPT로 고정한다(`forced_login_method = "chatgpt"`) — API 키 로그인은 이 타입의 경로가 아니다. 자격 증명은 파일에만 둔다(`cli_auth_credentials_store = "file"`); 파드에 OS 키링이 없고, 키링에 두면 슬롯 동기화가 로그인을 잃는다. 주 컨테이너에 Codex·OpenAI 자격 증명 환경 변수가 있으면 에이전트가 기동을 거부한다 — 세션 밖에서 주입된 계정이 세션 로그인을 대신하지 않게 한다.
- **달성 가치**: V3, V1
- **구체화 대상**: AC-E4(대화 연속성)를 로그인 상태까지 넓힌 것, AC-A1의 격리 — 로그인은 그 슬롯을 임대한 파드에만 있다(AC-N2)
- **검증 방법**: 로그인되지 않은 세션의 첫 write 출력에 확인 주소와 코드가 안내 줄로 나타남을 확인한다. 로그인 후 동결→복원한 세션의 다음 write가 로그인 안내 없이 실행됨을 확인한다. 슬롯 없이 기동한 `codex-chat` 에이전트가 거부됨을 확인한다. 자격 증명 환경 변수가 있는 주 컨테이너가 기동을 거부함을 확인한다.

### AC-J4: 파일시스템 아카이브, 전용 게이트
- **설명**: 동결·복원은 AC-E5의 파일시스템 아카이브를 그대로 쓴다 — 작업 디렉터리·HOME(`~/.codex`의 스레드 기록)·누적 출력 버퍼, generation 펜스, 복원 후 커서 연속성. 로그인(`~/.codex/auth.json`)은 슬롯의 것이라 아카이브에서 빠지고(AC-N4), 세션 DB는 슬롯에 있어 아카이브와 무관하게 남는다(AC-N6). 플랫폼 관리 파일(`~/.codex/config.toml`, 플러그인 스킬)은 부팅과 복원마다 그 파드의 설정으로 다시 쓴다 — 아카이브가 옛 설정을 되살리지 못한다. 외부 스토리지 전송은 **이 타입 전용 게이트** `CODEX_ARCHIVE_ENABLED`(기본 off) 뒤에 둔다 — 처음엔 아카이브가 로그인을 담아서였고(2026-11-09 전), 지금은 대화 기록을 아카이브 저장소에 두는 결정이다. 게이트 off에서 동결은 거부되고 파드는 남는다.
- **달성 가치**: V2, V3
- **구체화 대상**: AC-B1(동결)·AC-B2(복원)·AC-B3(무결성)
- **검증 방법**: 게이트 on에서 동결→복원 후 타입·모델·출력·커서가 보존되고, 아카이브에 `~/.codex/auth.json`이 없으며, 관리형 `config.toml`이 복원 파드의 것으로 다시 쓰임을 확인한다. 게이트 off에서 동결이 거부되고 파드가 남음을 확인한다.

### AC-J5: 도구 표면 — 대화, 플랫폼 플러그인 스킬, K3s MCP, 세션 DB뿐
- **설명**: 이 타입의 에이전트가 쓸 수 있는 것은 넷뿐이다 (2026-11-05 사용자 결정, 4는 2026-11-09).
  1. **대화** — 모델 응답.
  2. **플러그인으로 연결된 스킬** — K3s MCP 프록시 사이드카가 마켓플레이스에서 받아 온 플랫폼 플러그인(`CODEX_PLUGINS`, 기본 `codex-session` — 이 타입의 표면에서 동작하는 스킬만 모은 마켓플레이스 전용 번들, 2026-11-05 사용자 결정)의 스킬만 — 플러그인 매니페스트의 `skills` 필드가 가리키는 디렉터리, 없으면 `skills/<이름>/` — `$HOME/.agents/skills/<플러그인>--<스킬>/`에 관리 표식과 함께 설치한다. `read_skill`은 디렉터리 이름과 SKILL.md 머리말의 이름 둘 다로 찾는다(Codex가 머리말 이름으로 목록을 보이므로). 셸이 없으므로 모델은 SKILL.md를 파일로 열 수 없다 — 대신 에이전트 바이너리가 stdio MCP 서버 `skills`(`list_skills`·`read_skill`)로 그 디렉터리 안의 일반 파일만, 크기 상한 안에서 읽어 준다. 마켓플레이스가 있는 파드에서는 같은 서버가 `refresh_skills`도 낸다(AC-J7 턴 안 새로고침). 플랫폼은 개발자 지시를 넣지 않는다 — 모델은 `skills` MCP의 도구 설명으로 `read_skill`을 안다(*2026-11-14 개정*). 사용자가 손으로 둔 스킬(표식 없음)은 동기화가 지우지 않는다.
  3. **K3s MCP** — AC-J6의 사이드카를 거친다. 프록시가 토큰을 갖지 않으면 등록하지 않는다.
  4. **세션 DB** — 사이드카가 슬롯의 `db/`에서 서빙하는 SQLite MCP(`agent-auth-pool.md` AC-N6)를 `db` 서버로 등록한다(`raw_query`·`raw_exec`·`ledger_get/list/put/delete`). 주 컨테이너가 `SESSION_DB_MCP_URL`(loopback 주소만 받는다)을 받았을 때만 등록한다. DB 도구는 그 서버의 도구 설명이 알린다(*2026-11-14 개정*: 개발자 지시 제거). 파드 밖에 닿는 새 경로는 없다 — DB 파일은 그 세션의 슬롯에 있다.

  그 밖은 모두 끈다 — 관리형 `~/.codex/config.toml`이 셸(`shell_tool`·`unified_exec`), 이미지 보기·생성, 앱·Codex 자체 플러그인·원격 플러그인, 브라우저·컴퓨터 사용, 메모리·훅·목표·도구 제안·스킬의 MCP 자동 설치, 번들 시스템 스킬을 끄고, 웹 검색을 `disabled`로 둔다. 원격 모델 카탈로그가 강제하는 코드 모드 안의 `apply_patch`와 하위 에이전트 도구는 설정으로 끌 수 없어(Codex 0.166.0에서 확인), 파일 쓰기는 `sandbox_mode = "read-only"` + `approval_policy = "never"`가 막고, 러너가 **킬 스위치**로 한 번 더 막는다 — 턴 중 `command_execution`·`file_change`·`web_search` 아이템이 하나라도 나타나면 안내 한 줄을 남기고 턴을 즉시 중단한다. 하위 에이전트는 막지 않는다(AC-J8) — 메인 에이전트와 같은 관리형 설정·샌드박스로 돌며, 킬 스위치는 하위 에이전트 스레드의 아이템에도 걸린다(*2026-11-13*: `codex exec`는 메인 스레드 이벤트만 보여 줘서 그 전에는 하위 에이전트의 아이템이 킬 스위치에 닿지 않았다). 이미지 빌드는 관리형 설정으로 `codex debug prompt-input`을 렌더해 셸·이미지 도구·번들 스킬이 모델에 보이면 실패한다 — Codex 버전을 올려 표면이 넓어지면 이미지가 나가지 않는다.
- **달성 가치**: V1
- **구체화 대상**: AC-A1의 격리 — 세션이 자기 파드 밖에 닿는 경로를 도구 수준에서 좁힌 것
- **검증 방법**: 관리형 설정으로 렌더한 모델 도구 목록에 `exec_command`·`write_stdin`·`view_image`와 번들 스킬이 없음을 확인한다(이미지 빌드 검사 + 배포 파드 안 실측). 스킬 동기화(표식·오래된 관리 스킬 제거·사용자 스킬 보존)와 `read_skill`의 경로 경계·크기 상한을 확인한다. 금지 아이템 이벤트가 오면 러너가 턴을 중단함을 확인한다.

> 📌 **2026-11-07 (AC-L1)**: 배포의 `CODEX_PLUGINS`는 이제 **타입 기본값**이다 — 세션이 생성 시 `plugins`를 고르면 사이드카 시더는 그 목록을 받는다(`session-plugins.md`).

### AC-J6: K3s MCP 토큰은 loopback 사이드카에만
- **설명**: 선택 `k3s-mcp-token`은 Secret `codex-credentials`(control plane `CODEX_CREDENTIALS_SECRET`)에 두고, 세션 파드의 `k3s-mcp-proxy` 사이드카에만 투영한다. 사이드카는 같은 포트의 `/session-db/mcp`에서 세션 DB도 서빙한다(AC-J5 4, AC-N6) — 그 경로만 가로채고 나머지 요청은 그대로 K3s MCP로 넘긴다. 사이드카는 `minimax-code`의 K3s MCP 프록시(AC-G5)를 헬퍼 파드 대신 **같은 파드의 loopback**(`127.0.0.1:8093`)에 띄운 것이다 — 같은 헤더 허용 목록, 같은 마켓플레이스 시드. 단 **도구 거부 목록은 걸지 않는다**(2026-11-06 사용자 결정): 사이드카가 도구 정책 `K3S_MCP_TOOL_POLICY=allow-all`을 받아 쓰기·exec·`session_*`·`opensearch_*`를 포함한 K3s MCP 도구 전부를 그대로 넘긴다. 정책 값은 `allow-all`·`deny-list` 둘이고, 비었거나 모르는 값은 `deny-list`다(다른 타입은 이 env 없이 `deny-list`). 쓰기는 K3s MCP 자체의 승인 게이트가 막는다. 주 컨테이너는 그 주소만 받고 Secret 참조를 하나도 갖지 않는다. 워크로드 파드는 Kubernetes API 자격 증명도 받지 않는다(`automountServiceAccountToken: false`) — 다른 에이전트 타입은 셸로 클러스터를 조회하지만 이 타입에는 그 도구가 없다. Secret·ConfigMap 이름은 다른 에이전트 타입과 겹치면 control plane이 기동을 거부한다(키 이름이 같아 겹치면 다른 타입의 토큰이 조용히 넘어온다).
- **달성 가치**: V1
- **구체화 대상**: AC-A1/A2의 세션 격리 — AC-G5의 토큰 배치를 헬퍼 파드 없는 파드에 옮긴 것
- **검증 방법**: 제출된 pod spec에서 주 컨테이너에 Secret 참조가 없고 `K3S_MCP_PROXY_URL`이 loopback이며, 사이드카만 이 타입 Secret의 선택 `k3s-mcp-token`을 읽고, 사이드카가 `K3S_MCP_TOOL_POLICY=allow-all`을 받으며, 파드의 `automountServiceAccountToken`이 false임을 확인한다. 정책이 정확히 `allow-all`일 때만 거부 목록이 빠지고 빈 값·`deny-list`·모르는 값이면 그대로임을 프록시 단위 테스트로 확인한다.

### AC-J7: 수동 플러그인 새로고침 — 대화를 유지한 채 스킬을 다시 받는다
- **설명**: 사이드카는 마켓플레이스를 파드가 뜰 때 한 번 받고, 스스로 다시 받지 않는다 — **자동 새로고침은 없다**(2026-11-05 사용자 결정). 새로고침을 부르는 길은 둘이다 — 운영자의 `POST /api/v1/sessions/{id}/plugins/refresh`(작업 화면의 `Refresh plugin skills`, 턴 사이), 그리고 대화 안에서 모델이 부르는 `skills` MCP의 `refresh_skills`(턴 안, 아래 「턴 안 새로고침」, 2026-11-08 사용자 결정). 운영자가 부르면:
  1. 사이드카가 마켓플레이스를 한 번 더 받는다(`POST /plugin-seed/refresh`, 첫 클론과 같은 범위 토큰·같은 크기 상한). 받은 커밋을 `revision`으로 함께 낸다. 받지 못하면 **이전 번들을 그대로 둔다** — 세션이 이미 가진 스킬을 잃지 않는다(502).
  2. 에이전트가 새 번들로 관리 스킬을 AC-J5와 같은 규칙으로 맞추고, 추가·수정·삭제된 스킬 디렉터리 이름을 돌려준다. 내용이 같은 스킬은 다시 쓰지 않는다. 사용자가 손으로 둔 스킬은 건드리지 않는다.
  3. 대화·스레드·로그인은 건드리지 않는다. **대화에도 아무것도 넣지 않는다** — 다음 턴의 프롬프트는 사용자가 쓴 그대로다(*2026-11-14 개정, 사용자 결정*: 이전에는 HOME의 대기 기록에 바뀐 스킬을 쌓아 다음 재개 턴 프롬프트 앞에 안내를 붙였으나 뺐다). 바뀐 스킬은 4의 출력 줄로 사용자가 보고, 대화가 예전에 읽은 스킬을 다시 읽게 할지는 사용자가 정한다.
  4. 세션 출력에 플랫폼 안내 한 줄(`[session-platform: plugin skills refreshed at <revision> — …]`)을 남긴다.

  운영자의 새로고침은 **턴 사이에만** 돈다 — 턴이 실행 중이거나 대기 중이거나, 동결 중이거나, 다른 새로고침이 돌고 있으면 409다. 새로고침이 도는 동안 도착한 프롬프트는 대기열에서 기다린다. 쓰기처럼 idle 세션은 active로 올리고 동결된 세션은 먼저 복원한다(복원 파드는 이미 최신 마켓플레이스로 시작하므로 그 새로고침은 변화가 없다). `codex`가 아닌 세션은 422, 다른 테넌트의 세션은 AC-K2대로 404, 마켓플레이스가 없는 세션(사이드카에 토큰 없음)은 `state: unconfigured`로 200이다.

  **턴 안 새로고침** (2026-11-08): 사용자가 대화로 「플러그인 새로고침해 줘」라고 하면 모델이 `skills` MCP의 `refresh_skills`(인자 없음)를 부른다. 스킬 MCP는 에이전트의 loopback 경로 `POST /plugins/refresh/turn`(`SESSION_PLATFORM_AGENT_URL`, 관리형 설정이 스킬 MCP env로 준다)을 부르고, 에이전트는 위 1~2를 그대로 한다. 다른 점:
  - **그 턴이 호출자다** — 실행 중인 턴이 있어야 하고(없으면 409), 동결이 턴을 기다리는 중이거나 다른 새로고침이 돌면 409, **턴당 한 번**(두 번째는 429 — 모델이 마켓플레이스 클론을 되풀이하지 못하게)이다. 경로는 loopback 요청만 받는다(파드 IP로 오면 403 — control plane·kubelet은 파드 IP로 온다).
  - 결과(추가·수정·삭제 이름과 「`read_skill`로 다시 읽고 삭제된 것은 쓰지 말라」)는 **도구 결과로 바로** 돌아간다. 같은 턴 안에서 Codex가 턴 시작 때 받은 스킬 목록은 그대로지만, `list_skills`·`read_skill`은 디스크를 읽으므로 새 스킬을 그 자리에서 쓴다. 목록은 다음 턴부터 바뀐다.
  - 플랫폼 안내 한 줄(4)은 턴 출력 안이 아니라 그 턴의 `end` 표식 **뒤**에 남는다. 새로고침이 끝나기 전에 턴이 끝났으면(시간 초과) 끝나는 즉시 남긴다.
  - `refresh_skills`는 사이드카가 토큰을 가진 파드(새로 받을 마켓플레이스가 있는 파드)에서만 보인다. 클론을 기다리므로 스킬 MCP의 도구 시간 상한(`tool_timeout_sec`)을 사이드카 클론 시간 상한보다 길게 둔다.
- **달성 가치**: V3
- **구체화 대상**: AC-J5의 스킬 동기화(부팅·복원 때만 → 요청 때도)와 AC-E4의 대화 연속성(스킬이 바뀌어도 이어진다)
- **검증 방법**: 마켓플레이스에 스킬을 추가·수정·삭제한 뒤 같은 세션에서 새로고침하면 응답과 설치 디렉터리·`list_skills`가 그 변화를 보이고, 다음 턴의 러너 argv 프롬프트가 사용자의 프롬프트 그대로임을 확인한다. 턴 진행 중 새로고침이 409이고, 받기 실패가 502이며 스킬이 그대로임을 확인한다. 작업 화면의 버튼이 `codex` 세션에만 있고 결과를 알림으로 보임을 확인한다. 턴 안 새로고침은: 실행 중인 턴에서 한 번 성공하고 두 번째가 429, 턴 밖이 409, 파드 IP 요청이 403이며, 안내 줄이 `end` 표식 뒤에 오고, 새로고침한 턴이 성공하든 실패하든 다음 턴의 프롬프트는 사용자의 것 그대로임을 확인한다. `refresh_skills`가 에이전트 URL이 있을 때만 목록에 오고 결과·거절을 도구 결과 문장으로 돌려줌을 확인한다.

### AC-J8: 턴이 띄운 하위 에이전트는 답 뒤에도 마저 돌고, 결과는 같은 대화로 돌아온다
- **설명**: 모델이 Codex의 하위 에이전트 도구로 띄운 에이전트는 메인 에이전트의 답(메인 스레드 턴의 끝)과 함께 끝나지 않는다 (2026-11-13 사용자 결정). 러너는 `codex app-server`가 붙여 주는 하위 에이전트 스레드를 모두 따라간다. 메인 턴이 끝났을 때 아직 도는 것이 있으면:
  1. 기다리는 에이전트 이름을 플랫폼 안내 한 줄로 남기고, 그것들이 끝날 때까지 기다린다. 하위 에이전트의 시작·MCP 호출·끝은 안내 줄로만 보인다 — 하위 에이전트의 메시지를 메인 에이전트의 답으로 투영하지 않는다.
  2. 모두 끝나면 메인 스레드에 **후속 턴**을 하나 연다. 그 프롬프트는 플랫폼 문구(`[session-platform] Background agents you started have ended …`)로 시작하고, 메인 턴이 끝난 뒤 끝난 에이전트마다 결과를 싣는다 — 완료면 마지막 메시지(에이전트당 8 KiB까지 — 넘으면 앞부분과 끝부분을 남기고 가운데를 자른다), 실패면 그 사유, 중단이면 중단. 메인 에이전트는 그 턴에서 결과를 사용자에게 전한다. 메인 턴이 도는 중에 끝난 에이전트는 싣지 않는다 — 그 턴이 직접 기다렸거나 결과를 받았다.
  3. 기다림은 `CODEX_RUNNER_BACKGROUND_WAIT_MS`(기본 10분, AC-E2의 백그라운드 대기와 같은 값)까지다. 넘으면 러너가 남은 에이전트의 턴을 중단(`turn/interrupt`)하고 안내를 남긴다. 후속 턴은 그 에이전트들을 「플랫폼이 중단함」으로 받는다.
  4. 후속 턴이 또 에이전트를 띄우면 같은 일을 되풀이한다. 후속 턴은 다섯 번까지이고, 그 뒤에 남은 에이전트는 중단한다.

  이 모두가 **한 번의 write**(작업 하나)다. 기다림과 후속 턴을 포함해 AC-E2의 실행 시간 상한(`CLAUDE_CODE_RUN_TIMEOUT`) 안에서 돈다. 그동안 다음 프롬프트와 스케줄러 회차는 큐에서 기다리고, 동결은 작업이 끝나기를 기다린다. 하위 에이전트는 메인 에이전트와 같은 관리형 설정·샌드박스·도구 표면(AC-J5)으로 돌고, 킬 스위치는 하위 에이전트의 아이템에도 걸린다. 러너가 `codex exec`가 아니라 `codex app-server`를 쓰는 이유가 이것이다 — exec는 메인 턴이 끝나면 Codex를 내리고, 하위 에이전트도 같이 죽는다(Codex 0.166.0 소스에서 확인). `codex-task`도 같은 러너라 똑같이 동작한다.
- **달성 가치**: V3
- **구체화 대상**: AC-E2의 「턴의 백그라운드 작업은 그 턴 안에서 끝낸다」(2026-11-12)를 Codex 하위 에이전트에 맞춘 것
- **검증 방법**: 러너 단위 테스트(가짜 app server)로 확인한다. 메인 턴이 끝날 때 도는 하위 에이전트를 기다린 뒤, 그 마지막 메시지를 실은 후속 턴을 메인 스레드에 연다. 하위 에이전트의 메시지는 메인 답으로 투영되지 않는다. 대기 상한을 넘은 에이전트는 `turn/interrupt`로 중단되고 「중단」으로 보고된다. 메인 턴 중에 끝난 에이전트로는 후속 턴을 열지 않는다. 하위 에이전트의 금지 아이템은 턴을 멈춘다. 실 하위 에이전트 왕복은 실 ChatGPT 로그인 뒤의 턴이라 e2e로 돌리지 않는다(`../test/codex-workload.md` 시나리오 8).

## 결정 사항 (2026-11-05, 사용자)
- **SDK 기반**: 러너는 `@openai/codex-sdk`(고정 버전)로 스레드를 시작·재개한다. CLI 직접 호출이 아니다. *2026-11-13 개정*: `codex app-server`로 바꿨다(아래 2026-11-13).
- **로그인 단위는 세션**: 플랫폼 공용 계정·테넌트별 계정을 두지 않는다. ChatGPT의 refresh token이 사용 중 갱신되는 구조라 계정 하나를 여러 파드에 복사하면 서로를 무효화할 수 있다 — 세션 단위 로그인은 그 공유 자체를 없앤다.
- **로그인은 아카이브에 포함**: 복원 후 다시 로그인하지 않는다. 대신 이 타입의 아카이브 게이트를 따로 둔다(AC-J4). *2026-11-09 개정*: 로그인은 슬롯으로 옮겼다(아래).
- **도구 표면**: 대화 · 플러그인 스킬 · K3s MCP만 (AC-J5). 세션 MCP(파일·git·drop)는 주지 않는다. *2026-11-09*: 세션 DB가 넷째로 더해졌다(아래).
- **K3s MCP 도구는 전부 허용 (2026-11-06)**: `minimax-code`의 거부 목록(reconciler-local과 같은 목록)을 codex 사이드카에는 걸지 않는다(AC-J6). codex 세션이 `session_create`로 세션을 만들고 `opensearch_*`로 작업 기록을 쓸 수 있게 하기 위해서다. 대가: `session_*`은 K3s MCP 승인 게이트 밖이라, codex 세션이 게이트 없는 shell 세션을 만들어 그 egress 정책 안에서 일할 수 있다.
- **플러그인 업데이트는 수동 새로고침만** (AC-J7): 장기 세션이 대화를 유지한 채 스킬을 다시 받는 길은 작업 화면의 버튼(API) 하나다. 주기적·자동 새로고침은 두지 않는다.
- **대화로도 새로고침한다 (2026-11-08 개정)**: 사용자가 세션 대화 안에서 새로고침을 시킬 수 있게 `skills` MCP에 `refresh_skills`를 더한다(AC-J7 「턴 안 새로고침」). 여전히 사람이 시켜야 도는 수동 새로고침이다 — 주기·자동 새로고침은 여전히 없고, 언제 부르는지는 도구 설명이 알린다(*2026-11-14*: 개발자 지시 제거). 남용은 턴당 한 번으로 막는다. 도구 표면(AC-J5)의 「플러그인 스킬」 항목에 스킬 MCP 도구 하나가 늘 뿐, 파드 밖에 닿는 새 경로는 없다(사이드카가 이미 갖던 같은 범위 토큰의 같은 클론).

## 결정 사항 (2026-11-09, 사용자)
- **세션 DB를 둔다**: 채팅 세션이 대화 밖에 데이터를 쌓을 SQLite를 슬롯 PVC에 두고 사이드카 MCP로 연다(AC-J5 4, `agent-auth-pool.md` AC-N6). 스킬 MCP에 붙이지 않은 것은 복잡한 작업을 래핑하기에 스킬 경유가 컨텍스트에 비효율적이어서다.
- **로그인도 슬롯으로**: 세션 단위였던 로그인을 슬롯 풀(`codex-chat`)로 옮긴다(AC-J3). 장기 단일 세션 기준은 그대로이고, 풀은 확장을 위한 것이다. 기존 세션은 다시 로그인한다.
- **DB 도구**: raw 두 개와 작업 원장 네 개(슬롯 단위 — 같은 슬롯의 다음 채팅 세션이 이어 쓴다). [원장 계약](../session-ledger.md)의 버전·재시도·보존 경계를 따른다.

## 결정 사항 (2026-11-13, 사용자)
- **app server로 전환, 하위 에이전트는 답 뒤에도 돈다** (AC-J2·J8): 채팅 세션에 셸·파일 편집은 필요 없지만, 하위 에이전트를 백그라운드로 돌리고 MCP 도구를 쓰는 것은 필요하다. `codex exec`(SDK)는 메인 턴이 끝나면 하위 에이전트까지 내리므로, 러너가 상주하는 `codex app-server`를 직접 구동한다. 대기는 claude-code의 백그라운드 대기(AC-E2, 2026-11-12)와 같은 10분이다. 다만 멈추는 방식이 다르다 — claude-code는 모델에게 `TaskStop`을 시키지만, Codex는 러너가 하위 에이전트의 턴을 직접 중단하고 결과를 「중단」으로 넘긴다. Codex에는 다음 턴에 붙는 「stopped」 알림 문제가 없기 때문이다. SDK 의존은 걷고, 같은 고정 버전의 `@openai/codex` 바이너리만 둔다.
