# PRD: 에이전트 인증 풀 (agent auth pool)

> 대상 요구사항: 구독 계정으로 도는 작업용 에이전트 타입(`codex-task`, 2026-11-09부터 채팅용 `codex-manager`도)이 세션마다 로그인하지 않도록,
> 플랫폼이 **로그인 슬롯 풀**을 두고 세션에 슬롯을 하나씩 **독점 임대**한다 (2026-11-07 사용자 결정).
> 슬롯은 StatefulSet의 `volumeClaimTemplates`처럼 이름이 고정된 PVC이고, 세션 파드가 그 PVC를 직접 마운트한다.
>
> 📌 **개정 (2026-11-09, 사용자 결정)**: 채팅용 `codex-chat`도 풀을 쓴다(AC-N6). 이 풀의 슬롯은 로그인과 함께
> **세션 DB**(SQLite)를 담고, 사이드카가 그 DB를 MCP로 내놓는다. 채팅은 장기 단일 세션 기준이지만, 같은 타입의
> 세션이 늘어날 때를 위해 처음부터 슬롯 단위로 둔다.
>
> 📌 **개정 (2026-11-12, 사용자 결정)**: `claude-code`는 풀을 쓰지 않는다 — 구독 모드가 `claude setup-token`의 장기
> OAuth 토큰 하나를 Secret에서 받아 모든 세션이 함께 쓴다(`claude-code-workload.md` AC-E7). 풀 `claude-code`와
> `CLAUDE_CODE_AUTH_SLOTS` 설정은 없어졌고, 이미 만들어진 그 풀의 PVC·Lease는 AC-N1대로 control plane이 지우지 않는다.

## 달성 가치
- **V3 끊김 없는 세션 연속성** — 작업 세션이 동결·복원되거나 새로 만들어져도 다시 로그인하지 않는다. 로그인은 세션이 아니라 슬롯에 남는다 (AC-N1·L4)
- **V1 세션 격리** — 한 슬롯을 동시에 두 파드가 쓰지 않는다. 구독 계정의 refresh token은 쓸 때마다 바뀌어, 두 파드가 같은 계정을 갱신하면 한쪽 로그인이 깨진다 (AC-N2)
- **V2 유휴 자원 회수** — 로그인 전용 작업 세션은 동결 시 슬롯을 반납한다. DB가 있는 codex-manager는 삭제까지 유지한다 (AC-N3·N6)
- **V3 끊김 없는 세션 연속성(장기 세션)** — 채팅 세션이 쌓은 데이터가 동결·복원과 파드 재시작을 건너 슬롯에 남는다 (AC-N6)

> 📌 **가치 연결 규칙**: 다른 PRD와 같이 각 AC는 자신이 구체화하는 상위 AC의 가치를 상속한다.

> 이 문서는 **풀 자체**(슬롯·임대·반납·로그인 동기화)만 정한다. 어떤 타입이 풀을 쓰는지와 슬롯 안 파일 이름은
> 타입 PRD가 정한다 — `codex-task`는 `codex-task-workload.md`의 AC-M2,
> `codex-manager`는 `codex-workload.md`의 AC-J3과 이 문서의 AC-N6(슬롯 안 배치와 세션 DB).

## Acceptance Criteria

### AC-N1: 슬롯 = 이름이 고정된 PVC, control plane이 만들고 지우지 않는다
- **설명**: 풀은 타입마다 하나다. 풀 `<pool>`(`codex-task`·`codex-manager`)의 슬롯 `i`(0 ≤ i < N)는 PVC `<네임스페이스>-<pool>-auth-<i>`다. PVC 이름에 네임스페이스를 넣는 것은 동적 프로비저너가 PVC 이름만으로 볼륨을 정할 수 있어서다 — 운영 클러스터의 `efs` 클래스는 `/${.PVC.name}` 경로와 재사용 access point를 써, 이름이 같으면 프리뷰 네임스페이스의 슬롯이 운영 슬롯과 같은 디렉터리를 쓰고 프리뷰를 지울 때 운영 로그인까지 지운다(2026-11-07 프리뷰 점검에서 발견). N은 control plane 설정(`CODEX_TASK_AUTH_SLOTS`·`CODEX_CHAT_AUTH_SLOTS`)이고, 0이면 그 타입은 풀이 없어 `GET /config`에 나오지 않으며 생성은 pod 없이 실패한다. PVC는 처음 임대될 때 control plane이 만든다(`ReadWriteOnce`, 크기 `<POOL>_AUTH_STORAGE_SIZE` 기본 `16Mi` — `codex-manager`는 세션 DB를 담아 `1Gi`, 클래스 `<POOL>_AUTH_STORAGE_CLASS` 비면 클러스터 기본 — 운영은 기본 클래스가 없어 `efs`를 지정한다). 라벨은 `session-platform.dev/auth-pool=<pool>`, `session-platform.dev/auth-slot=<i>`다. control plane은 슬롯 PVC를 **지우지 않는다** — 세션이 지워져도, N을 줄여도 남는다(StatefulSet의 PVC 보존과 같다). N을 줄이면 범위 밖 슬롯은 더 임대하지 않을 뿐이다. 노드 국소 스토리지(local-path, kind e2e)에서는 PV의 노드 친화성 때문에 그 슬롯을 받은 세션 파드가 그 노드에 뜬다. 운영의 `efs`는 RWX라 노드에 묶이지 않는다.
- **달성 가치**: V3
- **구체화 대상**: AC-B3(무결성) — 동결·복원·재생성을 건너 보존되는 상태에 「슬롯의 로그인」을 더한 것
- **검증 방법**: 풀 크기 2의 배포에서 첫 세션 생성 뒤 PVC `<네임스페이스>-<pool>-auth-0`이 라벨과 함께 생기고 세션 파드가 그것을 마운트함을 확인한다. 세션을 지운 뒤에도 PVC가 남음을 확인한다. 풀 크기 0이면 `GET /config`에 타입이 없고 생성이 pod 없이 실패함을 확인한다.

### AC-N2: 독점 임대 = 슬롯마다 Lease 하나, holder는 세션 id
- **설명**: 슬롯 `i`의 임대는 `coordination.k8s.io` Lease `<pool>-auth-<i>`다(PVC와 같은 라벨, 이름은 네임스페이스 접두 없이 — Lease는 네임스페이스 안에서만 보인다). `holderIdentity`가 세션 id이면 그 세션이 슬롯을 쥔 것이다. 임대·반납은 resourceVersion으로 CAS하므로 두 control plane 경로가 같은 슬롯을 동시에 잡지 못한다. 로그인 전용 작업 세션은 슬롯을 **파드가 있는 동안** 쥔다(codex-manager는 AC-N6에 따라 삭제까지 유지) — 생성(AC-A1)과 복원(AC-B2)이 파드를 만들기 **전에** 임대하고, 파드 생성이 실패하면 반납한다. 고를 슬롯은 비어 있는 슬롯 가운데 로그인 상태(AC-N4)가 `signed-in` → 모름 → `signed-out` 순, 같은 순위에서는 번호가 작은 것이다. 비어 있는 슬롯이 없으면 생성·복원은 파드 없이 **503**(`auth pool exhausted`)으로 실패한다 — 복원 실패는 세션을 `snapshot`에 남긴다.

  holder가 남았지만 실제로는 쥐고 있지 않은 임대(control plane이 반납 전에 죽은 경우)는 다음 임대가 회수한다. 회수 조건은 **둘 다**다: ① holder 세션이 레코드에 없거나 DB 없는 타입의 `snapshot` 상태이고, ② 임대의 `renewTime`이 10분(생성·복원 한 번보다 긴 유예)보다 오래됐다. ②가 없으면 레코드를 쓰기 전인 생성이나 아직 `snapshot`인 복원의 임대를 다른 세션이 빼앗는다.
- **달성 가치**: V1
- **구체화 대상**: AC-A1/A2의 세션 격리 — 세션 전용 자원에 「세션 전용 로그인 슬롯」을 더한 것
- **검증 방법**: 풀 크기 1에서 첫 세션이 슬롯을 쥔 동안 두 번째 생성이 pod 없이 503임을 확인한다. holder가 지워진 세션이고 `renewTime`이 오래된 임대는 다음 생성이 회수하고, 유예 안의 임대는 회수하지 않음을 단위 테스트로 확인한다. 로그인된 슬롯이 먼저 배정됨을 확인한다.

### AC-N3: 반납 = 로그인 전용 타입 동결 완료·모든 타입 삭제 시
- **설명**: codex-manager는 AC-N6의 DB 보존을 위해 삭제까지 슬롯을 유지한다. 나머지 타입은 동결이 커밋되어 파드가 지워진 뒤(AC-B1) 슬롯을 반납하고, 삭제(`DELETE /sessions/{id}`)도 파드를 지운 뒤 반납한다. 반납은 holder가 자기 세션일 때만 지운다(CAS) — 이미 회수된 슬롯을 남의 것까지 풀지 않는다. 반납 실패는 동결·삭제를 실패시키지 않는다; 남은 임대는 AC-N2의 회수 조건이 처리한다. 복원은 이전 슬롯을 고집하지 않는다 — 대화 기록은 세션 아카이브에 있고 로그인은 슬롯에 있으므로, 다른 계정의 슬롯으로 복원해도 대화가 이어진다.
- **달성 가치**: V2
- **구체화 대상**: AC-B1(동결)·AC-A3(자원 회수)
- **검증 방법**: 풀 크기 1에서 세션 A를 동결하면 슬롯이 풀리고 세션 B 생성이 성공함을 확인한다. 이어서 A에 접근하면 B가 슬롯을 쥔 동안 503이고 A는 `snapshot`에 남음을 확인한다. 삭제한 세션의 슬롯이 풀림을 확인한다.

### AC-N4: 로그인은 슬롯 파일, 에이전트가 HOME과 동기화하고 아카이브에서 뺀다
- **설명**: 슬롯 PVC는 주 컨테이너의 `/var/run/session-platform/auth-slot`에 마운트되고(`AGENT_AUTH_SLOT_DIR`), 그 안에 타입이 정한 로그인 파일 하나가 있다. CLI는 그 파일을 HOME 아래 자기 자리(타입 PRD가 정함)에서 읽고 쓰므로, 에이전트가 두 자리를 **복사로** 맞춘다 — symlink를 두지 않는다(CLI가 임시 파일 + rename으로 바꿔 쓰면 symlink가 끊겨 갱신된 토큰을 잃는다).
  1. 턴 시작 전: 슬롯 → HOME. 슬롯에 파일이 없으면 HOME의 것도 지운다.
  2. 턴 중: 1초마다 HOME의 파일이 바뀌었으면 HOME → 슬롯. 턴 중에 파드가 죽어도 갱신된 refresh token이 슬롯에 남게 한다.
  3. 턴 끝: HOME → 슬롯. HOME에서 파일이 사라졌으면(로그아웃) 슬롯의 것도 지운다.

  쓰기는 임시 파일 + fsync + rename, 권한 0600이다. HOME의 로그인 파일은 **세션 아카이브에 넣지 않는다** — 로그인은 슬롯의 것이고, 아카이브에 넣으면 복원이 낡은 토큰으로 슬롯의 새 토큰을 덮을 수 있다. 에이전트는 `GET /auth-slot`으로 `{"signedIn": <슬롯 파일이 있고 비지 않음>}`을 알리고, control plane은 반납 직전에 그것을 읽어 Lease의 `session-platform.dev/auth-state`(`signed-in`·`signed-out`)에 적는다(AC-N2의 순위). 읽지 못하면 적지 않는다.

  빈 슬롯을 받은 세션은 첫 프롬프트에서 그 타입의 로그인 흐름을 돈다(타입 PRD). 로그인 결과는 3번으로 슬롯에 남아 다음 세션은 로그인하지 않는다.
- **달성 가치**: V3, V1
- **구체화 대상**: AC-E5·AC-J4의 파일시스템 아카이브 — 아카이브 대상에서 로그인 파일을 빼고 그 자리를 슬롯이 맡은 것
- **검증 방법**: 에이전트 단위 테스트로 턴 전·중·후 동기화(슬롯 없음 → HOME 삭제, HOME 갱신 → 슬롯 갱신, HOME 삭제 → 슬롯 삭제)와 아카이브에 로그인 파일이 없음을 확인한다. `GET /auth-slot`이 슬롯 상태를 돌려주고 반납이 Lease 주석에 적음을 확인한다.

### AC-N6: `codex-manager` 슬롯 = 로그인 + 세션 DB, 컨테이너마다 제 몫만 마운트
- **설명**: 이 타입의 풀 이름은 `codex-manager` 가 아니라 **`codex-chat`** 이다 — 2026-11-17 타입 이름 변경에서 풀만 옛 이름으로 남겼다. 이미 provision 된 Lease `codex-chat-auth-<i>`·PVC `<네임스페이스>-codex-chat-auth-<i>` 와 환경 변수 `CODEX_CHAT_AUTH_SLOTS` 를 그대로 쓰기 위한 것이고, 풀 이름을 바꾸면 돌고 있는 세션이 슬롯을 잃는다. `codex-chat` 풀(`CODEX_CHAT_AUTH_SLOTS`·`_STORAGE_CLASS`·`_STORAGE_SIZE` 기본 `1Gi`)의 슬롯은 두 디렉터리로 나뉜다 — `auth/`(로그인 파일 `auth.json`)와 `db/`(세션 DB `session.db`). DB 디렉터리는 세션이 아니라 **슬롯**의 것이다 — 채팅 세션을 지우고 새로 만들어도 같은 슬롯을 받으면 같은 DB를 이어 쓴다. 같은 PVC를 subPath로 나눠 마운트한다:
  1. 주 컨테이너는 `auth/`만 `/var/run/session-platform/auth-slot`에 받는다. 로그인 동기화·아카이브 제외는 AC-N4 그대로다.
  2. `k3s-mcp-proxy` 사이드카는 `db/`만 `/var/run/session-platform/session-db`에 받고(`SESSION_DB_DIR`), 같은 포트의 `/session-db/mcp`에서 **세션 DB MCP**를 서빙한다. 주 컨테이너는 그 주소만 받는다(`SESSION_DB_MCP_URL`). 사이드카는 로그인 파일에, 주 컨테이너는 DB 파일에 닿지 않는다 — 그래서 AC-N4의 「사이드카에 슬롯을 마운트하지 않는다」는 「사이드카에 로그인을 마운트하지 않는다」로 읽는다.
  3. 초기화 컨테이너 `slot-init`(root, `CHOWN`·`FOWNER`만)이 슬롯 전체를 마운트해 두 디렉터리를 만들고 `db/`를 사이드카 사용자(65532)에게 넘긴다 — kubelet이 만드는 subPath는 root 소유 0750이라 non-root 사이드카가 쓰지 못한다. `efs` access point처럼 소유자를 하나로 매핑하는 볼륨에서는 chown이 실패하지만, 그 볼륨은 이미 사이드카가 쓸 수 있으므로 실패를 무시한다.

  세션 DB MCP가 기본으로 내놓는 것은 **원장 네 도구**(`ledger_get/list/put/delete`)뿐이다. raw 도구 둘은 **디버그 전용**이다 (2026-11-16 사용자 결정) — 배포가 사이드카에 `SESSION_DB_RAW_SQL=debug`를 주지 않으면 `tools/list`에 **서지 않고**(기본 비노출), 이름을 알고 불러도 그 스위치를 가리키는 오류로 **거절된다**(기본 비활성). 세션이 켤 수 있는 스위치가 아니다 — 값은 배포의 `codex-config` ConfigMap 키 `session-db-raw-sql`에서 와 사이드카 env로만 들어가고, 주 컨테이너는 받지 않는다. `debug` 말고 다른 값(`true`·`1`)은 off로 읽지 않고 사이드카 기동을 실패시킨다 — 오타가 조용히 off가 되면 도구가 제거된 것처럼 보이기 때문이다. 옵트인된 사이드카에서 raw 도구는 둘이다: `raw_query`(행을 돌려주는 문장, 최대 1000행·약 1MiB, 넘으면 `truncated`)와 `raw_exec`(바꾸는 문장, `rowsAffected`·`lastInsertId`; 매개변수가 없으면 `;`로 이은 여러 문장). 둘 다 `{sql, params?}`를 받고 `params`는 `?` 자리에 순서대로 묶인다. SQLite가 거부한 문장은 `isError` 도구 결과로 메시지를 돌려준다. 한 문장은 30초로 끊는다. DB는 `journal_mode=DELETE`로 연다 — 운영 `efs`는 NFS라 WAL의 공유 메모리가 동작하지 않고, 파일을 여는 프로세스는 사이드카 하나다. 사이드카가 뜰 때 디렉터리가 준비되지 않았으면 그 호출만 실패하고 다음 호출이 다시 연다(사이드카는 K3s MCP도 맡으므로 죽지 않는다). DB는 아카이브에 들어가지 않는다 — 슬롯에 있으므로 동결·복원·재생성을 건너 남는다.
  원장은 세션 밖에서도 **읽기만** 할 수 있다. 사이드카는 `/session-db/ledger/tasks`에서 `ledger_list`를 그대로 쓰는 **GET 전용** 뷰를 서빙하고(입력은 `limit`·`after_id` 둘뿐 — SQL은 받지 않으므로 이 경로로는 원장 작업 행 말고 DB의 어느 것도 읽히지 않는다), 주 컨테이너가 `/ledger/tasks`에서 그것을 중계하며, control plane이 `GET /api/v1/sessions/{id}/ledger/tasks`로 내놓는다. 사이드카가 루프백에 묶여 있으므로 중계가 한 단 필요하다. 읽기는 **수동적**이다 — `Questions`·`ToolApprovals`처럼 접근으로 세지 않고 스냅샷을 복원하지 않으므로, 패널을 여는 것이 세션을 깨우지 않는다. 그래서 파드가 없는 세션(`snapshot`·파드 없음)은 **빈 원장이 아니라** 「읽을 수 없음」(409)으로 답한다 — 행은 슬롯 볼륨에 그대로 있어 「작업이 없다」는 거짓이 되기 때문이다. 세션 DB가 없는 타입은 501이다. 경로는 다른 세션 id 경로와 같은 범위 규칙을 따르므로(AC-K2) 남의 테넌트 세션은 없는 세션과 똑같이 답한다. 원장은 **슬롯**의 것이므로 지금 그 슬롯을 쥔 파드를 통해 읽는 것이 곧 「현재 채팅의 원장」을 읽는 것이다. 세션 밖에서 **쓸 수 있는 것은 작업 행이 아니라 사용자 요청 한 종류**이고, 그것은 AC-N7이 정한다.

  DB가 있는 codex-manager은 스냅샷/복구/복원 실패에도 슬롯을 유지하며 frozen holder 재회수 대상이 아니다. 삭제 시 반납하고, 동결 중에도 풀 용량을 차지한다. 다른 타입의 스냅샷 반납 규칙은 유지한다. 상위 작업 관리 도구와 raw 트랜잭션 경계는 [세션 원장 계약](../session-ledger.md)을 따른다. 한때(PR #216) DB가 `db/<sessionID>/`로 세션마다 나뉘어 재생성한 채팅이 빈 DB를 열었으므로, 슬롯 단위로 되돌린다; 그 사이 남은 `db/<sessionID>/` 디렉터리는 자동으로 합치지 않고 보존한다.
- **달성 가치**: V3(장기 세션), V1
- **구체화 대상**: AC-N1(슬롯)·AC-N4(로그인 배치) — 슬롯에 세션 DB를 더하고 컨테이너별로 나눠 마운트한 것, `codex-workload.md` AC-J5(도구 표면)·AC-J6(사이드카)
- **검증 방법**: 제출된 `codex-manager` pod spec에서 PVC가 자기 슬롯 하나이고, 주 컨테이너는 subPath `auth`, 사이드카는 subPath `db`, `slot-init`만 슬롯 전체를 마운트함을 확인한다(`control-plane/test/codex_orchestrator_test.go`). 세션 DB MCP 단위 테스트로 옵트인 없는 사이드카의 `tools/list`가 원장 넷뿐이고 raw 호출이 스위치 이름과 함께 거절되는 것(원장 호출은 그대로 되는 것), `debug` 아닌 값이 오류인 것, 그리고 옵트인된 사이드카에서 `raw_exec` → `raw_query` 왕복, SQLite 오류가 `isError`, 행 상한과 `truncated`, 늦게 생긴 디렉터리를 다음 호출이 여는 것, `/session-db/mcp` 밖의 요청은 K3s MCP 프록시로 가는 것을 확인한다(`data-plane/cmd/agent/session_db_mcp_test.go`). 제출된 pod spec에서 그 스위치가 사이드카에만, ConfigMap 키 참조(optional)로 붙음을 확인한다(`control-plane/internal/adapter/k8s/session_db_test.go`). 읽기 전용 뷰는 단위 테스트로 사이드카의 뷰가 `ledger_list`와 같은 페이지를 내고 커서가 끝나면 비는 것, GET 말고는 405인 것, SQL 모양의 질의 매개변수로 원장 밖 테이블이 새지 않는 것, 범위 밖 `limit`이 잘리지 않고 400인 것, 루프백 아닌 요청이 403인 것, `/session-db/ledger/tasks` 밖의 요청은 K3s MCP 프록시로 가는 것을 확인하고(`data-plane/cmd/agent/session_ledger_http_test.go`), control plane 경로로 페이지·커서·`limit` 거절·소유권 범위(남의 테넌트는 404)·세션 DB 없는 타입 501·스냅샷 409이면서 **읽어도 스냅샷에 머무르고 파드를 건드리지 않는 것**을 확인한다(`control-plane/internal/api/ledger_test.go`).

### AC-N7: 사용자 요청 — 앱이 원장에 남기고, 부모가 접수해 처리한다
- **설명**: 사람이 작업 하나를 두고 쓴 요청을 세션 밖에서 **그 슬롯의 원장에 영속 저장**한다. 대화 메시지로 보내지 않고 턴을 시작하지도 않으므로, 답이 쓰이는 중에도 저장되고 재시작·동결을 건너 남는다.
  1. **저장 위치는 작업 문서가 아니라 제 테이블**(`sp_ledger_user_requests`, `task_id`로 작업에 연결)이다. 요청이 도착하는 동안 부모가 같은 작업을 `ledger_put`으로 쓰더라도 서로의 쓰기를 잃지 않는다 — 요청은 작업 행을 건드리지 않는 INSERT 하나이므로 `details`·승인·커서가 부모가 쓴 그대로 남는다. 테이블은 **가산적**이고 `sp_ledger_meta`는 버전 1에 머문다 — 롤백한 옛 사이드카 이미지도 이 DB를 계속 연다. 작업을 지워도 그 작업에 대해 사람이 물어본 말은 지워지지 않는다(은퇴한 id로 새 요청은 거절).
  2. **경로는 POST 세 단**이다: 사이드카 `/session-db/ledger/requests`(루프백 전용) → 주 컨테이너 `/ledger/requests` 중계 → control plane `POST /api/v1/sessions/{id}/ledger/tasks/{taskID}/requests`(`{id, text, author}`). 작업 id는 경로에 있으므로 본문이 다른 작업을 겨눌 수 없다. 저장도 읽기처럼 **수동적**이다 — 접근으로 세지 않고 스냅샷을 복원하지 않으며 턴을 만들지 않는다. 201 저장 · 200 같은 id·같은 말의 재전송(한 건) · 404 없는 세션/작업 · 409 id 재사용·지워진 작업·파드 없음 · 501 세션 DB 없는 타입 · 400 형식. 범위 규칙은 AC-K2와 같다(남의 테넌트는 없는 세션과 동일). `author`는 사람을 인증한 경계에서 호출자가 **스스로 도출한** 값이고, 작업의 `owner`처럼 **기장(bookkeeping)**이다 — 원장은 그것을 근거로 도구·승인·머지를 주지 않는다. 요청 본문은 사람의 입력이며 세션이 할 수 있는 일의 범위를 넓히지 않는다.
  3. **부모의 소비는 조회가 아니라 접수다.** `ledger_requests_list`는 아무것도 바꾸지 않고, `ledger_requests_claim`이 `expected_version` CAS로 하나를 가져가며(여러 부모가 다퉈도 한 쪽만 이긴다) `claim_token`을 준다. `ledger_requests_dispatch`가 **외부 행동 전에** 실행 의도(`operation_key`·`operation_target`·`dispatch_state` `intended`→`dispatched`)를 적고, `ledger_requests_ack`만 `processed`/`failed`에 이르며 결과와 `related_seq`를 남긴다 — 보기만 하고 버린 요청은 미처리로 남는다.
  4. **만료된 claim은 재실행 허가가 아니다.** 적힌 dispatch가 없으면 외부에서 아무 일도 일어날 수 없었으므로 다시 claim되고, 적혀 있으면 요청은 `reconciling`이 되어 claim 응답이 `reconcile: true`와 앞선 `operation_key`를 함께 준다. 그 상태에서 **다른** operation key는 `observed=not_accepted`(앞 시도가 닿지 않았음을 확인했다는 진술) 없이는 거절되고, 적힌 key로의 재전송은 허용된다 — 외부가 그 key로 중복을 걸러내기 때문이다. 만료된 보유자의 토큰은 dispatch·ack 모두에서 거절되므로 늦게 돌아온 부모가 새 보유자 위에 결과를 덮어쓰지 못한다.
  5. **발견은 평소 조회로 된다** — `ledger_get`·`ledger_list`의 작업 레코드가 `requests`(`pending`·`claimed`·`reconciling`·`last_seq`)를 함께 싣는다. 작업 목록만 읽는 부모도 요청이 왔음을 보고, 같은 작업의 여러 요청은 도착 순(`seq`)으로 처리한다. 요청이 왔다는 것만으로 작업 상태·승인이 바뀌지는 않지만, `blocked`·`review` 작업도 **새 사용자 입력이 있으므로 재평가 대상**이다 — 무관한 차단이 자동으로 풀리지는 않는다. 부모가 적용하는 순서는 [세션 원장 계약](../session-ledger.md)의 「User requests」가 정한다.
- **달성 가치**: V3(장기 세션), V1
- **구체화 대상**: AC-N6(슬롯 세션 DB와 읽기 전용 뷰) — 그 경로에 「사용자 요청」 한 종류의 쓰기를 더한 것, `codex-workload.md` AC-J5(도구 표면)
- **검증 방법**: 데이터 플레인 단위 테스트로 작업에 연결되지 않은 요청 거절(404)·지워진 작업 거절(409)·같은 id 재전송 1건·id 재사용 충돌·형식 거절, 요청 저장이 작업 버전을 움직이지 않아 부모가 준비한 `ledger_put`이 그대로 착지하는 것, 도착 순 처리와 작업별 필터, 두 부모의 claim 경합에서 한 쪽만 이기는 것, 조회만으로는 상태가 바뀌지 않는 것, 보유하지 않은 토큰의 ack 거절, **dispatch 뒤 ack 전에 죽은 뒤** 만료 claim이 `reconciling`으로 열리고 다른 operation key가 근거 없이 거절되는 것, 작업 삭제 뒤에도 요청이 남는 것, 변이의 replay를 확인한다(`data-plane/cmd/agent/session_ledger_user_requests_test.go`). 사이드카 뷰는 루프백 아닌 POST 403·GET 405·201/200/404/409/400을 확인한다(같은 파일). control plane 경로는 201/200 재전송·없는 작업 404·남의 테넌트 404·세션 DB 없는 타입 501·형식 400과, 저장이 원장을 읽지도 세션을 깨우지도 않는 것을 확인한다(`control-plane/internal/api/ledger_test.go`).

### AC-N8: 보낼 선택지는 세션이 쓰고, 작업에는 이력이 남는다
- **설명**: 앱이 작업 상세에서 보여 주는 「보낼 수 있는 선택지」는 **세션이 쓴다** — 앱이 상태별로 들고 있던 고정 목록은 상태를 되풀이할 수밖에 없었고(「막혀 있으니 왜 막혔는지 물어보기」), 이 작업이 실제로 무엇을 기다리는지는 세션만 안다.
  1. `ledger_choices_put({id, request_id, expected_version, choices})`가 한 작업의 선택지 집합을 **전체 교체**한다(최대 6개, `{choice_id, label(≤80자), request_text(≤1000자)}`). `expected_version`은 그 작업의 **현재 version**이어야 하고, 그 값이 각 항목의 `basis_version`이 된다. `ledger_choices_clear`는 집합을 비운다.
  2. **읽기는 `basis_version`이 작업의 현재 version과 같은 항목만 내놓는다.** 작업이 바뀌면(version 상승) 그 선택지는 자동으로 더 이상 서빙되지 않는다 — 지우는 호출이 필요 없고, 낡은 문장이 화면에 남거나 그 문장으로 요청이 저장되는 일이 없다. 낡은 version 기준으로 쓰려 하면 **conflict**다(작업을 다시 읽고 지금 version 기준으로 쓴다).
  3. **낡은 선택지는 숨기는 것으로 그치지 않고 저장에서 거부된다** — 작업이 움직이기 전에 열린 화면은 여전히 옛 문장을 들고 있으므로, `choice_id`를 실은 요청은 그 선택지가 **지금도 그 작업이 내놓는 것**일 때(= 그 항목의 `basis_version`이 작업의 현재 version과 같을 때)만 저장되고, 호출자가 본 `choice_basis_version`도 그 값과 일치해야 한다(같은 `choice_id`를 새 version 기준으로 다시 쓴 경우에도 옛 화면은 통과하지 못한다). 거부는 재사용된 id 와 구별되는 `stale_choice`(409)이므로 앱은 「화면이 낡았다」고 말하고 **이미 쓴 초안을 지우지 않으며** 작업을 다시 읽는다. 자유 입력에는 `choice_id`가 없고 이 규칙에 걸리지 않는다.
  4. 선택지는 **보낼 문장**이며 **권한이 아니다** — 호출별 도구 승인·사람 머지 게이트를 대신하지 않는다. 앱은 라벨을 보여 주고, 누르면 `request_text`로 요청 칸을 채우며(전송 아님), 저장할 때 `choice_id`를 함께 보내 세션이 자기 문장 중 무엇이 돌아왔는지 안다. 선택지가 없으면 앱은 **없다고 말하고** 자유 입력을 남긴다.
  5. **작업 이력**(`sp_ledger_task_events`)은 append-only이고 **그 변화와 같은 트랜잭션**에 적힌다 — 커밋되지 않은 변화의 이력 줄은 존재할 수 없고, 멱등 재시도는 줄을 더하지 않는다. 종류: `task_created`·`task_updated`(무엇이 움직였는지)·`task_deleted`·`request_stored`(사람이 쓴 원문)·`request_claimed`·`request_dispatched`(operation key·대상 — **claim token 은 절대 넣지 않는다**)·`request_settled`(결과·related seq)·`choices_published`·`choices_cleared`.
  6. 읽기는 `ledger_events_list({id, after_seq?, limit?})`와, 세션 밖에서 사이드카 `GET /session-db/ledger/events` → 에이전트 `/ledger/events` → control plane `GET /api/v1/sessions/{id}/ledger/tasks/{taskID}/events`다. 커서는 행의 `seq`라서 **페이지 경계가 행을 겹치거나 빠뜨리지 않는다**. 범위는 물어본 **그 작업 하나**이고, 자격증명·토큰·트랜스크립트는 들어가지 않는다 — 에이전트 로그가 아니라 사람이 읽는 작업 이력이다. 읽기는 수동적이다(AC-N6과 같음: 접근으로 세지 않고 스냅샷을 복원하지 않는다).
  7. 이력은 이 스키마가 있는 시점부터 쌓인다 — **그 전 작업에는 이력이 없고, 없는 이력을 만들어 내지 않는다.** 옛 이미지를 쓰는 파드에는 이 라우트가 없으므로 control plane은 그것을 **「지원하지 않음」**으로 전하고(빈 이력·없는 작업으로 전하지 않는다), 요청 저장 라우트의 404도 같은 기준으로 구분한다.
- **달성 가치**: V3(장기 세션), V1
- **구체화 대상**: AC-N7(사용자 요청) — 그 요청에 「세션이 쓴 선택지」와 「작업 이력」을 더한 것
- **검증 방법**: 데이터 플레인 단위 테스트로 선택지가 기준 version에서만 서빙되고 작업이 움직이면 사라지는 것·낡은 기준 put 의 conflict·경계값과 중복 id 거절·변이 replay 가 이력을 늘리지 않는 것, 이력이 실제 일어난 순서(생성→전환→요청 저장→접수→dispatch→종료)대로 적히고 전환 줄이 무엇이 움직였는지 담는 것·요청 줄이 사람의 원문을 담는 것·claim token 이 이력에 없는 것·작업별로 섞이지 않는 것·seq 커서 페이지 경계·동시 put 의 단일 집합·**낡은/없는 선택지를 실은 저장이 `stale_choice`로 거부되고(작업이 움직인 뒤, 같은 id 재발행 뒤, 호출자 기준 불일치) 자유 입력은 그대로 저장되며 거부가 이력 줄을 남기지 않는 것**, 그리고 이력 뷰의 루프백 아닌 요청 403·GET 아닌 요청 405·범위 밖 limit/after_seq 400 을 확인한다(`data-plane/cmd/agent/session_ledger_task_choices_test.go`). control plane 경로로 이력 페이지·커서·작업 범위·남의 테넌트 404·형식 400 과, 작업 페이지가 선택지와 `basis_version`을 싣는 것·낡은 선택지를 실은 저장이 409 로 거부되고 선택지 없는 `choice_basis_version`이 400 인 것을 확인한다(`control-plane/internal/api/ledger_test.go`).

### AC-N9: 작업 기록 — 합의한 `task`·`turn` 두 레코드로 옮긴다
- **설명**: 새 작업은 레포 소유자와 합의한 **작업 레코드**(`task` 한 행과 `turn` 한 행)에 쓴다. 원장은 그대로 남는다 — 부모의 기장(승인 범위·세션 커서와 seq·보존 상태·모니터 행)은 작업과 턴에 들어가지 않으므로, 합의한 모양에 맞추려고 그것을 버리면 부모가 아직 쓰는 레코드가 사라진다.
  1. **합의한 모양이 전부다.** `sp_work_tasks`는 `id`·`session_id`(null이면 미배정)·`title`·`description`·`completion_criteria`·`status`·`version`·`created_at`·`updated_at`(null이면 기록 없음)이고, `sp_work_turns`는 `id`·`task_id`·`session_seq`·`request`(사람의 원문)·`instruction`(부모가 세션에 넘긴 원문)·`response`(그 세션의 최종 답 원문)·`explanation`(부모가 사람에게 쓴 설명)·`question`·`choices`·`artifacts`·`requested_at`·`started_at`·`ended_at`이다. 두 엔터티에 **그 밖의 것은 더하지 않는다** — `sp_work_tasks`를 읽는 쪽은 합의한 컬럼만 본다. turn의 `id`는 DB 전체에서 증가하므로 그것이 곧 일어난 순서이고, `(task_id, id)`로 색인된다. 상태 영역은 원장의 것을 그대로 쓴다(`planned`·`running`·`blocked`·`review`·`completed`·`unknown`) — 이름을 바꾸면 사람이 이미 「막혔다」·「끝났다」로 본 작업이 움직인다. `response`는 부모의 요약이 아니다(그것은 `explanation`이다).
  2. **도구는 `task_get`·`task_list`·`task_put`·`task_delete`·`turn_append`·`turn_patch`·`turn_list`·`turn_dispatch`**이고, 모든 변이가 `request_id`와 `expected_version`을 받는다(같은 id·같은 인자는 **그때 커밋된 답**을 돌려주고, 같은 id·다른 인자는 conflict). `expected_version`은 그 작업의 **현재** version이어야 하므로 같은 작업을 읽은 두 부모가 다음 턴을 둘 다 쓸 수 없다. 턴 쓰기는 version을 올리지 않지만(턴은 작업의 새 상태가 아니라 작업에 일어난 사건) `updated_at`을 움직인다. `task_put`은 **전체 교체**이고, 지운 id는 영구 은퇴한다. `turn_list({open: true})`는 아직 부모가 할 일이 남은 턴(요청이 왔고 `ended_at`이 없는 것)만 고르며, 턴은 읽기가 아니라 **응답과 `ended_at`을 쓰는 것으로** 소비된다. `turn_dispatch`는 턴 옆의 기장이며 AC-N7 4번의 대조 규칙을 그대로 따른다.
  3. **옮기기는 리허설·백업·펜스를 갖춘 한 번의 작업이다.** `work_migrate({request_id, dry_run?})`에서 `dry_run`은 쓸 것을 그대로 보고하고 **아무것도 바꾸지 않는다**. 실제 실행은 `PRAGMA integrity_check`로 손상된 DB를 **거절**한 뒤(손상을 복사하지 않는다) `VACUUM INTO`로 일관 스냅샷을 DB 옆 `<db>.pre-work-<UTC>.bak`에 떠서 경로·크기·SHA-256을 `sp_work_migration`에 적고, 그 스냅샷을 **지우지 않고 보존**한다 — 전체 복원의 출발점이고, 복원은 **오프라인 작업**이다(어느 사이드카도 DB를 열고 있지 않을 때 덮어쓰고 무결성·행 수를 다시 확인한다). `sp_work_meta.state`가 `ready`→`migrating`→`migrated`로 가고, `migrating` 동안 **원장과 작업의 쓰기는 `conflict`로 거절**된다(읽기는 유지) — 복사는 한 트랜잭션이고 원장까지 함께 가져가므로 중간의 쓰기를 받으면 원본에 없는 행을 복사하게 된다. 펜스는 복사 **전에** 커밋되므로 중단된 실행은 롤백되고 펜스를 남겨 다음 실행이 **이미 적힌 스냅샷에서 재개**하며(두 번 뜨지 않는다), 모든 insert가 키를 가지므로 두 번째 실행은 아무것도 더하지 않고 이미 있던 것을 `tasks_present`·`turns_present`로 보고한다. 스냅샷 기록 없이 펜스만 올라 있으면 **거절한다** — 출발점이 없는 복사는 되돌릴 데가 없다.
  4. **아무것도 지우거나 뭉개지 않는다.** 원장 테이블은 그대로 있고, 합의한 모양에 컬럼이 없는 부분(stage·owner·커서와 seq를 가진 세션 관계·승인과 보존 상태가 든 `details`·요청의 claim과 dispatch)은 `sp_work_task_legacy`·`sp_work_turn_legacy`에 **원문 그대로** 보존된다. 작업 레코드를 읽는 데 그것은 필요 없고, 부모는 계속 그것으로 일한다. **모니터 행은 사람의 작업이 아니므로 보존되고 작업이 되지 않는다** — 작업으로 보여 주면 사람이 요청한 적 없는 일을 만들어 내는 것이다. 원장이 실제로 적은 것만 옮긴다: 세션에 간 지시와 세션의 최종 답은 원장이 원문으로 남긴 적이 없으므로 `instruction`·`response`는 null이고, 요청의 `result`는 부모가 사람에게 쓴 문장이므로 턴의 `explanation`이 된다(`response`가 되면 부모의 요약이 세션의 말로 둔갑한다). 원장에 없는 시각·seq는 **추측하지 않고 null**로 둔다. 과거의 관리 이벤트는 턴이 아니다 — 저장된 사용자 요청(사람의 원문과 도착 시각)만 턴이 된다. 상태·승인·완료는 데이터가 움직였다는 이유로 움직이지 않는다.
  4-2. **합의한 모양은 앱까지 닿아야 한다.** 원장 모양의 뷰에는 작업의 `description`·`completion_criteria`도, 턴의 `instruction`·`response`·`explanation`·`question`·`choices`·`artifacts`·시각도 **담을 자리가 없다** — 그것만 가진 독자는 「작업이 있다」까지만 보여 줄 수 있고 「그 작업」은 보여 줄 수 없다. 그래서 작업 레코드는 자기 읽기 경로를 갖는다: 사이드카 `GET /session-db/work/tasks`·`GET /session-db/work/turns?task_id=`(루프백·GET 전용) → 에이전트 `/work/tasks`·`/work/turns` → control plane `GET /api/v1/sessions/{id}/work/tasks`·`GET /api/v1/sessions/{id}/work/tasks/{taskID}/turns`. 작업 레코드는 합의한 컬럼과 `turns_total`·`latest_turn`·`migrated`(원장에서 왔다 = 원장에 이력과 부모 기장이 함께 있다)를 싣고, 턴은 합의한 모든 필드와 `origin`(빈 값=세션이 쓴 턴 · `user_request`=원장 요청에서 옮겨온 턴 · `app_request`=커토버 뒤 요청 경로로 들어온 턴)을 싣는다. **claim token·operation key·dispatch state 는 이 경로에 없다** — 부모가 다른 시스템에 넘긴 것은 부모의 기장이고 사람이 읽는 것이 아니었다. 페이지는 원장과 같은 키셋이고, 범위 밖 limit 과 영역 밖 status 는 빈 페이지가 아니라 **거절**이며, 턴 0개는 빈 페이지지만 **없는 작업은 404**다(빈 페이지는 「아직 아무 일도 없다」로 읽혀 잘못된 id 를 가린다). 이관이 DB 를 쥐고 있는 동안의 읽기는 반쯤 복사된 페이지 대신 conflict 다. **새 작업의 이력은 그 턴들이다** — 커토버 뒤에 생긴 작업에는 원장 이력이 없고 만들어 내지 않으며, 지난 관리 이벤트를 턴으로 꾸미지 않는다. 옮겨진 작업의 원장 이력은 `/ledger/events` 에 그대로 남아 거기서 읽는다.
  5. **커토버 뒤에도 앱과 API는 그대로다.** 읽기 전용 뷰는 작업 레코드를 **원장 페이지와 같은 모양**으로 투영하고(보존된 기장을 그 모양의 독자가 기대하는 자리에 되돌려 놓는다) 사용자 요청 저장은 **다음 턴**이 되므로, 호출자는 응답만으로 이 슬롯이 옮겨졌는지 알 수 없다 — 그래서 이미지와 앱을 따로 배포할 수 있다. 투영된 `choice_id`는 자기가 나온 턴을 이름에 담으므로 **더 이상 최신이 아닌 턴의 선택지 선택은 거절**된다(AC-N8 3번과 같은 이유). 옮겨진 슬롯의 **원장 읽기는 유지되고**(모니터 행과 작업 이력은 거기에만 있다) **원장 쓰기는 쓸 작업 도구를 이름으로 알려 주며 `conflict`로 거절**된다 — 아무도 읽지 않는 행을 바꾸면 같은 일이 두 곳에 다른 답으로 존재한다. 되지 않는 배포 순서는 하나뿐이다: 옛 이미지에 작업 뷰를 기대하는 앱(404를 「작업 없음」이 아니라 「경로 없음」으로 읽는다).
  6. **롤백 가능하다.** 테이블은 가산적이고 `sp_ledger_meta`는 버전 1에 머문다 — 이 테이블을 모르는 이미지로 되돌려도 DB는 열리고 원장은 그대로 서빙된다(마이그레이션이 원장을 건드리지 않았으므로). 커토버 뒤에 쓴 작업은 원장에 없고, 원장에 **만들어 넣지도 않는다**. `sp_work_meta`는 이 네임스페이스의 버전을 들고, 더 높은 버전이 쓴 DB는 이 컬럼으로 읽지 않고 **거절**한다. 전체 복원은 3번의 스냅샷에서 오프라인으로 시작한다.
  7. **한 일은 뒤에서도 읽힌다.** 실행은 커밋 전에 자기 행 수를 검증하고, `work_migration_report`가 스키마 상태·적힌 모든 단계와 그 행 수·스냅샷 체크섬·지금 세어 본 현재 수를 준다(읽기는 아무것도 바꾸지 않는다). 옮겨진 DB에 `work_migrate`를 다시 부르면 `already_migrated`와 함께 그 보고를 돌려준다.
- **달성 가치**: V3(장기 세션), V1
- **구체화 대상**: AC-N6(슬롯 세션 DB와 읽기 전용 뷰)·AC-N7(사용자 요청)·AC-N8(선택지·이력) — 같은 경로의 기록을 합의한 두 엔터티로 옮기고, 그 경로를 그대로 유지한 것
- **검증 방법**: 데이터 플레인 단위 테스트로 합의한 컬럼이 **정확히 그 컬럼인 것**·task/turn CRUD와 version CAS·은퇴·DB 전역 턴 순서·열린 턴 큐·동시 쓰기의 단일 승자·replay·인자 검증·상위 스키마 버전 거절을 확인하고(`data-plane/cmd/agent/session_work_test.go`), 마이그레이션은 dry run이 아무것도 바꾸지 않는 것·원장이 적은 것만 옮기는 것·작업 시각이 기록된 이력에서 오는 것·살아 있는 선택지가 최신 턴에 붙는 것·빠진 레거시 행·손상된 DB 거절·멱등과 재개·펜스가 쓰기를 거절하는 것·스냅샷 없는 펜스 거절·사용자 테이블 불변·**원장이 롤백을 위해 그대로 남는 것**을 확인한다(`data-plane/cmd/agent/session_work_migrate_test.go`). 커토버는 앱 쪽에서 원장 쓰기 거절·읽기 유지·투영된 페이지와 요청→턴 경로·낡은 턴의 선택지 거절로 확인한다(같은 파일). 스냅샷 경로는 로컬 SQLite 파일로 시험하며 **슬롯 저장소에서의 배포 복원 리허설은 주장하지 않는다** — 그것은 머지·배포 뒤 검증이다.

### AC-N11: 매니저 파드의 두 레인 — 사람과 말하는 부모, 작업을 움직이는 모니터
- **설명**: `codex-manager` 세션 하나는 **사람의 채팅**과 **그 뒤의 작업**을 함께 맡는데, 그 둘은 타이밍이 맞지 않는다 — 부모는 사람에게 답을 쓰는 데 1분을 쓸 수 있어야 하고, 그 사이 벌여 둔 작업은 자기 시계(예약된 확인·회수할 결과·옮길 원장 행)로 돌봐야 한다. **턴은 직렬**이므로 대화 하나로는 둘을 못 한다. 그래서 파드가 **대화를 둘** 돌린다. 각 레인은 온전한 에이전트 워크로드다 — 자기 대화·자기 큐와 직렬 워커·자기 출력 버퍼(따라서 **자기 커서**)·자기 관리 설정과 도구 표면. 공유하는 것은 파드와 슬롯뿐이고, **서로의 대화는 보이지 않으며** 부모가 긴 답을 쓰는 동안 모니터의 워커가 멈추지 않는다.
  1. **한 세션·한 파드다 — 세션을 둘로 쪼개지 않는다.** 이유는 셋이고, 모두 이미 있는 계약에서 나온다. ① **작업 기록은 이 파드가 마운트한 슬롯에 있고**(AC-N6) 그 사이드카는 루프백에 바인드한다 — 파드를 둘로 하면 DB 사본을 둘 두거나 거기까지 네트워크 경로를 내야 하는데, 한 파드는 둘 다 필요 없고 **두 레인이 같은 사이드카로 같은 기록을 읽는다**. ② **슬롯의 로그인은 하나다**(AC-N4) — 한 슬롯에 파드 둘은 네트워크 파일시스템 위에서 한 파일을 쓰는 writer 둘이지만, 한 파드의 두 레인은 **한 프로세스의 잠금**을 지난다. ③ **세션은 control plane이 시작·동결·아카이브·삭제하는 단위다** — 채팅 하나에 세션 둘이면 그 각각이 둘이 되고, 스냅샷이 어느 쪽의 것인지 둘이 합의해야 한다. (`docs/monitor-separation.md`의 조사 결론 — 「지금 계약 위에서 **세션 분리**는 이득이 비용보다 작다」 — 는 그대로 유효하다. 이 AC는 세션 분리가 아니라 **한 파드 안의 실행 컨텍스트 분리**이며, 그 조사가 비용으로 꼽은 네 가지(원장 단일 원본·권한 축소 불가·알림 단일 담당·스킬 revision 분기)를 **지불하지 않는다**: 원장은 한 DB 그대로이고, 권한은 아래 3번처럼 플랫폼이 강제하며, 알림과 사람 보고는 부모에 남고, 스킬 집합은 파드 하나의 것이다.)
  2. **옵트인은 배포의 플래그 하나다.** 워크로드 컨테이너 env `MANAGER_MONITOR_LANE=1`(ConfigMap 키 `manager-monitor-lane`). `session-db-raw-sql`과 같은 이유로 **세션 생성 옵션이 아니다** — 매니저 파드가 무엇인지를 바꾸는 일이고, 채팅이 자기 자신의 두 번째 레인을 요구할 수는 없다. 없거나 `0`은 **레인 하나인 매니저**이고, 짝 도입 전에 만들어진 세션은 전부 그대로 그렇게 동작한다. `1`도 `0`도 아닌 값은 **파드 시작 실패**다 — 켜려다 오타 낸 배포가 「애초에 짝이 아닌 매니저」와 똑같이 보이면 안 된다. 레인은 `codex-manager`(와 구 `codex-chat`)의 것이며, 다른 타입에 요구하면 거절한다.
  3. **기록은 모니터가 쓰고 부모는 직접 읽는다 — 플랫폼이 강제한다.** 부모 레인의 도구 표면에 **기록 쓰기가 없다**(`task_put`·`task_delete`·`turn_append`·`turn_patch`·`turn_dispatch`·`task_book_put`·`monitor_put`·`monitor_delete`). 목록에서 빼는 것으로 끝내지 않고 **인자 앞의 가드**가 한 번 더 거절하며(옛 목록을 쥔 클라이언트), 거절문은 그 기록이 어느 레인의 것인지와 넘기는 방법을 이름으로 말한다. 반대로 **읽기는 부모가 직접 한다** — 같은 파드·같은 DB이므로 현재 원장을 보려고 모니터에게 물어볼 필요가 없고, 그것이 파드를 하나로 둔 이득이다. **이 분리는 스킬 문장이 아니라 주소로 성립한다**: 레인의 역할은 사이드카 MCP 주소(`/session-db/mcp/lane/<role>/<incarnation>`)에 있고, 그 주소는 플랫폼이 부팅마다 다시 쓰는 레인의 **관리 설정**에 있어 모델이 읽거나 바꿀 수 없다. 즉 부모 레인은 모니터로 호출할 **주소가 없다**. 레인 하나인 매니저는 표면 전체를 그대로 가진다 — 기록이 속할 다른 레인이 없으므로 좁히면 유일한 호출자에게서 쓰기를 빼앗는 것이다.
  4. **왕복은 직접 건넨 요청이고, 돌아오는 것은 접수 번호다 — 부모는 기다리지 않는다.** 부모는 사람의 요청을 **원문 그대로** 같은 파드의 사이드카에 넘기고(`lane_ask`), 사이드카는 그것을 모니터 레인의 **자기 큐에** 루프백으로 올린 뒤 그 레인이 발급한 **접수 번호**를 즉시 돌려준다. 부모의 턴은 사람의 턴이므로 **모니터의 답을 기다리며 막히지 않는다** — 막힌다면 대화이기를 그만둔 것이고, 레인을 둘 둔 이유가 바로 그것이다. 나중에 그 번호로 `lane_answer` 를 불러 **그 모니터 턴의 상태와 실제 답변**(queued·running·done + 그 턴이 쓴 출력과 종료 상태)을 받는다. 홉은 이미 파드에 있는 것뿐이다 — 사이드카는 슬롯 DB를 여는 유일한 프로세스이고(AC-N6) 두 레인이 모두 부르는 유일한 프로세스이며, 닿는 방법은 스케줄러가 이미 사람의 채팅에 쓰는 그 루프백 홉이다(AC-P2). 새 listener·control plane 홉·파드 밖에서 닿는 것이 늘지 않는다. **모니터에게는 이 두 도구가 없다** — 모니터의 답은 자기가 들어 있는 턴 그 자체이고, 여기서 부모의 턴을 시작시키면 말하지 않은 사람 앞에 글이 나타난다. **세션 간 요청함은 없다**: 레인 사이의 메시지 테이블(`sp_work_relay`·`sp_work_relay_claim`)과 `relay_send`·`relay_list`·`relay_claim`·`relay_ack`·`relay_status`, 그리고 그것을 돌리던 깨우기·재전달 절차는 이 설계에 없다.
  5. **같은 요청 재전송은 두 번째 턴이 아니다.** `lane_ask` 는 부모의 `request_id` 를 받는다. 같은 id·같은 원문은 **처음 발급된 접수 번호를 그대로** 돌려주고(`replayed: true`) 모니터에게 프롬프트를 다시 올리지 않으며, 같은 id·다른 원문은 **conflict** 다 — 답이 유실된 부모는 같은 호출을 다시 해서 자기가 이미 무엇을 했는지 배운다. 이 기억은 **그 런의 것**이다(사이드카 메모리): 접수 번호는 발급한 런에서만 뜻이 있으므로, 재시작을 건너 기억했다면 더 이상 풀 수 없는 번호를 돌려주게 된다.
  6. **접수 번호는 다른 턴의 답을 주지 않는다 — 네 갈래 모두.** 번호는 레인 자신의 것이고(발급한 **런**과 그 런의 **몇 번째 프롬프트**인지), 네 가지 섞임을 각각 막는다. ① **발급되지 않은 접수**: 번호는 그 책에서만 나오고, **큐에 들어가지 못한 요청에는 번호가 아예 발급되지 않는다**(거절은 접수 번호 없이 돌아온다) — 받은 적 없는 번호는 `absent` 다. ② **동시 요청**: 번호는 큐에 넣는 그 잠금 안에서 뽑으므로 원문이 똑같아도 **두 번호·두 항목**이 되고 겹칠 수 없다. ③ **이미 끝난 턴**: 항목마다 **자기 출력의 스크롤백 경계**를 턴 시작과 끝에 적어 두고, 런 안에서 스크롤백은 append-only 이므로 그 경계는 뒤에 몇 턴이 더 와도 같은 바이트를 뜻한다 — 요청 자체도 그 안에 들어가지 않는다(입력 표식 뒤부터가 답이다). ④ **재시작**: 번호 앞에 **런**이 붙고, 재시작한 레인은 새 런에 빈 책이고 번호는 1부터 다시 시작하므로 어제의 번호가 오늘의 첫 턴을 가리킬 수 있다 — 그래서 **런을 책보다 먼저 확인해** `unknown_run` 으로 답한다. `absent` 와 구별되는 이유는 호출자의 다음 행동이 다르기 때문이다. 책은 유한하므로 가장 오래된 항목은 버려지고 그 번호는 `expired` 로 답한다 — **이름 있는 거절이지 틀린 답이 아니다**. **재시작 시 미전달 요청의 자동 재전송은 보장하지 않는다**: 레인과 함께 사라진 요청은 사라진 채로 그렇게 말하고, 다시 물을지는 사람 앞에 있는 부모가 정한다.
  7. **모니터의 대화는 아카이브에 없다.** 모니터 레인의 상태 디렉터리는 아카이브되는 트리 **옆**에 둔다(env `MANAGER_MONITOR_STATE_DIR`). 그래서 스냅샷·복원·컨테이너 재시작은 모두 모니터를 **새 대화로** 시작시키고, 사람의 아카이브는 모니터의 대화를 싣지 않으며 체크포인트 중의 모니터 쓰기가 그 아카이브를 깨뜨리지 않는다. 의도된 것이다 — 모니터가 어디까지 했는지의 기록은 **슬롯 DB**(작업·턴 원장과 모니터 행)이고, 믿을 수 없는 대화를 들고 돌아온 레인도 결국 기록을 읽어야 제자리를 안다. 모니터 레인은 **복원 모드로 기다리지 않는다** — 기다릴 것이 없고, 기다리면 복원 내내 작업이 방치된다.
  8. **진입점은 세션의 것 그대로이고, 레인은 그 매개변수다.** 두 번째 세션 id도, 별도 라우트 묶음도 없다. `POST /api/v1/sessions/{id}/read`·`/write`의 본문과 `GET …/stream`의 질의에 `lane`(`parent`·`monitor`)이 붙고 **생략은 사람의 채팅**이다 — 레인을 모르는 클라이언트는 전에 보낸 것을 그대로 보내 전에 닿은 곳에 닿는다. 레인 아닌 값은 **거절**이고 채팅으로 조용히 떨어지지 않는다(오타가 「모니터를 보고 있다」는 착각이 된다). **레인마다 출력 버퍼가 다르므로 커서도 다르다** — 한 레인의 offset은 다른 레인에서 아무 뜻이 없다. 레인을 지목하면서 턴의 도구 호출을 세션 소유자에게 묻는 것(AC-E2)은 **둘 다 성립할 수 없으므로 거절**한다. 레인 하나짜리 워크로드에 `monitor`를 지목하면 501이고, 이는 「채팅이 없다」와 구분된다. 파드 안에서는 두 레인이 **같은 포트**에 있고(모니터는 `/monitor` 접두), 그 접두 아래에서 **자기 대화만** 서빙한다 — 접두 아래의 다른 경로는 부모 핸들러로 떨어지지 않고 이름으로 거절된다. 새 listener·새 Service·NetworkPolicy 변경이 없고, **파드 밖에서 닿을 수 있는 것이 늘지 않는다**.
  9. **오래 남는 것은 작업·턴 원장이다.** 접수 번호와 그 답은 **런 범위**다 — 답은 그 런의 스크롤백에 있고 모니터의 대화는 아카이브 밖이므로(7번), 재시작을 건너 남지 않는다. 그래서 **무엇을 결정했고 무엇이 됐는지는 모니터가 기존 SQLite 작업·턴 원장에 쓴다**(AC-N9의 `sp_work_tasks`·`sp_work_turns`와 그 영수증·CAS 계약 그대로), 그리고 **부모는 그것을 직접 읽는다**(3번). `lane_ask`/`lane_answer` 는 **턴을 시작시키고 그 턴의 답을 받는 길**이지 결과의 보관소가 아니다 — 보관소는 원장이고, 원장은 재시작·동결·복원을 건너 슬롯에 남는다(AC-N6).
  10. **짝이 한 파드에 있다는 것을 밖에서 확인할 수 있다.** `GET /api/v1/sessions/{id}/lanes`가 이 세션의 파드가 **실제로 돌리는** 대화와 그 각각이 있는 파드를 답한다. 목록은 **파드 자신의 답**(`GET /lanes`)에서 오고 control plane이 설정에서 조립하지 않는다 — 설정으로 만든 답은 두 번째 레인 시작에 실패한 파드를 「짝」이라고 말할 수 있다. 파드는 한 번에 자기 것만 답하므로, control plane이 돌려받은 모든 레인에 **세션의 파드를 찍는 것**이 주장이 아니라 사실이 된다. 이 읽기는 작업 읽기처럼 **수동적이다** — 스냅샷을 복원하지 않고 접근으로 세지 않으므로, 짝의 모양을 확인하는 독자가 파드를 깨우는 일이 없다(동결된 세션은 422).
- **달성 가치**: V3(장기 세션), V1
- **구체화 대상**: AC-N6(슬롯의 로그인과 세션 DB, 컨테이너마다 제 몫만)·AC-N9(작업 기록과 영수증 계약)·AC-C2/AC-C3(상태 분기 read·write) — 같은 파드·같은 슬롯·같은 세션 위에 실행 컨텍스트를 하나 더 두고, 기록의 쓰기를 그 중 한 쪽으로 좁힌 것
- **검증 방법**: 데이터 플레인 단위 테스트로 **두 레인이 실제로 동시에 도는 것**(두 run 이 동시에 활성 — 직렬 워커 하나로는 도달 불가)·서로의 대화와 커서가 분리된 것·`/monitor` 접두가 자기 대화만 서빙하고 나머지를 이름으로 거절하는 것·파드의 레인 목록·옵트인의 오타·잘못된 타입 거절·모니터 상태 디렉터리가 아카이브 밖인 것·레인 MCP 주소 유도와 파싱·incarnation 유일성을 확인한다(`data-plane/cmd/agent/manager_lane_test.go`). **접수 번호**는 네 갈래의 섞임을 각각 확인한다 — 거절된 쓰기가 번호를 발급하지 않는 것·같은 원문 두 요청이 다른 번호를 받는 것·앞 런의 번호가 `unknown_run` 이고 같은 번호의 이번 런 것은 정상 응답인 것·버려진 번호가 `expired`·받은 적 없는 번호가 `absent`·형식이 틀린 번호는 추측하지 않고 거절하는 것, 그리고 **세 턴을 실제로 돌려 번호마다 자기 턴의 답만 돌아오고 다른 턴의 말이나 자기 입력 표식이 섞이지 않는 것**·`/turn` 이 루프백 전용인 것(`data-plane/cmd/agent/turn_ticket_test.go`). **넘기기**는 부모 표면에 기록 쓰기가 없는 것·가드가 한 번 더 거절하며 `lane_ask`·`lane_answer` 를 이름으로 말하는 것·모니터와 레인 하나짜리 매니저에게 넘기기 도구가 없고 거절문이 그 이유를 말하는 것·재전송이 처음 번호를 replay 하고 프롬프트를 다시 올리지 않는 것·같은 id 다른 원문이 conflict 인 것·레인이 요청을 받지 않으면 **번호를 발급하지 않고 기억하지도 않는 것**·인자 검증, 그리고 **아무것도 모의하지 않은 통합**으로 「부모가 자기 턴 안에서 넘기고 즉시 번호를 받아 **턴을 놓지 않은 채** 모니터가 원문 그대로의 요청으로 돌고, 원장을 쓰고, 부모가 그 번호로 그 턴의 답을 읽고 원장을 직접 읽는 것」을 확인한다(`data-plane/cmd/agent/session_work_lane_test.go`). 슬롯은 HOME 마다 턴 상태가 따로인 것과 **느린 레인이 빠른 레인의 갱신을 덮지 않는 CAS**를 확인한다(`data-plane/cmd/agent/auth_slot_lane_test.go`). control plane 은 레인 호출이 자기 경로에 닿는 것·레인 아닌 값이 요청 전에 거절되는 것·목록이 파드에서 오는 것(`internal/adapter/agent/lane_test.go`), 레인 read 가 다른 read 처럼 복원하고 stream 은 수동적인 것·목록이 세션의 파드를 찍는 것·레인+도구승인 거절(`internal/service/lane_test.go`), 그리고 **정상 진입점**에서 `/lanes` 가 한 파드를 말하는 것·수동성·레인을 지목한 write 가 그 레인에 닿고 서로 새지 않는 것·커서 분리·오타 400·레인+도구승인 400·레인 하나짜리 타입 501 을 확인한다(`internal/api/lane_test.go`). **실 파드**에서는 정상 생성 경로가 만든 한 파드에서 짝의 env 배선·`/lanes`·각 레인의 관리 설정에서 읽은 실제 MCP 주소·역할별 표면·`lane_ask` 가 **기다리지 않고** 번호를 돌려주는 것·재전송 replay·**모니터 레인의 버퍼에 요청 원문이 나타나는 것**·**두 레인이 동시에 턴 중인 것**·앞 런/미발급 번호의 거절·부모 쓰기 가드·모니터가 쓴 원장을 부모가 읽는 것·레인별 버퍼 분리를 확인한다(`control-plane/test/e2e_auth_pool_9_lane_pair_test.go`). **실모델 턴은 주장하지 않는다** — 이 SUT 에 구독 로그인이 없고(AC-J3) 로그인 없는 CLI 는 멈춰 서므로, 번호가 `done` 에 이르러 모델의 실제 답을 담는 것은 턴이 끝나는 단위 테스트가 소유한다. **운영 적용은 머지·배포 뒤 검증이다.**

### AC-N13: 사람이 판단하는 상태는 `review` 하나다 — 옛 `blocked` 는 입력의 별칭이고 출력의 판정이다
- **설명**: 작업 상태에 `blocked` 와 `review` 가 함께 있었는데, 둘은 같은 사실 — 「사람이 설정해 줘야 움직인다」 — 을 두 이름으로 말하고 있었다. 그래서 읽는 쪽은 전부를 보려면 둘을 다 물어야 했고, 쓰는 쪽은 상대가 무엇으로 걸러 볼지 짐작해야 했다. **하나로 접는다: `review`.** 대신 세울 **새 상태도, 새 칩·분류도 없다** — 한 사실의 둘째 이름이 문제였으므로 셋째를 만들면 같은 일이 반복된다. 「대기」·「차단」도 동급·하위 상태로 추가하지 않는다.
  1. **접는 것은 개명이 아니다.** 개명은 사람이 이미 본 작업을 움직이고, 일괄 UPDATE 는 운영 DB 를 고친다. 그래서 `blocked` 는 두 가지가 된다 — **입력에서 별칭**(필터·`task_put`·HTTP 질의에서 받아들이고 `review` 로 읽는다. 옛 writer 와 저장해 둔 필터가 그대로 동작하고, 그 말로 **새로 저장되는 행은 없다**. `task_put` 의 답이 `alias_applied` 로 무엇이 착지했는지 말한다), **출력에서 판정**(옛 이미지가 그 말로 적어 둔 행은 **디스크를 고치지 않고** 옆에 이미 있는 근거로 제 상태를 가려 답한다. `blocked` 로도 `unknown` 으로도 답하지 않고 페이지에서 빠지지도 않으며, 저장된 바이트와 무엇이 그렇게 읽었는지가 `stored_status`·`status_basis` 로 **함께 간다**). 스키마 변경·새 테이블·마이그레이션이 **없다**.
  2. **판정은 일괄 매핑이 아니다 — 한 낱말 밑에 서로 다른 둘이 있다.** 눌러 버리면 **없는 결정을 사람 앞에 만들거나**, **아무도 승인하지 않은 일을 조용히 재개**한다. 그래서 근거로 가른다. ① 두 statement 가 어긋나면 **review**(어긋남은 깨뜨릴 동점이 아니다). ② 기록된 미해결 결정(`details.review`)이면 **review**. ③ 아무도 닫지 않은 턴의 질문이 있으면 **review** — 사람이 실제로 본 것이 어떤 기장보다 분명한 근거다. ④ `details.technical_wait` 가 대기의 모양이 아니면 **review** + 무엇이 없는지. ⑤ `details.technical_wait` 가 **owner·due·retry** 를 전부 구조화해 말하면 **running** — `running` 으로 가는 유일한 길이다. ⑥ 아무 말도 없으면 **review**: 모호한 경우이고, 기술 재개도 없는 질문의 발명도 하지 않고 「근거 없음」이라고 답한다. **산문도, 그렇게 읽히는 문자열도 근거가 아니고**, 어긋난 모양은 추측하지 않고 **보고**한다(AC-N12 의 취소 백필과 같은 규칙).
  3. **필터·정렬·집계의 정규화는 페이지를 자른 뒤다.** `status` 필터는 **읽는 쪽이 보는 상태**로 고른다. 이미 자른 페이지를 후처리로 걸러 내면 짧은 페이지가 나오고 건너뛴 행이 조용히 사라지므로, 쿼리는 그 상태로 **판정될 수 있는 모든 행**을 고르고 판정은 돌아온 행 위에서 하며, **페이지가 찰 때까지 이어 읽는다**. 커서는 여전히 id 이고 앞으로만 가므로 이어 읽기는 건너뛴 행을 다시 읽고 다시 건너뛴다 — 넘어가지 않는다. 스캔 상한에 걸려 짧게 끊긴 페이지는 **빈 커서가 아니라 커서를 들고** 돌아온다(상한은 페이지를 들지 행을 잃지 않는다). 상태들은 작업 집합을 **분할**한다 — 레거시 행까지 포함해 모든 작업이 정확히 하나에 속하므로, 상태를 하나씩 훑으면 모든 작업을 한 번씩 본다(중복도 누락도 없다). 동등 별칭(`blocked`)은 `review` 와 **같은 집합**을 고른다.
  4. **`review` 를 드나드는 것은 전용 호출이다.** 상태만 쓰는 것은 쉬운 절반이고, `review` 를 뜻있게 만드는 것은 **정확한 대상·범위·공식 승인 경로·사람이 답할 수 있는 질문·근거**가 같은 트랜잭션에 함께 착지하는 것이다. `task_review_open`(→ review, **출발 상태를 가리지 않는다**)이 그것을 **같은 논리 턴에** 기록하고 옮기며, 질문은 **축자 저장**된다(꾸미지 않는다). `task_review_resume`(review → running)은 **무엇으로 확인했는지**(`outcome.evidence`)와 **남은 일**(`outcome.remaining`)을 요구하고, 둘 중 하나라도 비면 거절되어 **작업은 review 에 머문다** — 보류·승인 미적용은 review 다. `task_review_complete`(review → completed)는 **최종 결과 수락 + 작업 자신의 완료 기준 축자 일치 + 남은 것 없음 + 열린 요청 0 + 미적용 결정 없음**을 모두 요구한다. 이 셋은 `review` 를 드나드는 **완전한 길**이지 평범한 상태 쓰기를 둘러싼 울타리가 **아니다** — `task_put` 은 도메인 안의 어떤 상태든 그대로 쓴다(10번). 셋이 더하는 것은 상태가 뜻을 갖게 하는 **기록**이고, 울타리 없이 쓴 `review` 는 **아무도 결정을 기록하지 않은 작업**이며 읽는 쪽에 보이는 것도 정확히 그것이다(묻는 것 미기록). **판단이 필요 없던 기승인 정상 완료 경로는 planned → running → completed 그대로**다.
  5. **같은 승인을 두 번 만들지 않는다.** 같은 `target·scope·route` 를 다시 물으면 둘째 승인이 아니다 — `already_open` 으로 **아무것도 쓰지 않고 카운터도 올리지 않는다**(다른 `request_id` 여도, 사람이 새 요청을 남긴 뒤여도). 이 판정은 **카운터를 집기 전에** 하므로 낡은 값을 쥔 부모가 경합으로 승인을 쌓을 수 없다. 열린 승인이 있는데 **다른** 결정을 물으면 conflict 다 — 한 작업에 사람이 들고 있는 열린 결정은 하나다. **중간 `blocked` 쓰기는 없다**: running → review 는 한 번의 쓰기이고, 그 사이에 다른 상태를 거치지 않는다.
  6. **「선택지를 눌러 초안 채움」·「제출」·「모니터가 읽고 running」은 별개다.** 누르는 것은 요청 칸을 채우는 것이고(권한이 아니다, AC-N8), 제출은 요청 경로로 **턴 하나**가 되며 **상태를 건드리지 않는다**(AC-N7 의 수동성 그대로). running 으로 옮기는 것은 모니터가 내용을 확인하고 실제 권한 적용·CI·머지 결과 같은 전제와 이어갈 일을 확인한 뒤 부르는 `task_review_resume` 다.
  7. **기술 대기는 running 에 머문다.** CI 가 진행 중이거나 정책상 자동 재시도가 허용된 대기는 **아무에게도 질문이 아니다** — 그것을 review 에 두면 없는 결정을 사람 앞에 만든다. 그 근거(owner·due·재시도 조건)는 `task_book_put` 의 `details.technical_wait` 에 유지되고, 그 레인은 작업 version 을 움직이지 않으므로 대기를 적는 것이 화면을 무효화하지 않는다. `task_review_open` 은 `route` 와 `question` 을 요구하므로 기술 대기로는 모양 자체가 통과하지 않는다.
  8. **보존.** 과거 `blocked` 의 원인·근거, 이력·턴·선택, 승인 대기, owner/CAS, cursor 와 dispatch receipt 는 전부 그대로다. 어느 호출도 턴의 `request`·`instruction`·`response`·`explanation` 과 `ended_at` 을 바꾸지 않는다(원천 이력 비변경). 덮어쓰는 승인 기록은 `details.review_history` 로 **누적**되고, 레거시 행을 resume/complete 할 때는 **저장된 낱말과 그것을 읽은 근거**가 그 항목에 들어간다 — 그러지 않으면 왜 붙잡혀 있었는지의 유일한 기록이 지워진다. 읽을 수 없는 JSON 기장은 **덮지 않는다**(유일한 사본일 수 있다).
  9. **상태 값에 전이 제약을 두지 않는다 — 그것이 합의한 계약이다.** 작업 레코드는 **전체 교체 + version CAS** 로 쓰이고, 목표 상태 문서가 이름 붙인 **정정**이 그 성질에 기대고 있다: 사용자가 결정한 적이 없는데 `completed` 로 적힌 작업을, 사용자가 정정을 명시하고 모니터가 턴 기록을 대조하면 `review` 로 **바로잡는다**. 다이어그램에 화살표가 없는 이유가 그것이고(정상 흐름이 아니다), 여기에 게이트를 두면 그 정정이 **없던 상태를 한 번 거쳐야만** 닿는 길이 된다. 그래서 `task_put` 은 주어진 상태를 쓰고, `task_review_open` 은 **`completed` 를 포함한 어떤 출발 상태도 받는다** — 정정이야말로 사람의 진술과 모니터의 대조를 함께 실어야 하는 이동이므로, 증거를 나르는 호출을 거부하면 증거가 사라진 바에서만 정정할 수 있게 된다. 전이의 규율은 모니터의 몫이고(운영 구성), 플랫폼의 몫은 그 기록이 함께 착지하게 하는 것이다.
  10. **등록은 아무것도 합성하지 않는다.** `task_put` 한 번이 쓰는 것은 **작업 행과 그 영수증 둘뿐**이다 — 기장·카운터·출처·턴·claim·dispatch·모니터 행은 전부 0건이고, 실행을 금지하는 플래그 같은 레코드는 **존재하지도 합성되지도 않는다**(합의한 컬럼만 있는 테이블이므로 들어갈 자리가 없다). `planned → running` 과 `running → completed` 는 `task_put` 하나로 되고 추가 착수 승인·토큰·두 번째 호출을 요구하지 않는다. 일반 기능 추가에 `execution_authorized:false` 류의 값을 만들지 않는다는 뜻이고, 도구 표면에도 그런 인자가 없다.
  11. **플랫폼이 못 하는 것을 적는다.** 승인이 바깥에서 **실제로** 적용됐는지는 이 플랫폼이 볼 수 없다. 할 수 있는 것은 ⑴ 확인을 **이름으로 요구**하고 ⑵ 그 이름을 작업 옆에 남기고 ⑶ 추측으로는 작업을 옮기지 않는 것뿐이다. 검증하는 척하는 게이트는 무엇을 검사하는지 말하는 게이트보다 나쁘므로, 이 한계는 코드 주석과 이 AC 에 함께 남긴다. 버전 불일치도 같은 정직함을 따른다 — control plane 은 별칭을 **풀지 않고 호출자의 낱말을 그대로** 슬롯에 보낸다. 이 이미지보다 옛 데이터 플레인은 `blocked` 가 아직 제 상태이므로, `review` 로 바꿔 보내면 호출자가 찾던 행을 바로 놓친다.
- **달성 가치**: V1, V3(장기 세션)
- **구체화 대상**: AC-N9(작업 기록의 상태 도메인과 CAS 레인)·AC-N7(요청의 수동성)·AC-N8(선택지는 권한이 아니다)·AC-N11(기록은 모니터가 쓴다) — 상태 하나를 줄이고, 그 하나를 드나드는 길에 근거를 요구한 것
- **검증 방법**: 데이터 플레인 단위 테스트로 **세션의 실제 `db` MCP(tools/call)와 사이드카 루프백 뷰·요청 POST 를 실제로 밟아** 다음을 확인한다 — 도메인에 옛 낱말이 없는 것, `task_put` 의 별칭이 `review` 로 저장되고 답이 그렇게 말하는 것, 필터·뷰가 별칭을 받고 **같은 집합**을 고르는 것, 도메인 밖 상태의 거절(도구 `invalid_argument`·뷰 400), `task_put` 이 **양방향으로 전이 제약 없이** 쓰고 새 낱말이 별칭보다 불리하게 다뤄지지 않는 것(울타리 없이 쓴 review 는 기장을 남기지 않는다), `completed` 로 잘못 적힌 작업이 **한 번의 `task_review_open`** 으로 근거를 실은 채 review 로 정정되고 턴은 그대로인 것, **등록이 작업 행과 영수증 둘만 쓰고 나머지 레코드가 모두 0건인 것**·`planned → running → completed` 가 `task_put` 만으로 되는 것·도구 표면에 권한 인자가 없는 것, 옛 이미지가 적은 `blocked` 행 일곱 가지(침묵·기록된 결정·완전한 기술 대기·불완전한 기술 대기·어긋남·산문·열린 질문)가 각각 제 상태와 근거로 답하고 **디스크가 그대로인 것**, 이 이미지가 쓴 행에는 호환 필드가 **없는 것**, 같은 판정이 사이드카 작업 페이지·턴 페이지에 **같게** 도달하는 것, 상태들이 작업 집합을 **분할**하고 여러 페이지·limit 1 의 리필 경로에서도 중복·누락이 없는 것, 꽉 찬 페이지의 커서와 마지막 페이지의 빈 커서, 승인 개설의 축자 질문과 **동일 승인 재요청의 `already_open`**(카운터·version 불변)·다른 결정의 conflict, **제출된 요청이 상태를 옮기지 않는 것**, 증거·남은 일 없는 resume 의 거절과 review 유지, 완료의 다섯 검사(미수락·다른 기준·남은 일·열린 요청·미적용 결정)와 정상 완료, 레거시 행의 resume·open 이 **저장된 낱말과 근거를 이력에 남기는 것**, 기술 대기가 running 에 머물며 근거를 유지하고 기장 레인이 작업을 움직이지 않는 것, 기승인 정상 경로가 `task_put` 만으로 planned → running → completed 인 것, 경합에서 **한 승자**와 패자의 재시도가 승인·턴을 중복시키지 않는 것·낡은 카운터의 거절·`request_id` replay, **격리 DB 를 닫고 다시 열어도 스키마 버전·레거시 바이트·페이지가 그대로인 것**(멱등), 읽을 수 없는 기장이 그대로 남고 그 행이 사람 쪽으로 답하는 것(`data-plane/cmd/agent/session_work_review_test.go`, `session_work_test.go`, `session_db_mcp_test.go`). control plane 은 **정상 진입점**에서 통합된 도메인·별칭 필터의 200·도메인 밖 400 과 `stored_status`·`status_basis` 가 독자에게 도달하는 것을 확인한다(`control-plane/internal/api/work_test.go`). **운영 DB 에는 어떤 마이그레이션도 돌리지 않았다** — 판정은 읽기이고, 격리 fixture DB 왕복만 검증했다. 운영 적용은 머지·배포 뒤 검증이다.

### AC-N5: 권한 — control plane은 PVC·Lease만, 세션은 자기 슬롯만
- **설명**: control plane Role은 이미 가진 `persistentvolumeclaims` create/get/list/watch와 `leases` 전체 동사로 풀을 다룬다 — 새 권한이 없다. 세션 파드는 자기 슬롯 PVC 하나만 마운트하고, 다른 슬롯에 닿는 Kubernetes 자격 증명을 받지 않는다(타입별 SA 권한은 바뀌지 않는다). 슬롯 파일은 셸이 있는 주 컨테이너가 읽을 수 있다 — 프록시로 숨기지 않기로 했다(2026-11-07 사용자 결정): 세션 안 에이전트가 그 계정의 토큰을 읽을 수 있다는 것이 이 풀의 알려진 대가다.
- **달성 가치**: V1
- **구체화 대상**: AC-A1/A2의 세션 격리
- **검증 방법**: 제출된 pod spec에 PVC 볼륨이 자기 슬롯 하나뿐임을 확인한다. `deploy/base/rbac.yaml`이 바뀌지 않음을 확인한다.

## 결정 사항 (2026-11-07, 사용자)
- **독점 임대**: 공유(슬롯 파드 하나가 혼자 갱신하고 세션은 프록시로 부름)는 로그인 파일을 세션 컨테이너에 두는 방식과 함께 쓸 수 없어 고르지 않았다.
- **로그인 파일은 세션 컨테이너에 마운트**: 프록시로 숨기지 않는다(AC-N5의 대가).
- **슬롯 저장소는 PVC**: Secret에 되쓰는 사이드카와 RBAC가 필요 없다. 운영은 `efs`(RWX)라 노드에 묶이지 않는다.
- **빈 슬롯은 첫 세션이 로그인**: 운영자 전용 로그인 API를 두지 않는다.

## 결정 사항 (2026-11-09, 사용자)
- **`codex-manager`도 풀을 쓴다**: 세션 DB를 둘 PVC가 필요했고, 따로 PVC 종류를 만들지 않고 로그인과 함께 슬롯에 담는다. 채팅은 장기 단일 세션 기준이지만 확장을 생각해 슬롯 단위로 둔다(AC-N6).
- **세션 DB는 슬롯에 남는다**: 슬롯을 다음 세션이 받으면 DB도 이어받는다 — 새 세션이라고 비우지 않는다.
- **기존 세션은 다시 로그인**: 슬롯 도입 전 `codex-manager` 세션의 로그인은 아카이브된 HOME에 있지만 슬롯으로 옮기지 않는다. 빈 슬롯은 AC-N4 1번대로 HOME의 로그인을 지우고, 다음 프롬프트가 로그인 흐름을 돈다.
- **슬롯 0이면 타입을 내놓지 않는다**: `codex-task`와 같은 규칙. 운영은 1이다.
- **DB 도구는 raw 두 개**: `raw_query`·`raw_exec`만 둔다. 도메인 도구는 쓰임이 정해지면 그때 더한다. *(2026-11-16 개정: 원장 도구가 들어선 뒤 raw 둘은 디버그 전용이 됐다 — 아래 결정 참고)*

## 결정 사항 (2026-11-16, 사용자)
- **raw SQL은 디버그 전용**: 채팅 세션의 기본 DB 표면은 버전이 있는 원장 네 도구다. `raw_query`·`raw_exec`는 기본으로 보이지도, 불러지지도 않는다. 원장이 쓰임을 가져간 뒤로 raw는 그 스키마를 우회해 깨뜨릴 수 있는 길이기도 해서, 평소에 모델이 볼 이유가 없다.
- **옵트인은 배포의 명시적 플래그 하나**: 사이드카 env `SESSION_DB_RAW_SQL=debug`(ConfigMap 키 `session-db-raw-sql`). 세션 생성 옵션도, 모델이 부를 수 있는 전환 도구도 두지 않는다 — 디버깅은 사람이 배포를 만지는 일이다.
- **원장 API는 그대로**: 도구·인자·오류 코드·`sp_ledger_*` 스키마는 바뀌지 않는다. 옵트인 여부는 원장 동작에 닿지 않는다.

## 남은 일
- 슬롯 이용률·로그인 상태를 보여 주는 운영 화면은 없다. Lease 주석과 `kubectl get lease -l session-platform.dev/auth-pool`로 본다.
- 실 계정 로그인과 그 뒤의 토큰 갱신은 e2e로 검증하지 않는다 — 사람의 브라우저 승인이 필요하다.
