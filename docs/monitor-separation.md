# 조사·설계: 배경 모니터를 API 프로세스에서 분리할 것인가

> **상태: 조사·설계만.** 구현도, 운영 변경도 이 문서에 없다. 결정은 사용자의 몫이고,
> 아래 「결정이 필요한 것」이 그 목록이다. 코드·매니페스트·예약은 하나도 건드리지 않았다.
>
> 조사 시점의 HEAD: `work/codex-manager-rename` (PR #252), main `c0f4d1d` 기준.

## 1. 지금 무엇이 돌고 있나 (실측)

control plane 프로세스 하나가 **HTTP API와 배경 모니터를 함께** 안고 있다. 모니터는
타이머 하나에 세 책무가 묶여 있는 **단일 루프**다.

| 책무 | AC | 어디 |
|---|---|---|
| 유휴 → 스냅샷 트리거 | AC-B1 · AC-D5 · AC-A3 | `control-plane/internal/service/reaper.go` `IdleReaper.Run`/`ScanOnce` |
| 파드를 잃은 세션 해소 | AC-C5 · AC-B5 | 같은 `ScanOnce` 안의 `lostPodReconciler` |
| 살아 있는 파드의 자동 아카이브 URL 갱신 | AC-B5 | 같은 `ScanOnce` 안의 `autoArchiveRefresher` |

- 기동: `control-plane/cmd/control-plane/main.go` — `NewIdleReaper(mgr, session.MaxIdle, cfg.idleScanInterval, …)`
  를 만들고, `snapshotEnabled`일 때만 `go reaper.Run(ctx)`. 아카이브 전략이 하나도 없으면
  「idle reaper disabled」 경고만 남기고 띄우지 않는다.
- 주기: 설정 `idleScanInterval` 하나. 세 책무가 같은 주기를 공유한다.
- 종료: API 서버와 **같은 `ctx`** — SIGTERM 하나가 둘을 같이 내린다.
- 배치: `deploy/base/deployment.yaml`의 `replicas: 1`. 즉 지금 모니터가 하나뿐인 것은
  설계가 보장해서가 아니라 **레플리카가 1이기 때문**이다.
- 안전망: 세션 상태 전이는 점유 토큰을 쥐고 일어나고(`store.Renew(ctx, id, token)`),
  긴 스냅샷은 그 Lease를 갱신하며 돈다(`service/manager.go` `renewLeaseContext`).
  따라서 모니터가 둘로 겹쳐 돌아도 **데이터가 깨지지는 않는다** — 늦게 온 쪽의 전이가
  버려질 뿐이다. 겹침은 안전 문제가 아니라 낭비·로그 소음 문제다.

## 2. 왜 분리를 검토하나 (관찰된 결합)

1. **API를 2개 이상으로 늘릴 수 없다.** `replicas`를 올리는 순간 모니터도 같이 복제된다.
   깨지지는 않지만(1절 안전망) 스캔이 N배로 돌고 「누가 전이를 가져갔나」가 로그에서
   흐려진다. 즉 지금 `replicas: 1`은 가용성 선택이 아니라 **모니터가 묶여 있어서 생긴 제약**이다.
2. **배포 단위가 하나다.** 스캔 주기 하나를 바꾸려도 API를 재시작한다. 반대로 API 수정
   배포가 진행 중인 스캔을 끊는다.
3. **장애 반경이 겹친다.** 스캔이 느린 Kubernetes 호출에 묶이면 같은 프로세스의 고루틴·
   메모리를 쓴다. 반대로 API가 OOM으로 죽으면 모니터도 같이 죽는다 — 이 세션 자체가
   2026-11-17 08:52 OOM으로 그 모양을 한 번 보여 줬다.
4. **관측이 섞인다.** 모니터 로그와 요청 로그가 한 스트림이라, 「스캔이 몇 번 돌았나」를
   요청 로그에서 골라내야 한다.

## 3. 분리가 요구하는 것

- **단일성 보장.** 지금은 레플리카 수가 그 역할을 한다. 분리하면 그 보장을 명시해야 한다 —
  별도 Deployment `replicas: 1`이든, Lease 기반 리더 선출이든.
- **포트 공유.** 모니터는 `session.Manager`(= 상태 저장소 + 오케스트레이터 + 아카이브)에
  그대로 의존한다. 분리된 프로세스도 같은 어댑터·같은 RBAC·같은 ConfigMap/Secret을 받아야
  한다. 즉 **새 바이너리가 아니라 같은 바이너리의 다른 모드**가 비용이 가장 낮다.
- **설정 분할.** `idleScanInterval`·아카이브 켬/끔 플래그는 모니터 쪽으로, 주소·타임아웃은
  API 쪽으로 갈린다. 지금은 한 `config`에 섞여 있다.
- **멱등성 재확인.** `ScanOnce`의 세 책무는 이미 「다시 돌아도 같은 결과」여야 하지만,
  분리하면 **겹쳐 도는 구간이 배포 중 상시로 생긴다**(구 파드와 새 파드). 1절의 점유 토큰이
  그걸 받아 주는지가 분리 가능성의 핵심 전제다.

## 4. 선택지

### A. 같은 프로세스 유지 + Lease 리더 선출
모니터 루프를 리더만 돌린다. API는 전부 돈다.
- 👍 API를 N개로 늘릴 수 있다. 매니페스트는 하나로 유지. 코드 변경이 가장 작다.
- 👎 「모니터를 따로 재시작·따로 롤아웃」은 못 한다. 장애 반경·관측 분리도 안 된다.
- 비용: `coordination.k8s.io` Lease 하나와 리더 루프. 이 레포에는 이미 Lease를 쓰는
  코드가 있다(인증 풀 슬롯) — 패턴을 새로 들여오지 않는다.

### B. 별도 Deployment `control-plane-monitor` (`replicas: 1`), 같은 바이너리의 `--mode=monitor`
- 👍 API 스케일아웃·독립 롤아웃·독립 자원 한도·로그 분리를 모두 얻는다. 단일성은
  `replicas: 1`로 지금과 같은 방식으로 유지된다(새 메커니즘 없음).
- 👎 매니페스트·RBAC·설정이 둘로 늘어난다. 「모니터가 안 떴다」는 새 실패 모드가 생기므로
  그걸 보는 알림이 필요하다. 배포 중 구/신 파드가 겹쳐 도는 구간이 상시화된다(3절 전제).
- 비용: 모드 플래그 + `deploy/base`에 Deployment 하나 + 두 모드의 설정 분기.

### C. 책무별 CronJob
- 👍 가장 단순한 운영 모델. 겹침을 `concurrencyPolicy: Forbid`로 막는다.
- 👎 세 책무의 주기가 분당보다 촘촘해야 할 때 맞지 않고, 매 실행이 저장소·클러스터 연결을
  새로 맺는다. `autoArchiveRefresher`는 살아 있는 파드를 따라가는 성격이라 특히 안 맞는다.

## 5. 권고

**B를 목표로, A를 먼저 둘 가치는 없다.** 분리를 검토하게 만든 네 가지 결합(2절) 중
A가 푸는 것은 1번 하나뿐이고, 2·3·4번은 그대로 남는다. B는 네 개를 다 풀면서 단일성을
**지금과 같은 방식**(`replicas: 1`)으로 유지하므로 새 합의 메커니즘을 들이지 않는다.

다만 B의 전제는 3절의 멱등성이다. 그래서 **순서는 「검증 먼저」**를 권한다:

1. `ScanOnce`를 겹쳐 돌려도 결과가 같은지 테스트로 고정한다(같은 세션 집합에 대해 두
   스캔을 동시에 돌려, 전이가 한 번만 일어나고 늦은 쪽은 점유 토큰에서 깨끗이 지는 것).
   이건 분리와 무관하게 **지금도 참이어야 하는 성질**이므로, 분리를 하지 않아도 남는다.
2. 그 테스트가 초록인 뒤에 모드 플래그와 Deployment를 더한다.
3. 롤아웃은 `replicas: 1` → 모니터 Deployment 추가 → API의 모니터 기동 제거 순서로,
   중간 단계에서 **둘이 같이 도는 구간을 일부러 통과**시켜 1번의 가정을 실물로 확인한다.

## 6. 결정이 필요한 것 (사용자)

- 분리를 할 것인가, 한다면 A/B/C 중 무엇인가.
- API 레플리카를 2 이상으로 올릴 계획이 있는가 — 없다면 2절 1번의 무게가 줄고, B의
  근거는 2·3·4번만 남는다.
- 모니터가 떠 있지 않은 것을 무엇으로 알아챌 것인가(알림 경로). 이것이 없으면 B는
  「조용히 안 도는」 실패를 새로 만든다.
- 이 조사 문서를 PRD로 승격할지, 설계 노트로 남길지.

## 7. 이 문서가 하지 않은 것

- 코드·매니페스트·예약·테넌트·flux 설정 변경 **없음**.
- 성능 수치 측정 **없음** — 2절 3번의 자원 결합은 구조에서 읽은 것이고, 실측 프로파일이
  아니다. 수치가 결정에 필요하면 별도 작업으로 재야 한다.
- 겹침 멱등성의 **실증 없음** — 5절 1번이 그걸 세우는 일이고, 아직 하지 않았다.
  1절의 「안전하다」는 점유 토큰 코드를 읽은 결론이지 테스트로 고정된 성질이 아니다.
