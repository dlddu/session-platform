# 조사·설계: 매니저 세션의 30분 작업 모니터를 별도 에이전트 세션으로 분리할 것인가

> **상태: 조사·설계만.** 분리 구현·운영 DB·예약·세션 변경은 **하지 않았다**. 결정은 사용자의 몫이다.
>
> **범위 오해 정정 (2026-11-17).** 이 문서의 첫 판은 control plane 안의 `IdleReaper`
> (유휴→스냅샷·파드 유실 해소·자동 아카이브 갱신 루프)를 API 프로세스에서 떼어내는 문제를
> 다뤘다. **그건 사용자가 요구한 대상이 아니다.** 실제 대상은 **PocketAide 채팅
> (`codex-manager`) 세션의 부모가 직접 돌리는 30분 작업 모니터**를 별도 **에이전트 세션**으로
> 분리하는 것이다. `IdleReaper` 분리는 성격이 다른 **별도 주제**이고, 이 조사의 완료로
> 세지 않는다(그 판의 내용은 이 문서에 남기지 않았다 — 필요하면 새 문서로 다시 세운다).

조사 범위: `plugin-marketplace`(스킬 계약) · `session-platform`(플랫폼 계약) ·
`homelab-k3s-mcp`(도구·인증) · `pocket-aide`(알림 수신). 아래 근거는 모두 읽은 파일의 인용이다.

## 1. 지금 모니터는 무엇인가 (근거)

- **부모가 직접 돌린다.** `plugin-marketplace/skillset/task-monitoring-lifecycle/SKILL.md`
  첫 문단: 「현재 부모가 실행한다. **새 관리 세션을 만들지 않는다.**」 모니터는 부모
  (= PocketAide 채팅의 `codex-manager` 세션) 자신의 턴에서 실행된다.
- **주기.** 같은 스킬의 `references/cadence.md`는 사용자가 지정한 「단일 30분 통합모니터」를
  `monitor.cadence`에 기록해 **PT30M**로 적용하고, 지정이 없으면 상태별 기본값
  (개발 진행 10~20분, CI 임박 3~5분, 일시 장애 15→30→60분)을 쓴다. 즉 30분은 **기본값이 아니라
  사용자 지정 통합 주기**다.
- **예약 메커니즘.** self-paced `loop_create`(interval 생략) → 매 run 끝에 `loop_next({id, delay})`,
  중지는 `schedule_cancel`, 대조는 `schedule_list`. delay는 1분~24시간, loop 수명 상한 P7D.
  플랫폼 쪽 계약은 `session-platform/docs/prd/session-scheduler.md` AC-P1~P3(세션 사이드카의
  `scheduler` MCP).
- **모니터 원장.** 작업/세션 상태와 **분리된** monitor 레코드(안정 ID·owner·generation·
  desired/observed_state·operation·transitions)를 세션 SQLite에 둔다
  (`task-monitoring-lifecycle/references/monitor-record.md`, 공통
  `task-session-lifecycle/references/sqlite-ledger.md`).

## 2. 요구 ↔ 근거 대응표

| 사용자가 요구한 조사 축 | 지금의 실제 계약 (근거) | 분리했을 때 생기는 문제 |
| --- | --- | --- |
| **main↔monitor 인증 통신** | 세션 간 통신 수단은 k3s MCP의 `session_read`/`session_write`뿐이다. 그 서버는 control plane에 **투영 ServiceAccount 토큰**으로 인증한다 — `homelab-k3s-mcp/internal/sessionplatform/sessionplatform.go:295·306·725`(`SESSION_PLATFORM_TOKEN_FILE` → `Authorization: Bearer`), 거절 메시지는 「control plane refused **this server's tenant identity**」(:734). 즉 신원은 **서버/테넌트 단위**이고 세션 단위가 아니다. | 모니터 세션은 부모와 **같은 테넌트 권한**을 갖는다. 「모니터는 읽기만」 같은 축소 권한을 **플랫폼이 강제할 수 없다** — 스킬 문장으로만 제한된다. 분리의 보안 이득은 0에 가깝고, 반대로 감시자가 모든 작업 세션에 쓰기를 갖는 새 주체가 된다. |
| **명령·결과 전달** | 비동기 접수 모델이다. `task-session-lifecycle/SKILL.md:70`: 「`session_write`의 성공은 **접수이며 완료가 아니다**」, 커서는 `nextOffset`/`seq`로 회수하고 응답값 그대로 보존(`sqlite-ledger.md:62`). | 부모→모니터→작업 세션의 **2단 접수**가 된다. 커서·seq가 한 단 더 늘어나고, 중간 단계의 「접수 불명」이 새 상태로 추가된다. 지금 1단에서도 접수불명 write 재전송 금지 규칙이 필요했다. |
| **도구 호출 승인 전달** | 호출별 승인은 **부모가 평가·정식 승인**한다 — `task-session-lifecycle/SKILL.md:18`(`human-tool-approval` 위임, 「자동 classifier 거절만으로 재질문하지 않으며 **정책 deny는 우회하지 않는다**」). 플랫폼 쪽은 AC-E2(턴 중 도구 승인, 세션 소유자가 결정). | 승인 요구는 **사용자에게 가는 질문**이다. 모니터를 중간에 두면 승인 경로가 사용자→부모→모니터→작업자로 길어지고, 승인 주체가 둘(부모/모니터)로 보이는 모호함이 생긴다. **승인 전달은 분리의 이득이 아니라 비용**이다. |
| **설정·시작/중지** | 시작 트리거는 「승인된 감시 요청/작업 접수, 새 대상 추가, 사용자 복귀와 해결 입력」이며 **작업 등록만으로 시작하지 않는다**. 중지는 `desired_state=paused/stopped` + generation 증가 + 정확한 `schedule_cancel` + 목록 부재 확인(상태전이표). | 분리하면 **제어 평면이 둘**이 된다. 사용자 중단 의도는 부모에 도착하는데 예약은 모니터 세션 pod에 있다. 부모가 모니터 세션에 write하고 그 세션이 자기 예약을 취소해야 하므로, 「취소 불명(pausing 유지)」 구간이 **구조적으로 상시화**된다. |
| **대상·주기 관리** | 대상 추가/제외는 최신 작업 승인과 monitor version을 읽고 **generation을 올려** 기록하며, 세대가 낡은 예약은 취소·부재 확인 후 재등록한다(「작업집합 변경과 복구」). | 대상 집합의 원본은 **작업 원장**이고 그 원장은 **부모 세션의 DB**에 있다(아래 참조). 모니터 세션은 자기 DB를 갖게 되므로 **대상 집합을 소유하지 않은 쪽이 주기를 돌리는** 구조가 된다. |
| **책임 generation 관리** | run 전에 `run ID·generation·원장 version`으로 **claim**을 기록하고, 「중복/이전 run은 관측·쓰기·알림·`loop_next`를 실행하지 않는다」. 외부 쓰기·알림·다음 예약 **직전에** generation·대상 membership·승인 version을 다시 읽는다(「한 run의 순서」 1·5). | 이 규칙은 **단일 원장 안에서 CAS로** 성립한다. 부모와 모니터가 각자 DB를 가지면 generation의 단일 원본이 사라져, 두 DB 사이의 합의 프로토콜을 새로 만들어야 한다. **분리의 가장 큰 설계 비용**이다. |
| **SQLite 원장 소유·격리** | DB는 **슬롯 PVC의 세션별 디렉터리**에 있고 **아카이브에 포함되지 않는다**. 같은 세션/슬롯의 재시작·복원만 같은 경로를 쓰고, PVC 소실·슬롯 이동을 견디지 않는다. 「과거 슬롯 공용 DB는 **소유 확인 없이 자동 이관하지 않는다**」(`sqlite-ledger.md:9`). 플랫폼 쪽: `session-platform` AC-N6 — 슬롯 PVC의 `db/`는 **사이드카만** 마운트하고 `/session-db/mcp`로만 닿는다. | **별도 세션 = 별도 DB.** 모니터를 분리하면 모니터 원장과 작업 원장이 **다른 PVC**에 놓인다. 두 원장을 한 트랜잭션으로 못 쓰고(`ledger_put`은 단일 레코드 CAS, `:14`), 지금 한 DB 안에서 공짜였던 「monitor ↔ task」 교차 참조가 **네트워크 경유 2단 CAS**가 된다. |
| **원장 API** | `ledger_get/put/delete` 세 개뿐. `ledger_put`은 **전체 task 교체 + `expected_version` CAS**, `request_id`로 멱등(동일 인자 재시도는 최초 커밋 응답 반환, 다른 내용에 같은 ID면 conflict) (`:13·14·20`). | 교차 세션 원장을 쓸 **API가 없다**. 한쪽이 상대 DB를 읽을 수단이 없으므로, 분리하면 **상태를 `session_write` 본문(대화)으로 옮겨야** 한다 — 지금 DB가 보장하던 CAS·멱등이 사라진다. |
| **중복 run 방지** | 「한 번에 하나만 실행된다」(self-paced) + run claim + generation 무효화 + 목록 대조. 「목록 오류는 예약 부재 증거가 아니다」. | 세션이 둘이면 **두 pod가 각자 예약을 가질 수 있다**. 이동(통합/분리) 절차가 이미 「출발 예약 무효화·취소 확인 뒤 도착 예약 활성화, 중간 실패는 이동 pending, **양쪽에서 같은 대상을 실행하지 않는다**」를 요구하는데, 분리는 그 위험 구간을 영구 구조로 만든다. |
| **복구·재시작·예약 유실** | 「예약은 **현재 부모의 실행 pod에만 존재**하며 freeze/restore/delete·pod 재시작으로 유실될 수 있다」 → `schedule_lost`. 「이 스킬/DB는 **wakeup을 만들지 않는다**」, **실제 사용자 복귀나 확인된 트리거**가 있어야 복구된다. 플랫폼은 AC-P3으로 **예약이 남아 있으면 유휴 회수를 미룬다**(에이전트에 `GET /scheduler`를 물어 `lastAccess` 갱신, 상한은 루프 수명 7일 = AC-P1). | 분리의 **유일한 실질 이득**이 여기다: 부모 세션이 동결·재시작돼도 모니터 세션의 예약은 남고, AC-P3이 그 세션을 살려 둔다. 다만 상한은 **7일**이고, 「사용자 주도 동결·삭제는 막지 않는다」. 그리고 **모니터 세션 자신의 유실**은 여전히 아무도 감지하지 못한다 — 감시자를 감시할 주체가 없다. |
| **알림 단일 담당** | 「사용자에게 보내는 채팅 결과와 PocketAide push는 **부모만** 담당한다」(`task-session-lifecycle/SKILL.md:108`, 「## 부모 전용 PocketAide 알림」:124). 작업자 계약에는 「알림은 **부모가 회수 후 단독 처리**」(:66). | 분리해도 **알림은 부모가 유지해야 한다**. 그러면 모니터는 관측만 하고 보고는 못 하므로, **부모가 모니터를 다시 폴링**해야 한다 — 부모를 깨우는 주체가 없다는 원래 문제가 그대로 남는다. 반대로 모니터에 알림을 주면 단일 담당 규칙이 깨지고 중복 push 억제(작업 ID·seq·단계·head 동일성 판정)의 단일 원본이 사라진다. |
| **스킬 수정·검증·버전·적용·롤백** | 수정은 `chat-skill-management`가 `codex-task` 작업 세션에 위임한다(부모는 셸·편집 없음). 검증은 `validate_marketplace.py`·`site/build.py`(:24), PR·CI까지 자율, **머지는 사용자 명시 요청**(:28~32). 적용은 **부모 자신의 `skills.refresh_skills({})`를 한 번** 호출하고 응답의 marketplace revision·`added/updated/removed`를 기록(:36·39·40). 확인은 변경 스킬을 `read_skill`로 **다시 읽기 전에는 그 지침을 따르지 않는다**(:41). | **적용은 구조적으로 부모 전용이다** — `refresh_skills`는 호출한 세션 자신의 스킬 집합을 갱신한다. 모니터를 분리하면 **스킬 집합이 둘**이 되고, 두 세션의 revision이 어긋나는 새 상태가 생긴다. 모니터 스킬만 올리거나 되돌리려면 모니터 세션에서 따로 refresh해야 하고, 그 확인(`read_skill` 재독)도 그 세션에서 해야 한다. **롤백 경로는 지금 문서화돼 있지 않다** — 되돌림은 marketplace를 되돌리는 PR + 각 세션의 refresh이며, 세션 단위 revision 고정(pin)은 계약에 없다. 플랫폼의 AC-J7 수동 플러그인 새로고침도 **대화를 유지한 채 스킬을 다시 받는** 것이지 버전 고정이 아니다. |

## 3. 결론

**지금 계약 위에서는 분리의 이득이 비용보다 작다.** 분리가 실제로 푸는 문제는
「부모 pod가 내려가면 예약도 사라진다」 하나이고, 그것은 이미 AC-P3이 **유휴 회수 경로에서는**
막아 준다(7일 상한). 반대로 분리는 다음을 새로 만든다:

1. **generation·원장의 단일 원본 소멸** — 2절 「책임 generation」·「SQLite 소유·격리」·「원장 API」.
   한 DB 안의 CAS로 성립했던 중복 방지가 두 PVC 사이의 합의 문제로 바뀐다. 교차 세션 원장
   API가 없으므로 상태가 대화 본문으로 내려간다.
2. **권한 축소 불가** — 통신 신원이 테넌트 단위(`sessionplatform.go:734`)라 「모니터는 읽기만」을
   플랫폼이 강제하지 못한다.
3. **알림 단일 담당과의 충돌** — 부모만 push하는 규칙을 지키면 부모를 깨울 주체가 여전히 없고,
   깨면 중복 억제의 단일 원본이 사라진다.
4. **스킬 revision 분기** — 적용(`refresh_skills`)이 세션 자신에게만 작용하므로 집합이 둘로 갈린다.

### 권고

**지금은 분리하지 않는다.** 대신 분리가 풀려던 「부모가 없으면 모니터도 없다」를 더 작은
변경으로 좁힌다 — 아래는 **제안이고 승인 대상이지, 이 조사에서 구현하지 않았다**:

- **(권고 1) 모니터 원장에 「유실 감지 근거」를 명시적으로 남긴다.** 지금도 `schedule_lost`
  상태는 있지만 **감지는 사용자 복귀에 의존**한다. 복귀 시 `schedule_list` ↔ 원장 대조를
  보고 형식의 필수 항목으로 올리면, 분리 없이 「조용히 안 도는」 구간을 사용자에게 드러낼 수 있다.
- **(권고 2) AC-P3의 7일 상한을 모니터 원장에 적어 둔다.** 루프 수명(P7D)이 곧 예약 보존
  상한이라는 사실이 지금은 플랫폼 PRD에만 있다. monitor.cadence/expiry에 그 상한과 재등록
  조건을 함께 기록하면 만료를 종료로 오인하지 않는다.
- **(권고 3) 분리를 다시 검토할 선행 조건을 못 박는다.** ① 교차 세션 원장 읽기 API(또는
  모니터 전용 공용 원장), ② 세션 단위 권한 축소(테넌트 아래 scope), ③ 알림 담당 이전 규칙 —
  이 셋 중 하나라도 없으면 분리는 2절의 비용을 그대로 지불한다. **셋이 생기면 재검토할 가치가 있다.**

분리를 그래도 하겠다면 가장 작은 모양은 **「모니터 세션은 관측·기록만, 알림·승인·대상 변경은
부모」**이고, 그때도 2절의 1번(원장 단일 원본)을 먼저 풀어야 한다.

## 4. 결정이 필요한 것 (사용자)

- 분리를 진행할 것인가, 권고 1~3으로 대신할 것인가.
- 분리한다면 권고 3의 선행 조건 중 무엇을 먼저 만들 것인가.
- 모니터 세션의 알림 권한을 옮길 것인가(= 「부모 전용 push」 규칙 개정 여부).
- 스킬 revision을 세션 단위로 고정(pin)할 필요가 있는가 — 지금 계약에 없는 기능이다.

## 5. 이 문서가 하지 않은 것 (한계)

- **구현·운영 변경 0** — 스킬·플랫폼 코드·예약·세션·운영 DB를 건드리지 않았다.
- **실측 없음** — 모든 서술은 **문서·코드 인용**이다. 실제 모니터 run의 지연·실패율·예약 유실
  빈도를 측정하지 않았다. 「AC-P3이 막아 준다」도 코드/PRD를 읽은 결론이며 운영 관측이 아니다.
- **`pocket-aide` 쪽은 수신면만 확인** — push 수신·히스토리 구조는 읽지 않았다. 알림 담당을
  옮기는 결정을 하려면 그 쪽 영향(디바이스·중복 억제·히스토리 그룹)을 따로 조사해야 한다.
- **롤백 경로는 계약에 없음을 확인한 것까지** — 되돌림 절차를 설계하지 않았다. 세션 단위
  revision pin이 필요한지는 4절의 결정 항목이다.
- **`IdleReaper` 분리는 다루지 않는다** — 다른 주제이고, 이 조사의 완료로 세지 않는다.
