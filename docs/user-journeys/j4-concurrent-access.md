## 1. 서비스 개요 (참고)

**Session Pod Platform** — 세션 상태 전이를 control plane이 단일하게 소유하여, 어떤 순서로 요청이 도달해도 세션이 하나의 유효한 상태로 수렴하게 하는 플랫폼.

- 제품 가치: [`../values.md`](../values.md) · 상태 API PRD: [`../prd/state-api.md`](../prd/state-api.md)

## 2. 여정 정의

**대상 사용자 (페르소나)**
P1 멀티세션 작업자 + P2 자동화 클라이언트. 사람과 프로그램이 같은 세션을 동시에 다룬다. P2는 사람의 개입 없이 read/write를 보내며 타이밍을 조율하지 않는다. (정의: [README.md](./README.md#페르소나))

**진입 맥락**
한 세션에 사람의 작업과 자동화의 호출이 겹치거나, 사용자 요청과 시스템의 동결·복원이 같은 순간에 발생한다.

**트리거**
동일 세션에 대한 요청이 시간적으로 겹치는 것. 사용자가 의도해서 만드는 상황이 아니다.

**사용자 목표**
어떤 타이밍에 요청을 보내도 세션 상태가 깨지지 않고 일관된 결과를 받는 것. 사용자 입장에서 이 여정의 성공은 **아무 일도 일어나지 않는 것**이다.

**완료 기준**
겹친 요청들이 처리된 뒤 세션이 하나의 유효한 상태로 조회되고, 중복 pod·이중 스냅샷이 존재하지 않는다.

## 3. 단계별 상세

### `J4-S1` 동시 요청 발생

- **사용자 행동**: 작업자가 write를 보내는 동안 자동화 클라이언트가 read를 보내거나, 복원과 스냅샷이 같은 시점에 트리거된다. 어느 쪽도 상대의 존재를 모른다.
- **터치포인트**: read/write/switch/snapshot API (사람과 프로그램이 같은 엔드포인트를 공유)
- **생각·감정**: (인지하지 못함) — 겹쳤다는 사실 자체를 사용자는 모른다
- **페인포인트 / 이탈 위험**: 겹침이 드물게만 재현되므로 문제가 생겨도 원인을 특정하기 어렵다 → 상태 전이를 서버가 단일하게 소유
- **관련 AC**: (직접 없음 — 상황 정의 단계)
- **mockup**: ⚪ 없음 — 백엔드 동시성, UI 비대상

### `J4-S2` 원자적 전이로 단일화

- **사용자 행동**: 없음. ConfigMap resourceVersion compare-and-swap(점유는 Lease)으로 단일 상태 전이만 성공하고, 중복 pod 기동·이중 스냅샷이 발생하지 않는다.
- **터치포인트**: 없음(control plane 내부)
- **생각·감정**: (해당 없음)
- **페인포인트 / 이탈 위험**: 경합에서 진 요청이 조용히 사라지면 클라이언트가 결과를 오해한다 → 실패한 전이는 충돌로 명시적으로 알림
- **관련 AC**: AC-C1
- **mockup**: ⚪ 없음 — 백엔드 동시성, UI 비대상

### `J4-S3` 일관된 결과

- **사용자 행동**: 작업자와 자동화 클라이언트 모두 유효한 단일 상태로 수렴한 세션을 보며 각자의 작업을 잇는다. 상태가 깨지거나 중복 처리되지 않는다.
- **터치포인트**: 각 클라이언트의 read/write 응답
- **생각·감정**: "평소랑 똑같네" — 성공의 증거가 무사건이라는 점이 이 여정의 특징이다
- **페인포인트 / 이탈 위험**: 한 번이라도 상태가 깨지면 플랫폼 신뢰가 통째로 무너진다 → 경합 경로를 테스트로 상시 고정
- **관련 AC**: AC-C1, AC-C3
- **mockup**: ⚪ 없음 — 백엔드 동시성, UI 비대상

## 4. 분기·예외 흐름

| 상황 | 처리 | 이어지는 단계 |
|---|---|---|
| 전이 경합에서 패배 | compare-and-swap 실패를 충돌로 반환, 상태는 변경되지 않음 | `J4-S3` |
| 동결과 재접근이 겹침 | 한쪽만 성공하고 세션은 단일 상태로 수렴 | `J2-S4` 또는 `J2-S2` |
| 비-active 세션에 동시 접근 | 각 요청이 "active 보장 후 처리" 규칙을 따르되 승격·복원은 한 번만 수행 | `J2-S4` |
| 점유 소유자가 사라짐 | Lease 만료로 점유가 회수되어 후속 요청이 진행 가능 | `J4-S2` |

## 7. 인접 여정과의 관계

- **J2(자리 비움과 재개)**: 동결과 복원이 겹치는 경합을 이 여정이 받아낸다.
- **J3(멀티세션 전환)**: 전환이 다른 요청과 겹칠 때의 원자성도 동일한 규약을 따른다.
- **J1(세션 생성)**: 세션-pod 1:1 격리(AC-A2)가 전제이며, 이 여정은 그 1:1이 경합 상황에서도 유지됨을 보장한다.
- **J5·J6**: 두 타입 모두 같은 상태 전이 규약 위에서 동작하므로 이 여정은 타입과 무관하다.

## 8. 구현 상태

- 세션 상태는 ConfigMap에 저장되고 `CompareAndSwapState`/`CompareAndSwapSession`으로 원자적으로 전이하며, 점유는 Lease로 관리한다.
- ⚠️ **페르소나 공백**: P2(자동화 클라이언트)는 이 여정에서만 등장하고, P2가 `claude-code` 세션을 다루는 시나리오는 아직 어느 여정도 다루지 않는다([README.md](./README.md) 미해결 항목).
