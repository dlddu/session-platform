## 1. 서비스 개요 (참고)

**Session Pod Platform** — 세션 하나를 전용 Kubernetes pod 하나에 매핑해 격리된 장시간 작업 환경을 제공하고, 유휴 세션을 동결했다 복원하는 플랫폼.

- 제품 가치: [`../values.md`](../values.md) (V1~V5·V8)
- 아키텍처: [`../prd/architecture.md`](../prd/architecture.md)

## 2. 여정 정의

**대상 사용자 (페르소나)**
P1 멀티세션 작업자. 여러 개의 장시간 상태 유지 세션을 동시에 보유하고 그 사이를 오간다. 세션의 생성·동결·복원은 시스템이 알아서 해주기를 기대하며, 자기는 작업 자체에만 집중하고 싶어 한다. (정의: [README.md](./README.md#페르소나))

**진입 맥락**
새로 시작할 작업이 생겼는데 기존 세션들은 각자 다른 작업 맥락에 물려 있다. 그 맥락을 건드리지 않고 깨끗한 환경이 하나 더 필요하다.

**트리거**
새 작업의 시작. 기존 세션에 섞어 쓰면 맥락이 오염된다는 판단.

**사용자 목표**
다른 세션에 영향을 주지도 받지도 않는 전용 작업 공간을 즉시 확보하고, 곧바로 작업을 시작하는 것.

**완료 기준**
세션 생성 요청이 성공 응답을 받고 세션이 `active` 상태로 조회되며, 첫 read/write가 정상 왕복한다.

## 3. 단계별 상세

### `J1-S1` 세션 생성 요청

- **사용자 행동**: 세션 이름을 정하고(필수) 워크로드 타입을 고른 뒤 생성을 요청한다. 타입을 생략하면 `shell`이며, `claude-code`를 고르면 모델도 함께 지정한다(선택 경험 상세는 `J6-S1`).
- **터치포인트**: `new-session.html` 생성 폼 · `POST /api/v1/sessions`
- **생각·감정**: "이름만 정하면 되나? 뭘 더 골라야 하지"
- **페인포인트 / 이탈 위험**: 이름 누락·알 수 없는 타입·형식 밖 모델은 pod가 뜨기도 전에 거부되고 요청 본문이 한계를 넘으면 별도 오류가 난다. 화면이 사유를 필드 단위로 보여주지 않으면 무엇을 고쳐야 할지 알 수 없다 → 오류를 입력 필드 옆에 표기
- **관련 AC**: AC-A1 (보조 AC-E1·E6)
- **mockup**: `new-session.html` ✅

### `J1-S2` 전용 pod 기동 대기

- **사용자 행동**: 요청을 보낸 뒤 세션이 준비되기를 기다린다. 그동안 control plane이 이 세션 전용 data plane pod를 정확히 1개 기동하고(1:1 매핑), 워크로드 에이전트에 도달되는지 확인한 뒤 세션 메타데이터를 등록한다. 응답을 받은 시점의 상태는 `active`.
- **터치포인트**: `new-session.html` 프로비저닝 진행 표시("Register session metadata" → "Schedule dedicated pod" → "Open read / write channel")
- **생각·감정**: "얼마나 걸리지?" — 기다리는 동안 내 세션이 남의 세션과 섞이지 않는다는 확신이 필요하다
- **페인포인트 / 이탈 위험**: 생성이 동기 처리라 pod 스케줄링이 늦으면 화면이 멈춘 것처럼 보인다. 에이전트에 도달하지 못하면 pod를 회수하고 생성 자체가 실패하므로 사용자에게는 "아무 일도 일어나지 않은 것"으로 보인다 → 진행 단계를 노출하고 실패 시 회수 사실까지 안내
- **관련 AC**: AC-A1, AC-A2
- **mockup**: `new-session.html` ✅

### `J1-S3` 격리된 작업

- **사용자 행동**: read/write API로 세션에서 작업한다. `shell` 타입이면 명령을 실행하고(`J5`), `claude-code` 타입이면 프롬프트를 보낸다(`J6`). 다른 세션 pod의 장애·부하·보안 이슈는 이 세션으로 전파되지 않는다.
- **터치포인트**: `workspace.html` 세션 작업 화면 · `POST /api/v1/sessions/{id}/read`·`/write`
- **생각·감정**: "다른 세션이 터져도 내 건 안전한가"
- **페인포인트 / 이탈 위험**: 격리는 눈에 보이지 않는 보장이라 화면에 근거가 없으면 신뢰가 생기지 않는다 → 세션-pod 1:1 매핑을 화면에 명시
- **관련 AC**: AC-A2, AC-C2, AC-C3
- **mockup**: `workspace.html` ✅ — ⚠️ `claude-code` 타입으로 만든 세션의 이 단계는 `agent-workspace.html`에 해당하나 `../mockups/README.md`의 매핑에는 기재되어 있지 않음(미해결)

## 4. 분기·예외 흐름

| 상황 | 처리 | 이어지는 단계 |
|---|---|---|
| 입력 검증 실패(이름 누락·알 수 없는 타입·형식 밖 모델) | pod를 기동하기 전에 거부하고 사유를 반환 | `J1-S1` 재진입 |
| 요청 본문 한계 초과 | 본문 크기 초과로 거부 | `J1-S1` 재진입 |
| pod는 떴으나 워크로드 에이전트에 도달 실패 | 방금 띄운 pod를 회수하고 생성을 실패시킴(active로 만들지 않음) | `J1-S1` 재진입 |
| 세션 메타데이터 저장 실패 | 방금 띄운 pod를 best-effort 롤백 후 실패 응답 | `J1-S1` 재진입 |
| 생성 후 손을 떼고 유휴가 쌓임 | 유휴 60분에 도달하면 동결 | `J2-S1` |
| `claude-code` 타입을 고름 | 타입·모델 선택이라는 축이 추가된 생성 경험 | `J6-S1` |

## 7. 인접 여정과의 관계

- **J5(쉘에서 명령 실행)**: `J1-S3`의 `shell` 타입 구체화가 `J5-S2`·`J5-S3`다.
- **J6(작업 환경 선택 + 에이전트 루프)**: `J6-S1`은 `J1-S1`에 타입·모델 선택 축이 추가된 것이다. `J1-S2`(전용 pod 기동)는 타입과 무관하게 그대로 성립한다.
- **J2(자리 비움과 재개)**: 이 여정이 만든 `active` 세션이 J2의 동결·복원 대상이 된다.
- **J3(멀티세션 전환)**: 이 여정이 반복되어 세션이 여러 개가 되면 J3이 시작된다.

## 8. 구현 상태

- 세션 생성은 **동기 처리**다: pod 기동 → 워크로드 에이전트 도달 확인 → 메타데이터 저장 → `active`로 성공 응답. 도달 확인이나 저장이 실패하면 pod를 회수·롤백한다.
- 타입 생략은 `shell`로 정규화되고, 알 수 없는 타입·형식 밖 모델은 pod 기동 이전에 거부된다.
- ⚠️ **미기술 영역**: 세션 수명 종료(삭제)는 API와 화면에 구현되어 있으나 어느 여정도 담당하지 않는다. AC-A3("종료·동결 시 자원 회수") 중 "종료" 절반이 미할당 상태다.
