## 1. 서비스 개요 (참고)

**Session Pod Platform** — 세션 하나를 전용 pod 하나에 매핑하고, 유휴 세션을 동결해 자원을 회수했다가 재접근 시 복원하는 플랫폼.

- 제품 가치: [`../values.md`](../values.md) · 수명주기 PRD: [`../prd/lifecycle.md`](../prd/lifecycle.md)

## 2. 여정 정의

**대상 사용자 (페르소나)**
P1 멀티세션 작업자. 세션을 켜둔 채 회의·다른 업무로 자리를 비우는 일이 잦다. 돌아왔을 때 하던 자리 그대로이기를 기대하며, 그 사이 자원이 어떻게 관리되는지는 알고 싶어 하지 않는다. (정의: [README.md](./README.md#페르소나))

**진입 맥락**
`active` 세션에서 작업하던 중 다른 일이 생겨 손을 뗀다. 세션을 정리하거나 저장하는 행위는 하지 않는다.

**트리거**
작업자의 이탈. 마지막 클라이언트 read/write 이후 유휴 시간이 쌓이기 시작한다.

**사용자 목표**
자리를 비우는 동안 아무것도 신경 쓰지 않고, 돌아왔을 때 떠날 때의 맥락에서 곧바로 이어가는 것.

**완료 기준**
재접근 요청이 성공하고 세션이 다시 `active`로 조회되며, 동결 이전의 상태(쉘 프로세스 트리 또는 대화 기록·작업 디렉터리)가 유지된 채 다음 명령·프롬프트가 처리된다.

## 3. 단계별 상세

### `J2-S1` 작업 중 이탈

- **사용자 행동**: 세션에서 손을 떼고 다른 일을 한다. 유휴 시간은 **마지막 클라이언트 read/write**부터 잰다.
- **터치포인트**: 없음(사용자 행위의 부재가 곧 신호) · 세션 목록의 상태 표시
- **생각·감정**: "잠깐 다녀올 건데 이거 꺼도 되나?" — 대개는 아무 생각 없이 그냥 떠난다
- **페인포인트 / 이탈 위험**: 얼마나 비우면 동결되는지 화면에 보이지 않으면, 돌아왔을 때 상태가 바뀐 이유를 이해하지 못한다 → 남은 시간을 목록·작업 화면에 표기
- **관련 AC**: (직접 없음, `J5-S1`~`S3`·`J6-S2`~`S3`의 read/write가 `lastAccess`를 갱신 — AC-D5)
- **mockup**: ⚠️ 부분 — `index.html` 목록의 idle 상태 / `workspace.html` lifecycle. 전용 화면 없음

### `J2-S2` 60분 도달 시 동결

- **사용자 행동**: 없음. 시스템이 유휴 60분(최대 한계)에 도달하면 워크로드별 snapshot(`shell`=CRIU 체크포인트, `claude-code`=filesystem archive)을 만들고 상태를 `snapshot`으로 전이한 뒤 pod와 점유 자원(CPU/메모리)을 회수한다. 작업자는 이 과정을 직접 보지 않는다.
- **터치포인트**: 없음(백그라운드) · 사후적으로 세션 목록의 `snapshot` 상태
- **생각·감정**: (자리에 없음) — 돌아와서야 "얘 멈췄네?"를 인지한다
- **페인포인트 / 이탈 위험**: 동결 사실을 알리지 않으면 복원 지연을 장애로 오인한다. 동결이 실패하면 자원이 회수되지 않은 채 남는다 → 상태 전이를 목록에 즉시 반영
- **관련 AC**: AC-B1, AC-A3
- **mockup**: ⚠️ 부분 — `restore.html`/`agent-workspace.html`의 auto-freeze 표기. 동결 진행 전용 화면 없음

### `J2-S3` 재접근

- **사용자 행동**: 나중에 그 세션에 다시 접근한다(read/write 또는 세션 전환).
- **터치포인트**: 세션 목록에서 세션 선택 · read/write/switch 요청
- **생각·감정**: "아까 하던 거 그대로 있겠지?" — 여기서 신뢰가 시험된다
- **페인포인트 / 이탈 위험**: 복원에 시간이 걸리는데 아무 표시가 없으면 실패로 오인해 재요청·이탈한다 → 복원 중임을 명시
- **관련 AC**: AC-C2, AC-C3(비-active 접근은 "active 보장 후 처리")
- **mockup**: ❌ 없음 — 복원의 트리거 단계, 전용 화면 없음(의도적 제외 여부 미결)

### `J2-S4` 복원 후 재개

- **사용자 행동**: 복원된 세션에서 하던 작업을 잇는다. 시스템은 새 pod에 워크로드별 snapshot을 복원하고 상태를 `active`로 전이한다. `shell`은 CRIU로 프로세스 트리를, `claude-code`는 archive로 대화 기록·작업 디렉터리·누적 출력/커서를 이어받는다.
- **터치포인트**: `restore.html`(shell) · `agent-workspace.html`(claude-code)
- **생각·감정**: "어? 그대로네" — 멈췄다는 사실을 거의 인지하지 못한다
- **페인포인트 / 이탈 위험**: 복원이 실패하거나 일부만 되면 신뢰가 한 번에 무너진다. 동결 전에 받은 출력 커서가 무효화되면 화면이 이력을 잃는다 → 커서를 아카이브에 포함해 복원 후에도 유효하게 유지
- **관련 AC**: AC-B2, AC-B3
- **mockup**: `restore.html`(shell), `agent-workspace.html`(claude-code) ✅

## 4. 분기·예외 흐름

| 상황 | 처리 | 이어지는 단계 |
|---|---|---|
| 유휴 중 다시 접근(동결 전) | 유휴 카운트가 초기화되고 그대로 `active` 유지 | `J2-S1` 재진입 |
| `idle` 상태에서 read/write | 동일 pod를 유지한 채 `idle→active`로 원자적 승격 후 처리 | `J2-S4` |
| `snapshot` 상태에서 read/write | 복원해 `active`로 만든 뒤 처리(write는 복원 후 반영) | `J2-S4` |
| 동결과 재접근이 동시에 발생 | 원자적 전이로 한쪽만 성공, 이중 스냅샷·중복 pod 없음 | `J4-S2` |
| `claude-code` 타입의 동결·복원 | CRIU 없이 파일시스템 아카이브 경로로 처리 | `J6-S5` |
| 복원 실패 | 세션은 `active`가 되지 않으며 오류를 반환 | `J2-S3` 재진입 |

## 7. 인접 여정과의 관계

- **J1(세션 생성)**: J1이 만든 `active` 세션이 이 여정의 출발점이다.
- **J5(쉘 사용 루프)**: `J5-S4`에서 축적된 쉘 프로세스 트리가 이 여정의 보존 대상이다. J5의 read/write가 유휴 카운트 기준(AC-D5)이다.
- **J6(에이전트 루프)**: `J6-S5`가 이 여정을 `claude-code` 경로로 밟는다. 사용자가 보는 흐름은 동일하고 메커니즘만 갈린다.
- **J3(멀티세션 전환)**: 전환 대상이 `snapshot`이면 `J3-S3`이 이 여정의 복원 경로를 그대로 탄다.
- **J4(동시 접근)**: 동결과 복원이 겹칠 때의 원자성은 J4가 담당한다.

## 8. 구현 상태

- 유휴 판정은 `active`/`idle` 레코드를 직접 검사하는 reaper가 담당하며, 별도의 operational `active→idle` producer는 없다.
- `idle` 세션은 pod를 유지한 채 원자적으로 `active`로 승격되고, `snapshot` 세션은 복원 후 처리된다.
- ⚠️ **미결**: 유휴 60분의 grace period·busy-shell 세부 정책은 열린 항목이다([README.md](./README.md) 미해결 항목 참고).
