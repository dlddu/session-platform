## 1. 서비스 개요 (참고)

**Session Pod Platform** — 세션마다 전용 pod를 두어 격리하고, 세션 사이를 오갈 때도 각 세션의 상태를 보존하는 플랫폼.

- 제품 가치: [`../values.md`](../values.md) · 상태 API PRD: [`../prd/state-api.md`](../prd/state-api.md)

## 2. 여정 정의

**대상 사용자 (페르소나)**
P1 멀티세션 작업자. 서로 다른 작업 맥락을 세션 단위로 나눠 두고 하루에도 여러 번 오간다. 전환 비용이 크면 세션을 나누는 의미 자체가 사라진다고 느낀다. (정의: [README.md](./README.md#페르소나))

**진입 맥락**
이미 세션을 두 개 이상 보유하고 있고, 한 세션에서 작업하던 중 다른 세션의 작업이 필요해진다.

**트리거**
작업 맥락의 변경. 세션 A의 작업이 대기 상태가 되거나 세션 B에 급한 일이 생긴다.

**사용자 목표**
전환 대상 세션이 어떤 상태(`active`/`idle`/`snapshot`)든 신경 쓰지 않고, 일관된 경험으로 오가는 것.

**완료 기준**
전환 요청 후 대상 세션이 `active`로 조회되고, 되돌아온 세션에서도 떠날 때의 상태가 보존된 채 작업이 이어진다.

## 3. 단계별 상세

### `J3-S1` 세션 목록 확인

- **사용자 행동**: 보유한 세션들과 각 상태(`active`/`idle`/`snapshot`), 워크로드 타입을 확인한다.
- **터치포인트**: `index.html` 세션 목록 대시보드 · `GET /api/v1/sessions`
- **생각·감정**: "지금 뭐가 살아 있고 뭐가 얼어 있지?"
- **페인포인트 / 이탈 위험**: 세션이 늘어나면 목록에서 목표 세션을 찾는 비용이 커진다. 상태·타입이 한눈에 안 보이면 잘못된 세션을 연다 → 상태 배지와 workloadType 태그 표기
- **관련 AC**: (직접 없음 — ⚠️ 목록 조회가 PRD에 명시되지 않음, 아래 8절 참고)
- **mockup**: `index.html` ✅

### `J3-S2` 세션 B로 전환

- **사용자 행동**: `active`인 세션 A에서 작업하다 세션 B를 선택해 전환한다.
- **터치포인트**: `index.html` → `workspace.html`/`agent-workspace.html` 네비게이션 · `POST /api/v1/sessions/{id}/switch`
- **생각·감정**: "바로 열리겠지" — 전환은 무의식적 동작이라 지연에 민감하다
- **페인포인트 / 이탈 위험**: A에서 진행 중이던 작업이 전환 때문에 끊기거나 유실될까 하는 불안 → 전환이 A에 영향을 주지 않음을 화면에 명시
- **관련 AC**: AC-C4
- **mockup**: ⚠️ 부분 — 목록↔작업 화면 네비게이션으로 암시. 전용 화면 없음

### `J3-S3` 대상 상태에 따른 활성화

- **사용자 행동**: (시스템 처리를 기다린다) B가 `snapshot`이면 복원해 `active`로 전이하고, `idle`이면 원자적으로 승격하며, 이미 `active`면 그대로 접근시킨다. 전환은 세션 격리(1:1 pod)를 깨지 않는다.
- **터치포인트**: `restore.html`(대상이 snapshot일 때) · 작업 화면
- **생각·감정**: "왜 어떤 건 바로 열리고 어떤 건 기다려야 하지"
- **페인포인트 / 이탈 위험**: 상태에 따라 대기 시간이 달라지는데 그 이유가 안 보이면 불안정한 시스템으로 느껴진다 → 복원 중임을 상태 배지로 설명
- **관련 AC**: AC-C4
- **mockup**: ⚠️ 부분 — 대상이 snapshot이면 `restore.html`로 전환되는 것으로 암시

### `J3-S4` 다시 A로 복귀

- **사용자 행동**: 다시 세션 A로 전환한다. A의 상태가 보존되어 있어 전환 대상의 상태와 무관하게 일관된 경험으로 재개된다.
- **터치포인트**: 세션 목록 → A의 작업 화면
- **생각·감정**: "아까 그대로네" — 왕복이 안전하다는 확인이 반복되면 세션을 더 적극적으로 나눠 쓰게 된다
- **페인포인트 / 이탈 위험**: A가 자리를 비운 사이 유휴 한계에 도달해 동결되면 복귀에 대기가 생긴다 → 남은 유휴 시간을 목록에 표기
- **관련 AC**: AC-C4, AC-B3
- **mockup**: ❌ 없음 — 전용 화면 없음(의도적 제외 여부 미결)

## 4. 분기·예외 흐름

| 상황 | 처리 | 이어지는 단계 |
|---|---|---|
| 전환 대상이 `idle` | 동일 pod를 유지한 채 원자적으로 `active`로 승격 | `J3-S3` |
| 전환 대상이 `snapshot` | 복원 경로를 타고 `active`로 전이 | `J2-S4` |
| 전환 대상이 이미 `active` | 복원 없이 그대로 접근 | `J3-S3` |
| 떠나 있는 사이 원 세션이 동결됨 | 복귀 시 복원 후 재개 | `J2-S3` |
| 두 클라이언트가 같은 세션을 동시에 전환 | 원자적 전이로 하나만 성공, 중복 pod 없음 | `J4-S2` |
| 타입이 섞인 세션 간 전환 | 타입에 따라 작업 화면이 갈리되 출력 커서 규약은 동일 | `J5` 또는 `J6` |

## 7. 인접 여정과의 관계

- **J1(세션 생성)**: J1이 반복되어 세션이 여러 개가 되면 이 여정이 성립한다.
- **J2(자리 비움과 재개)**: `J3-S3`에서 대상이 `snapshot`이면 J2의 복원 경로를 그대로 탄다.
- **J4(동시 접근)**: 전환이 다른 요청과 겹칠 때의 원자성은 J4가 담당한다.
- **J5·J6**: 전환 후의 작업 루프는 세션 타입에 따라 J5(쉘) 또는 J6(에이전트)로 갈린다. 타입이 달라도 전환 규약과 출력 커서 계약은 같다.

## 8. 구현 상태

- 세션 목록 조회(`GET /api/v1/sessions`)와 목록 화면이 구현되어 있고, 전환은 전용 엔드포인트로 처리되며 `idle`에서 승격된 경우 접근 시각을 갱신한다.
- ⚠️ **문서 공백**: 목록 조회 흐름이 구현·화면에는 있으나 **PRD에 대응 AC가 없다**. `J3-S1`의 AC 칸이 빈 이유이며, PRD 보강이 필요하다([README.md](./README.md) 미해결 항목).
