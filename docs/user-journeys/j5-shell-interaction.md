## 1. 서비스 개요 (참고)

**Session Pod Platform** — `shell` 타입 세션은 전용 pod 안에서 PTY에 연결된 인터랙티브 쉘을 돌리고, 그 쉘 프로세스 트리를 세션의 보존 대상 상태로 삼는다.

- 제품 가치: [`../values.md`](../values.md) · 쉘 워크로드 PRD: [`../prd/shell-workload.md`](../prd/shell-workload.md)

## 2. 여정 정의

**대상 사용자 (페르소나)**
P1 멀티세션 작업자. 명령을 직접 치는 방식에 익숙하고, 환경 변수·작업 디렉터리처럼 앞선 명령이 만든 상태가 다음 명령에 이어지는 것을 당연하게 기대한다. (정의: [README.md](./README.md#페르소나))

**진입 맥락**
`J1`로 만든 `shell` 타입 세션이 `active` 상태다. J1이 "세션을 만드는" 여정이라면 이 여정은 그 안에서 "실제로 무엇을 하는가" — 세션의 핵심 사용 루프다.

**트리거**
작업자가 세션 작업 화면을 열고 첫 명령을 입력하려 한다.

**사용자 목표**
로컬 터미널을 쓰듯 명령을 실행하고, 그 과정에서 쌓인 상태가 중단 없이 이어지는 것.

**완료 기준**
입력한 명령의 출력을 확인하고, 앞선 명령이 만든 상태(환경 변수·작업 디렉터리 등)가 이어진 채 다음 명령이 실행된다.

## 3. 단계별 상세

### `J5-S1` 쉘 연결

- **사용자 행동**: 세션이 `active`가 되면 전용 data plane pod 안에서 PTY에 연결된 인터랙티브 쉘(기본 `/bin/bash`)이 이미 기동되어 있고, 작업자는 이 쉘에 연결한다.
- **터치포인트**: `workspace.html` session shell 콘솔
- **생각·감정**: "터미널이랑 똑같이 쓰면 되겠네"
- **페인포인트 / 이탈 위험**: 연결 여부가 화면에 드러나지 않으면 명령을 쳐도 되는지 알 수 없다 → 쉘 attach 상태와 프롬프트를 명시
- **관련 AC**: AC-D1
- **mockup**: `workspace.html` — session shell 콘솔 ✅

### `J5-S2` 명령 입력

- **사용자 행동**: write API로 쉘 stdin에 명령을 보낸다(예: `ls`, `cd /work`, `export KEY=…`). 개행이 포함된 입력은 쉘이 명령으로 실행한다.
- **터치포인트**: `workspace.html` input-row `$` 프롬프트 · `POST /api/v1/sessions/{id}/write`
- **생각·감정**: "엔터 치면 도는 건가?" — 로컬 터미널과 다른 점이 있는지 탐색한다
- **페인포인트 / 이탈 위험**: 개행 없이 보낸 입력은 실행되지 않는데 화면상 차이가 없으면 멈춘 것으로 오인한다 → 입력이 전송되었음을 콘솔에 즉시 반영
- **관련 AC**: AC-D2
- **mockup**: `workspace.html` — input-row `$` 프롬프트 ✅

### `J5-S3` 출력 확인

- **사용자 행동**: read API로 쉘 출력(stdout/stderr)을 확인한다. read는 서버가 직전 응답에 발급한 `nextOffset` 커서 이후의 **델타**를 반환하므로 반복 조회는 신규 출력만 받고, `offset=0`으로 읽으면 세션 시작 이후 **전체** 스크롤백이 반환된다(재진입 시 이력 복원). read는 비파괴적이라 서버는 출력을 버리지 않는다.
- **터치포인트**: `workspace.html` term(stdout 렌더) · `POST /api/v1/sessions/{id}/read`
- **생각·감정**: "아까 것까지 다 남아 있네" — 재진입 시 이력이 살아 있으면 안심한다
- **페인포인트 / 이탈 위험**: 커서를 잃으면 출력이 중복되거나 누락된 것처럼 보인다 → `offset=0` 전체 조회로 복구 가능하게 유지
- **관련 AC**: AC-D3
- **mockup**: `workspace.html` — term stdout ✅

### `J5-S4` 쉘 상태 축적과 이어짐

- **사용자 행동**: 앞선 명령이 만든 상태(환경 변수, 현재 작업 디렉터리, 쉘 변수·함수, 실행 중 포그라운드 프로세스)를 전제로 다음 명령을 실행한다. 이 쉘 프로세스 트리가 곧 세션의 보존 대상 상태이며, idle·snapshot·restore(`J2`)를 거쳐도 동결 직전 맥락 그대로 재개된다.
- **터치포인트**: `workspace.html` Shell state 패널(cwd·env·shell var·background job)
- **생각·감정**: "이게 체크포인트되는 거구나" — 무엇이 보존되는지 알면 세션을 믿고 떠날 수 있다
- **페인포인트 / 이탈 위험**: 무엇이 보존 대상인지 보이지 않으면 동결 전에 불필요한 방어(수동 저장)를 하게 된다 → 보존 대상을 화면에 명시
- **관련 AC**: AC-D4 (보조 AC-B3)
- **mockup**: `workspace.html` — Shell state 패널 ✅

## 7. 인접 여정과의 관계

- **J1(세션 생성)**: J1이 pod를 기동해 `active` 세션을 만들면 이 여정은 그 세션의 쉘을 쓰는 루프다. `J1-S3`(격리된 작업)의 구체화가 `J5-S2`·`J5-S3`다.
- **J2(자리 비움과 재개)**: `J5-S4`에서 축적된 쉘 상태가 J2의 snapshot/restore 대상이다. J2의 "인메모리 상태 보존"이 여기서는 쉘 프로세스 트리로 구체화된다.
- **J6(에이전트 루프)**: 같은 축의 타입별 쌍이다. J5는 `shell` 타입의 사용 루프(직접 명령), J6는 `claude-code` 타입의 사용 루프(프롬프트)이며, append-only 출력과 offset 커서 계약은 두 타입이 동일하다.
- **유휴 판정(AC-D5)**: J5의 read/write가 세션 `lastAccess`를 갱신하며, 이 클라이언트 쉘 I/O의 부재가 J2의 60분 유휴 카운트 기준이다.

## 8. 구현 상태

- `J5-S1`은 2026-07-02 구현(PTY 쉘 에이전트 기동 + `active` 전이 도달 검증).
- `J5-S2`·`J5-S3`은 2026-07-03 구현 — 에이전트 scrollback + HTTP `/write`·`/read`, control plane이 AgentClient를 경유해 write→stdin·read→offset 커서 델타를 처리, web Workspace 쉘 콘솔(`$` input-row, 재진입 시 전체 이력 복원).
- `J5-S4`는 agent-driven in-pod CRIU + durable archive로 구현되어 kind 배포 e2e가 실제 상태·커서 왕복을 단언한다.
- ⚠️ production gate는 기본 off이며, S3/IAM·privileged 보안 정책을 별도로 준비해야 한다.
